# Quantor — пакет промтов для Opus 5.5
## Расчётный портал стадии П

---

# ОБЩИЙ КОНТЕКСТ ДЛЯ ВСЕХ ПРОМТОВ

Мы развиваем проект Quantor.

Текущий приоритет — создать внутри Quantor инженерный расчётный портал для тендерной стадии П.

ВАЖНО:

1. Основной сценарий сейчас — стадия П с недостаточной инженерной детализацией.
2. Стадия РД сейчас НЕ реализуется. Нужно лишь не создать архитектурный тупик для будущего расширения.
3. ВОР не создаётся нами с нуля как основной результат. ВОР, как правило, поступает от Заказчика.
4. Quantor должен независимо рассчитывать ожидаемый состав и объёмы инженерных систем и сравнивать их с ВОР Заказчика.
5. Архитектура, квартирография, таблицы потребителей, таблицы воздухообменов, задания смежных разделов, ТУ, текстовые документы и другие разделы проекта могут являться источниками расчётных исходных данных.
6. При недостаточности данных разрешены инженерные допущения, но каждое допущение должно быть явно зарегистрировано и видно пользователю.
7. Любая величина должна иметь происхождение:
   - исходный документ;
   - непосредственно считанное значение;
   - вычисленное значение;
   - нормативное правило;
   - правило производителя;
   - инженерное допущение;
   - ручной ввод.
8. Математические инженерные расчёты должны выполняться детерминированным кодом. LLM-модель не должна быть источником арифметического результата.
9. LLM может использоваться для:
   - понимания документа;
   - классификации таблиц;
   - извлечения исходных данных;
   - сопоставления сущностей;
   - поиска противоречий;
   - предложения кандидатов;
   но результат инженерного расчёта должен воспроизводиться кодом.
10. Старый расчётный портал использовать как read-only (только чтение) источник формул, идей, состава расчётов и контрольных сценариев. Не переносить его архитектуру в Quantor буквально.
11. Все коэффициенты старого портала должны быть классифицированы. Нельзя автоматически считать неизвестный коэффициент нормативным.
12. Base recognition (базовое распознавание) Quantor не переделывать.
13. OCR (оптическое распознавание текста), растровый pipeline (конвейер обработки растра), детекторы и существующую базовую обработку PDF не менять без отдельного решения.
14. Замороженную синтетическую ветку MEP v0.3, Quantity Engine 0.3.1, MOCK /experiments/mep и сценарии A/B/C/D не ломать и не переписывать.
15. Новый расчётный контур должен существовать отдельно и потреблять уже доступные артефакты Quantor.
16. Полноценный MEP semantic (семантический граф инженерной сети) не является обязательным входом расчётного портала.
17. В будущем существующий MEP semantic сможет выступать ещё одним источником фактов проекта.
18. Все новые возможности по возможности размещать за отдельным feature flag (флагом функции).
19. Для критических инженерных формул обязательны автоматические тесты.
20. Не продолжать следующий этап автоматически. В конце каждого этапа дать отчёт и остановиться.

# PROMPT 00 — АУДИТ И АРХИТЕКТУРА НОВОГО РАСЧЁТНОГО КОНТУРА

Изучи текущий репозиторий Quantor и архив старого расчётного портала.

На этом этапе НЕ ПИШИ production-код (рабочий код продукта).

Задача — спроектировать правильную архитектуру расчётного портала стадии П.

Целевая цепочка:

Документы / архитектура / таблицы / ВОР Заказчика / ручной ввод
→ Facts Registry (реестр фактов проекта)
→ подготовка расчётных исходных данных
→ детерминированный инженерный расчёт
→ синтез предполагаемой структуры системы
→ расчёт ожидаемых количеств
→ сверка с ВОР Заказчика
→ вопросы / риски / допущения.

Проведи:

1. Аудит существующей архитектуры Quantor.
2. Определи существующие компоненты, которые можно переиспользовать.
3. Отдельно укажи компоненты, которые нельзя менять из-за ранее принятых решений.
4. Полностью проанализируй старый расчётный портал.
5. Составь таблицу его расчётных функций по системам.
6. Для каждой формулы старого портала классифицируй её как:
   - физическая/математическая;
   - нормативная;
   - правило производителя;
   - геометрическая;
   - инженерная эвристика;
   - тендерный коэффициент;
   - неизвестного происхождения;
   - потенциально ошибочная.
7. Выяви hidden assumptions (скрытые допущения).
8. Найди архитектурные и инженерные риски прямого переноса.
9. Предложи целевую структуру модулей Quantor.
10. Определи границы между:
   - извлечением данных;
   - реестром фактов;
   - расчётным ядром;
   - библиотекой правил;
   - синтезом системы;
   - расчётом количеств;
   - сопоставлением с ВОР;
   - интерфейсом.

Обязательно предложи ADR (запись архитектурного решения) для нового расчётного контура.

Отдельно ответь:

- нужен ли полноценный MEP semantic сейчас;
- какие функции текущего MEP semantic можно использовать опционально;
- как подключить MEP semantic позже без изменения расчётного ядра;
- где должна находиться граница между LLM и детерминированными расчётами.

В конце предоставь:

A. карту текущей архитектуры;
B. карту предлагаемой архитектуры;
C. список файлов/модулей, которые потребуется создать;
D. список существующих файлов, которые придётся изменить;
E. риски;
F. последовательность реализации;
G. что НЕ должно быть сделано сейчас.

Не реализовывай следующий этап.

# PROMPT 01 — КОНТРАКТЫ ДАННЫХ И РЕЕСТР ФАКТОВ ПРОЕКТА

На основании утверждённого Prompt 00 реализуй фундамент нового расчётного контура: Facts Registry (реестр фактов проекта).

Это центральное хранилище исходных данных для всех инженерных расчётов.

Нам нужны как минимум сущности:

ProjectFact
FactSource
FactEvidence
FactConflict
ManualOverride
CalculationInput
Assumption
RuleReference
CalculationRun
CalculationStep
CalculationResult
ExpectedQuantity
CustomerVorItem
VorMatch
ProjectQuestion.

Каждый ProjectFact должен поддерживать:

- тип факта;
- значение;
- единицу измерения;
- корпус;
- секцию;
- этаж;
- помещение, если применимо;
- инженерную систему;
- источник;
- документ;
- страницу/лист;
- координаты/ссылку на исходный фрагмент, если доступны;
- метод получения;
- confidence (уверенность);
- дату;
- версию;
- статус проверки человеком.

Методы получения минимум:

DOCUMENT_EXPLICIT
TABLE_EXPLICIT
GEOMETRY_MEASURED
CALCULATED
INFERRED
NORMATIVE
MANUFACTURER_RULE
ASSUMPTION
MANUAL.

Нужна полноценная provenance (прослеживаемость происхождения).

Если два документа сообщают разные значения одного факта, нельзя молча выбрать один.

Нужно создать конфликт с вариантами и источниками.

Добавь механизм приоритета источников, но не зашивай глобальную истину вроде «спецификация всегда главнее плана».

Приоритет должен зависеть от типа факта и стадии документа.

Реализуй минимальные API (интерфейсы программирования) и хранилище.

Создай автоматические тесты.

Не реализовывай сами расчёты инженерных систем.

В конце:
- перечисли контракты;
- покажи примеры фактов;
- покажи пример конфликта;
- покажи пример ручного подтверждения;
- дай результаты тестов;
- остановись.

# PROMPT 02 — СБОР РАСЧЁТНЫХ ИСХОДНЫХ ДАННЫХ СТАДИИ П

Теперь необходимо научить Quantor собирать исходные данные для расчёта стадии П.

Не разрабатывай новый OCR.

Используй существующие выходы распознавания Quantor.

Не привязывай систему только к инженерным чертежам.

Источниками фактов могут быть:

- АР;
- квартирография;
- экспликация помещений;
- разрезы;
- планы этажей;
- генплан;
- ВОР Заказчика;
- таблицы потребителей;
- таблицы нагрузок;
- таблицы воздухообменов;
- таблицы санитарных приборов;
- текстовые пояснительные записки;
- ТУ;
- задания смежных разделов;
- бренд-листы;
- технические требования;
- ручной ввод.

Создай слой Source Adapters (адаптеры источников), преобразующий различные результаты распознавания в ProjectFact.

Важный принцип:

система должна уметь сказать не только:
«значение найдено»,

но и:
«для расчёта В1 необходимо N параметров, найдено 12, отсутствует 4».

Реализуй понятие Input Requirement (требуемое исходное данное).

Для каждого будущего калькулятора должна существовать декларация:

REQUIRED
DESIRABLE
OPTIONAL
DERIVABLE.

Если REQUIRED отсутствует, расчёт может:
- остановиться;
- запросить ручное значение;
- либо перейти в сценарий расчётного допущения, если для данного параметра такой режим разрешён.

Не позволяй системе незаметно придумывать значения.

Создай базовый экран/интерфейс «Исходные данные проекта»:

Факт | Значение | Ед. | Источник | Надёжность | Используется в | Статус.

Реализуй тесты и остановись.

# PROMPT 03 — БИБЛИОТЕКА ИНЖЕНЕРНЫХ ПРАВИЛ И НОРМАТИВОВ

Создай Rule Registry (реестр правил).

Нельзя размещать инженерные коэффициенты хаотично внутри расчётного кода.

Любое правило должно быть самостоятельной версионируемой сущностью.

Типы правил:

PHYSICS
GEOMETRY
NORMATIVE
MANUFACTURER
ENGINEERING
TENDER_ASSUMPTION.

Для правила необходимо хранить:

- ID;
- название;
- инженерную систему;
- описание;
- формулу/алгоритм;
- единицы;
- диапазон применимости;
- источник;
- нормативный документ;
- редакцию;
- дату действия;
- производителя, если применимо;
- статус инженерной проверки;
- комментарий;
- версию.

Отдельно импортируй знания из старого расчётного портала.

НО:

не переносить все коэффициенты как подтверждённые правила.

Каждое старое правило сначала должно попасть в статус:

UNVERIFIED_LEGACY.

Создай отчёт Legacy Rule Catalog (каталог старых правил):

правило → где использовалось → формула → предполагаемый смысл → источник известен/нет → предлагаемое действие.

Не придумывай нормативный источник там, где его нет.

Создай механизм, позволяющий заменить правило новой версией без изменения старых CalculationRun (запусков расчёта).

Старый расчёт всегда должен воспроизводиться с той версией правил, на которой он выполнялся.

Автоматические тесты обязательны.

# PROMPT 04 — ДЕТЕРМИНИРОВАННОЕ РАСЧЁТНОЕ ЯДРО

Создай Calculation Engine (расчётное ядро), не привязанное к одной инженерной системе.

Расчёт должен быть декларативным и воспроизводимым.

Пример:

исходные факты
→ нормализованные CalculationInput
→ последовательность CalculationStep
→ CalculationResult
→ ExpectedQuantity.

Каждый CalculationStep обязан хранить:

- входные значения;
- формулу или ID правила;
- промежуточный результат;
- единицу;
- источник входов;
- использованные допущения.

Результат должен быть explainable (объяснимым):

пользователь нажимает на итоговые 842 м трубы и видит, из каких составляющих они получены.

Добавь Dependency Graph (граф зависимостей расчёта).

Если пользователь изменил:

«этажность 24 → 25»,

должны пересчитываться только зависимые результаты.

Поддержать три сценария стадии П:

MINIMUM — только подтверждённые объёмы;
EXPECTED — инженерно ожидаемый вариант;
TENDER_SAFE — ожидаемый вариант с разрешёнными тендерными резервами.

TENDER_SAFE не должен автоматически означать +10%.

Резерв формируется только через конкретные зарегистрированные правила.

Все три сценария должны показывать разницу.

Не реализовывай конкретную систему глубоко.

Создай один простой демонстрационный calculator (калькулятор), подтверждающий архитектуру.

Добавь unit tests (модульные тесты).

# PROMPT 05 — СИНТЕЗ СИСТЕМЫ ПОСЛЕ ИНЖЕНЕРНОГО РАСЧЁТА

Реализуй System Synthesizer (синтезатор системы).

Это НЕ BIM-модель и НЕ полноценная РД.

Его задача:

на основании инженерного расчёта, архитектуры и доступной информации построить наиболее вероятную структуру системы, необходимую для оценки количества.

Например ВК:

корпус
→ зона давления
→ стояки
→ этажные ответвления
→ квартирные подключения
→ магистрали
→ ввод.

Например вентиляция:

помещения
→ требуемые расходы
→ группы помещений
→ системы
→ вентустановки
→ магистральные ветви
→ ответвления.

Каждый созданный элемент должен иметь provenance:

OBSERVED — обнаружен в документации;
CALCULATED — необходим по расчёту;
SYNTHESIZED — предложен алгоритмом;
ASSUMED — принят как допущение.

Не пытайся рисовать точную трассу там, где её нельзя обосновать.

Синтез должен уметь выдавать диапазон.

Например:

«ожидается 4–5 стояков К1».

Создай графовую структуру системы.

Количество фитингов и узлов впоследствии должно рассчитываться из топологии графа, а не только коэффициентом на метр.

Не вмешивайся в существующую замороженную MEP-синтетику.

# PROMPT 06 — ПЕРВЫЙ БОЕВОЙ КАЛЬКУЛЯТОР: В1 / Т3 / Т4 / К1

Реализуй первый production-калькулятор (рабочий калькулятор) стадии П.

Системы:

В1
Т3
Т4
К1.

Старый расчётный портал использовать как источник идей и контрольных кейсов, но не копировать слепо.

Цель:

имея неполный проект стадии П и архитектуру, получить инженерно обоснованную оценку необходимой системы и ожидаемых объёмов.

Использовать, если доступны:

- этажность;
- отметки;
- количество квартир;
- типы квартир;
- санузлы;
- кухни;
- общественные помещения;
- коммерция;
- МОП;
- шахты;
- санитарные приборы;
- таблицы водопотребления;
- данные ВК стадии П;
- данные ВОР Заказчика.

Алгоритм должен разделять:

A. расчёт потребности системы;
B. расчёт зон;
C. расчёт количества/структуры стояков;
D. магистральную структуру;
E. типовые этажные подключения;
F. оборудование;
G. трубопроводы;
H. изоляцию;
I. арматуру;
J. фитинги;
K. крепления;
L. проходки/гильзы.

По возможности фитинги выводить из графа.

Legacy-коэффициенты использовать только как fallback (резервный метод).

Для каждого fallback показывать пользователю предупреждение.

Результат:

не «готовый ВОР»,

а Calculation Passport (расчётный паспорт системы) с ожидаемыми количествами.

Добавь golden tests (эталонные тесты) на нескольких типовых зданиях.

Сравни результаты с логикой старого портала и объясни различия.

# PROMPT 07 — РАСЧЁТНЫЙ КОНТУР ОВ

После принятия ВК реализуй архитектурно аналогичный расчёт стадии П для ОВ.

Не пытайся сразу делать полноценную аэродинамику РД.

Нужен тендерный расчёт стадии П.

Источники:

- назначения помещений;
- площади;
- высоты;
- количество людей;
- таблицы воздухообменов;
- кратности;
- технологические задания;
- оборудование;
- архитектурные шахты;
- доступные схемы П.

Расчёт:

помещения
→ требуемый воздухообмен
→ распределение по системам
→ производительность установок
→ ориентировочные сечения
→ магистральная структура
→ воздуховоды
→ фасонные элементы
→ клапаны
→ решётки/диффузоры
→ изоляция
→ крепления.

Если таблица воздухообменов существует — она является сильным источником.

Если отсутствует — расчёт должен использовать зарегистрированные правила и явно показывать основание.

Отдельно не смешивать:

общеобменную вентиляцию;
дымоудаление;
подпор;
вентиляцию паркинга.

Дымоудаление и подпор должны получить самостоятельные калькуляторы либо явно оставаться NOT_IMPLEMENTED (не реализовано), если методика ещё не утверждена.

# PROMPT 08 — ЭОМ: РАСЧЁТ ОТ ТАБЛИЦЫ ПОТРЕБИТЕЛЕЙ

Создай архитектуру расчёта ЭОМ стадии П.

Основной принцип:

не пытаться сначала найти все кабели на плане.

Если существует таблица потребителей:

потребители
→ установленная мощность
→ коэффициенты

# PROMPT 09 — СВЕРКА С ВОР ЗАКАЗЧИКА

Теперь реализуй одну из главных функций продукта.

Quantor НЕ создаёт основной ВОР с нуля.

Он получает ВОР Заказчика и сопоставляет его со своим инженерным расчётом.

Создай VOR Reconciliation Engine (механизм сверки ВОР).

Для каждой позиции ВОР определить:

MATCHED
PARTIAL_MATCH
CALC_HIGHER
CALC_LOWER
NOT_IN_CALC
MISSING_IN_CUSTOMER_VOR
REQUIRES_REVIEW.

Сопоставлять не только буквальные названия.

Использовать:

- систему;
- функциональный тип;
- материал;
- диаметр/сечение;
- характеристики;
- единицу;
- область здания;
- контекст.

LLM может предлагать match (соответствие), но количественное сравнение выполняется кодом.

Показывать:

ВОР Заказчика | расчёт Quantor | отклонение | % | основание Quantor | надёжность | комментарий.

Особо выделять:

1. вероятно недостающие позиции;
2. существенное занижение объёма;
3. существенное завышение;
4. позиции, которые Quantor не может проверить;
5. объёмы, полностью основанные на допущениях.

Не использовать единый глобальный порог отклонения для всех типов материалов.

Поддержать настройку допустимых отклонений по классам позиций.

# PROMPT 10 — ВОПРОСЫ ЗАКАЗЧИКУ И НЕОПРЕДЕЛЁННОСТЬ

Создай Question & Uncertainty Engine (механизм вопросов и неопределённости).

Система должна автоматически понимать:

какие отсутствующие данные существенно влияют на стоимость или количество.

Не нужно задавать Заказчику вопрос на каждый отсутствующий параметр.

Вопрос создаётся, если:

- отсутствие параметра существенно влияет на расчёт;
- документы противоречат друг другу;
- существует несколько технически разных решений;
- ВОР Заказчика противоречит расчёту;
- нормативно значимое решение невозможно определить;
- требуемое оборудование/параметр не определён.

Для вопроса хранить:

- систему;
- тему;
- описание;
- какие документы проверены;
- чего не найдено;
- на какие позиции расчёта влияет;
- оценку влияния;
- текущее временное допущение;
- что изменится после ответа.

Создай отдельную вкладку «Вопросы Заказчику».

Свяжи вопрос с CalculationRun и конкретными ExpectedQuantity.

# PROMPT 11 — ИНТЕРФЕЙС РАСЧЁТНОГО ПОРТАЛА

# PROMPT 12 — ВЕРИФИКАЦИЯ, РЕГРЕССИЯ И МИГРАЦИЯ ЗНАНИЙ СТАРОГО ПОРТАЛА

Проведи инженерно-программную верификацию нового расчётного контура.

Старый портал является baseline reference (контрольным ориентиром), а не абсолютной истиной.

Создай regression dataset (набор регрессионных сценариев).

Минимум:

- низкоэтажный жилой дом;
- высотный жилой корпус;
- корпус с несколькими зонами давления;
- объект с неполными данными;
- объект с противоречащими документами;
- объект с архитектурой, но почти без инженерной стадии П;
- объект с таблицами потребителей;
- объект с ВОР Заказчика.

Для каждого:

входные факты
→ правила
→ промежуточные вычисления
→ ожидаемые результаты
→ сравнение со старым порталом.

Различия разделить:

EXPECTED_IMPROVEMENT
LEGACY_BUG
RULE_CHANGED
INPUT_DIFFERENCE
REGRESSION.

Не пытаться добиться совпадения со старым порталом любой ценой.

Главный критерий — инженерная объяснимость нового результата.

Проверь:

- воспроизводимость;
- единицы измерения;
- округления;
- versioning (версионирование) правил;
- изменение одного факта;
- пересчёт зависимостей;
- ручную корректировку;
- конфликты;
- три сценария MINIMUM / EXPECTED / TENDER_SAFE.

Подготовь итоговый отчёт.

# PROMPT 13 — ПОДГОТОВКА К БУДУЩЕМУ MEP SEMANTIC И РД БЕЗ РЕАЛИЗАЦИИ РД

ВАЖНО: РД сейчас НЕ реализовывать.

Нужно только проверить, что архитектура расчётного портала сможет в будущем принять более точные данные.

Создай интерфейс optional provider (опционального поставщика фактов):

MEP Semantic Provider.

В будущем он сможет предоставлять:

- реальные трассы;
- реальные узлы;

ручного ввода,

Заверши архитектурным отчётом и остановись.
