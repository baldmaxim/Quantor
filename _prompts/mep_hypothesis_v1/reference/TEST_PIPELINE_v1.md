**QUANTOR**

Тестирование гипотезы: стадия П → инженерная РД → ВОР → расценивание

*Пайплайн MVP для одного этажа · версия 1.0 · 15 сентября 2026*

|  |
| --- |
| **Рекомендация:** первый PoC делать на одной узкой системе ВК (горизонтальная разводка типового жилого этажа), а не на всех ВИС сразу. Генерировать нужно не «картинку РД», а структурированный граф сети, из которого детерминированно считаются объёмы и только потом отдельно применяются цены. |

# 1. Что именно проверяем

Гипотеза состоит из трёх независимых утверждений. Их нужно измерять отдельно, иначе высокая точность одного этапа скроет провал другого.

| **Этап** | **Вход** | **Выход** | **Что доказываем** |
| --- | --- | --- | --- |
| 1. Распознавание П | PDF стадии П, один план этажа | MepEvidenceGraph | Quantor понимает исходный лист: масштаб, помещения/шахты, стояки, приборы, подписи, явные трассы. |
| 2. Отрисовка РД | MepEvidenceGraph + обученный prior по РД + правила | MepNetworkGraph | Система восстанавливает связность, трассировку и параметры на уровне, достаточном для ВОР. |
| 3. ВОР и цена | MepNetworkGraph | Нормализованный ВОР + работы/материалы/итого | Объёмы выводятся из графа, а цены подбираются отдельной моделью по историческим ВОР/КП. |

## Ключевая архитектурная мысль

**PDF П → EvidenceGraph → P-MEPGraph → RD Generator → Topology/Rule Validator → RD-MEPGraph → Quantity Engine → BOQ → Pricing Model**

Текущий архив Quantor уже содержит правильные базовые идеи: source-space geometry, EvidenceGraph, полноформатный контекст + крупные detail views, typed POINT/LINE/AREA heads, project-heldout split, raw/source-supported/unresolved и строгий downstream handoff. Для ВИС их нужно переиспользовать, но поверх геометрии добавить сетевую топологию.

# 2. Что переиспользуем из текущей логики, а что добавляем

| **Уже есть в текущем контуре** | **Для ВИС оставить** | **Что добавить** |
| --- | --- | --- |
| PDF/vector/raster ingest, source transforms | Да | MEP page/system classifier и cross-sheet binding |
| Whole-sheet context + high-res views | Да | MEP symbol/text/route supervision |
| POINT / LINE / AREA primitives | Да, как визуальные примитивы | Node/Port/Edge topology и connectivity |
| EvidenceGraph и provenance | Да | MEP-specific evidence kinds |
| Raw / source-supported / unresolved | Обязательно | Observed / rd\_prior\_inferred / rule\_derived / retrieved / human\_confirmed |
| BIM handoff philosophy | Да | MepNetworkGraph до Revit/IFC |
| Project-heldout evaluation | Обязательно | Парный P↔RD split по project\_id |

Не рекомендуется обучать end-to-end image-to-image модель, которая из П рисует «похожий лист РД». Такая модель плохо контролируется, трудно валидируется и не даёт надёжной основы для ВОР. Более устойчивый объект обучения — граф инженерной сети + геометрия трасс.

# 3. Данные для обучения: критически нужны парные П ↔ РД

Для обучения достройки сети единицей данных должен быть не случайный альбом РД, а связанный кейс одного объекта: проект → корпус/секция → этаж → система → лист П → соответствующий лист РД. Непарные РД полезны для pretraining распознавания, но слабо учат переходу П→РД.

| **Что хранить на кейс** | **Зачем** |
| --- | --- |
| Hash, revision, project\_id, floor\_id, system | Исключить смешение ревизий и leakage |
| Aligned P и RD в общей системе координат | Учить реальный delta |
| P EvidenceGraph | Вход модели |
| RD NetworkGraph | Ground truth |
| Delta: added/moved/removed/connected/size changed | Явная задача обучения |
| Architecture/rooms/shafts/risers | Ограничения маршрута |
| Reference ВОР/КП, если есть | Проверка количества и цены |
| Human review status | Не превращать неоднозначность в false-negative |

# 4. Сколько альбомов нужно

Ниже — практические диапазоны для планирования. Это не математическая гарантия: решение о достаточности принимается по learning curve на фиксированном project-heldout наборе. Один “зачтённый альбом” — только если существует корректная пара П↔РД и листы можно связать по этажу/системе.

| **Уровень** | **Парные проекты** | **Парные альбомы П↔РД** | **Полезные floor-pairs** | **Назначение** |
| --- | --- | --- | --- | --- |
| Proof of Concept, 1 subsystem | 20–30 | 40–60 | 150–300 | Понять, есть ли сигнал P→RD; не production. |
| Рабочий пилот, 1 дисциплина | 60–100 | 150–250 | 700–1 500 | Обучить устойчивый narrow model и проверить новые проекты. |
| Стабильный контур, 1 дисциплина | 150–250 | 400–700 | 2 000–5 000 | Разные проектировщики, типологии, ревизии, графика. |
| Мультидисциплинарная модель | 250–400+ | 800–1 500+ | 5 000–10 000+ | ОВ/ВК/ЭОМ/СС с балансом по системам и отдельными head/ontology. |

## Ориентир по сложности систем

| **Система** | **Рабочий пилот** | **Стабильный контур** | **Комментарий** |
| --- | --- | --- | --- |
| ВК | 150–250 paired albums | 300–500+ | Хороший первый кандидат: endpoints/risers/routes/diameters. |
| ОВ (отопление/вентиляция) | 200–350 | 400–700+ | Больше 3D/сечений/оборудования и допустимых вариантов трассы. |
| ЭОМ | 200–350 | 400–700+ | Нужны схемы, панели, цепи, нагрузки; план одного этажа не всегда достаточен. |
| СС/АПС | 150–300 | 300–600+ | Много символов и проектных правил; трасса кабеля часто неоднозначна. |

Важно: 500 листов одного проектировщика хуже, чем 200 хорошо связанных кейсов от 10–20 разных проектных организаций. Для генерации критична вариативность решений, а не только число страниц.

# 5. Данные для модели расценивания

Эта модель должна обучаться не на PDF РД, а на исторических ВОР/КП/оценках. Лучше использовать retrieval + нормализацию + регрессию/ранжирование, а не просить LLM “назвать цену”.

| **Уровень** | **Нормализованные строки ВОР** | **Исторические документы/проекты** | **Цель** |
| --- | --- | --- | --- |
| PoC | 5–10 тыс. | 30–50 | Проверить mapping и цену на узком ВК scope. |
| Пилот | 25–50 тыс. | 150–250 | Устойчивые работы/материалы с датой/регионом/классом. |
| Рабочий контур | 100 тыс.+ | 500+ | Калибровка по времени, рынку, брендам и типам объектов. |

# 6. Трёхэтапный pipeline теста

## Этап 1 — распознаём документацию П

1. Ингест PDF и фиксация hash/revision/page.
2. Определение viewport, этажа, системы и масштаба. Если масштаб не доказан — metric quantities блокируются.
3. Векторный канал: native PDF paths/text/layers. Растровый канал: vision fallback. Каналы не смешивать без provenance.
4. Распознавание архитектурного контекста, шахт/стояков, оборудования/приборов, подписей, диаметров, отметок и явно существующих трасс.
5. Сборка MepEvidenceGraph: только observed + conflicts + unresolved.
6. Фиксация Stage 1 output перед переходом к генерации.

## Этап 2 — строим RD-подобную систему

1. Сначала предсказывается логическая сеть: какие endpoints должны быть соединены и к какой системе относятся.
2. Затем строится геометрический маршрут с учётом стен, шахт, технологических зон, пересечений и штрафов за лишние повороты.
3. Отдельные heads/модули заполняют диаметры/сечения, материал, отметки и аксессуары только по known supervision.
4. Topology/rule validator проверяет dangling endpoints, несовместимые порты, разрывы, смешение систем, запрещённые пересечения.
5. Выход — MepNetworkGraph с provenance каждого узла/ребра/параметра и overlay на исходном плане.

## Этап 3 — ВОР и расценивание

1. Quantity Engine детерминированно выводит длины/количества/площади из NetworkGraph.
2. Формируется нормализованный ВОР со ссылкой каждой строки на source node/edge ids.
3. Pricing Model сопоставляет строку с историческими аналогами и рассчитывает работы/материалы в контексте даты, региона, класса и бренда.
4. Пользователь видит STRICT и ESTIMATE режимы; rule-derived allowances не маскируются под фактический объём.

# 7. Как провести тест на одном этаже без самообмана

1. Выбрать один held-out проект, который полностью исключён из train/validation.
2. Зафиксировать hashes стадии П, reference РД и reference ВОР. Reference РД/ВОР закрыть для inference.
3. Run A: подать “идеальный” oracle Stage 1 в Stage 2. Это проверяет саму способность P→RD.
4. Run B: обычный end-to-end: PDF П → Stage 1 → Stage 2 → ВОР → цена.
5. Run C: retrieval + deterministic routing baseline без обучаемого генератора.
6. До открытия reference зафиксировать outputs и их hashes.
7. После reveal отдельно посчитать recognition, engineering и commercial metrics.
8. Инженер вручную проверяет валидные альтернативные трассы: другой маршрут не всегда ошибка, если он технологически корректен.

# 8. Метрики и гейты

| **Блок** | **PoC gate** | **Цель рабочего пилота** |
| --- | --- | --- |
| Stage 1 — ключевые endpoints/anchors F1 | ≥ 0,90 | ≥ 0,95 |
| Stage 2 — подключение обязательных terminal nodes | ≥ 95% | ≥ 98% |
| Stage 2 — topology edge F1 к reference | ≥ 0,85 | ≥ 0,90 |
| Route length error | ≤ 15% | ≤ 8% |
| Quantity WAPE | ≤ 15% | ≤ 7–10% |
| BOQ item coverage | ≥ 90% | ≥ 95% |
| Pricing total APE на поддержанных строках | ≤ 15% | ≤ 10% |
| Unresolved | Показывать отдельно | Снижать, не скрывать |

Нельзя сводить результат к одной цифре “точность 95%”. Для MEP нужен вектор метрик: распознавание → связность → инженерная валидность → геометрия → количества → стоимость.

# 9. Почему граф сети — правильнее маски

В актуальных исследованиях автоматического MEP BIM также используется графовое представление и интеграция информации между чертежами: это естественно для трубопроводов, воздуховодов и электрических цепей. Векторные технические чертежи тоже эффективно представляются как граф примитивов. Это подтверждает направление Quantor: визуальная модель должна добывать evidence, а инженерная система — жить в структурированной топологии, пригодной для BIM и ВОР.

| **Источник** | **Практический вывод для Quantor** |
| --- | --- |
| Zhao et al., Automation in Construction, 2025, DOI 10.1016/j.autcon.2025.106542 | MEP BIM через multi-drawing graph integration; missing information достраивается по связям между компонентами. |
| Carrara et al., Journal of Computing in Civil Engineering, 2025, VectorGraphNET | Vector PDF primitives + graph attention подходят для семантической сегментации сложных технических чертежей. |
| Urbieta et al., Automation in Construction, 2026, DOI 10.1016/j.autcon.2025.106746 | Electrical circuits: detection symbols + extraction traces + semantic circuit assembly → IFC. |

## Минимальный UX сценарий

1. Загрузить П → выбрать один этаж и ВК.
2. Нажать “Распознать”.
3. Проверить/зафиксировать Stage 1.
4. Нажать “Построить РД”.
5. Проверить topology и overlay.
6. Нажать “Сформировать ВОР”.
7. Нажать “Расценить”.
8. После фиксации результата открыть reference RD/VOR и получить отчёт.

# 11. Как интерпретировать результат

| **Результат** | **Действие** |
| --- | --- |
| Stage 1 слабый, oracle Stage 1 → Stage 2 хороший | Инвестировать в распознавание, генератор не менять. |
| Stage 1 хороший, Stage 2 слабый | Улучшать paired dataset / topology model / routing constraints. |
| Stage 2 визуально отличается, но quantities/validity хорошие | Не оптимизировать под копирование конкретной РД; считать valid alternative. |
| NetworkGraph хороший, ВОР слабый | Ошибка в quantity rules/taxonomy, а не в vision. |
| ВОР хороший, цена слабая | Увеличивать/чистить историческую ценовую базу. |
| Baseline почти равен ML | Не усложнять модель раньше времени; использовать retrieval + solver как продуктовый baseline. |
