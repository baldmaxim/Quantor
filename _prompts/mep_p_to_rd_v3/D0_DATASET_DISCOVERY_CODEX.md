## 1. Цель

Из полученных архивов с альбомами стадий П и РД получить:

1. опись всех архивов, файлов и страниц с хешами;
2. классификацию документов: проект, стадия, дисциплина, система, тип листа, этаж — с доказательствами;
3. группы проектов и кандидаты пар **П ↔ РД одного проекта** для контура ВК (типовой жилой этаж);
4. короткий список листов-кандидатов для пилота PROMPT 02;
5. отчёт со статистикой и вопросами владельцу.

## 2. Входы и где лежат данные

- `MEP_ARCHIVE_ROOT` — каталог с исходными архивами, задаёт владелец. **Только чтение.** Исходные архивы не

## 4. Шаги

### 4.1. Безопасная опись архивов (без распаковки)

- Форматы: `.zip` — `zipfile`; `.7z`, `.rar` — системный `7z l -slt` (как в `planswift_gt/archive.py`).
  Нет 7-Zip — архив в `HOLD` с причиной, не падать.
- Для каждого члена: путь, размер, сжатый размер, CRC, признак шифрования.
- Отказ (`HOLD`, причина в описи): абсолютные пути, `..`, символьные ссылки, шифрование, коэффициент сжатия
  выше предела, суммарный размер выше предела, вложенность архивов глубже 2.
- Имена в cp866/cp1251 — корректно декодировать и записать исходные байты имени.
- SHA-256 каждого архива.

### 4.2. Распаковка в датасет

- Разрешённые архивы — в `$QUANTOR_DATASET_ROOT/mep/raw/<sha256[:12] архива>/` с сохранением структуры.
- SHA-256 каждого файла; дубликаты по хешу — одна копия, ссылки из всех мест, где файл встречался.
- Вложенные архивы — рекурсивно, с теми же проверками.

### 4.3. Опись файлов

`files.jsonl`, запись на файл: `file_id` (sha256), все исходные пути, расширение, размер, тип:

| Тип                   | Что делать сейчас                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------- |
| `.pdf`                | опись страниц (4.4)                                                                          |
| `.dwg`                | только заголовок: версия по первым 6 байтам (`AC1015`, `AC1018`, `AC1021`, `AC1024`, `AC1027`, `AC1032`…), размер, хеш. **Не конвертировать** |
| `.dxf`                | только заголовок `$ACADVER` и размер; разбор слоёв — после решения владельца                |
| `.xlsx`/`.xls`/`.csv` | пометить `boq_or_spec_candidate` по имени и листам книги; содержимое не разбирать           |
| `.rvt/.nwc/.nwd/.ifc` | только опись: BIM в Quantor хранится, но не разбирается                                     |
| прочее                | опись и тип                                                                                  |

### 4.4. Опись страниц PDF

`pages.jsonl`, запись на страницу, через `pypdf`:

- номер страницы, размер MediaBox/CropBox в мм, поворот, формат (A0–A4, нестандартный);
- есть ли текстовый слой (число символов), доля страницы под одним растровым изображением — признак скана
  (`vector` / `raster_scan` / `mixed`);
- текст штампа — только из текстового слоя, **без OCR**. Нет текстового слоя — поля штампа `null`.

### 4.5. Классификация — только правилами, с доказательствами

Поля документа и страницы: `project_key`, `object_code` (шифр), `stage` (`P` / `RD` / `unknown`),
`discipline` (`VK` / `OV` / …/ `unknown`), `systems` (В1, В2, Т3, Т4, К1, К2, К3…), `sheet_kind`
(`floor_plan` / `scheme` / `axonometry` / `specification` / `general_data` / `detail` / `unknown`),
`floor` (номер, отметка, «типовой»), `building` / `section`.

- Источники по приоритету: текст штампа → заголовок листа в текстовом слое → имя файла → путь каталога.
- Для каждого значения — `evidence[]`: источник, найденная строка, правило (id регулярного выражения).
- Противоречие источников или отсутствие данных → `unknown` + причина. **Не угадывать.**
- Регулярные выражения держать в одном версионированном файле правил; каждое правило — с примером и тестом
  на синтетической строке.

### 4.6. Проекты и пары П ↔ РД

- `projects.json`: `project_id` = стабильный хеш нормализованного `object_code` (или набора признаков, если
  шифра нет); реальные названия — только в датасете.
- Пары строятся **только внутри одного проекта**: дисциплина + система + корпус/секция + этаж/тип листа.
- `pairs.jsonl`: ссылки на страницы П и РД, совпавшие признаки, `pair_status`:
  - `AUTO_OK` — совпали шифр, дисциплина, система и этаж;
  - `REVIEW` — совпало не всё, перечислить что;
  - `HOLD` — неоднозначно или несколько кандидатов.
- Не совмещать листы геометрически и не строить alignment — это PROMPT 06.
- Не разбивать на train/val/test — только группировка по `project_id` (П и РД одного проекта всегда вместе).

### 4.7. Кандидаты для пилота PROMPT 02

`pilot_candidates.json`: 5–10 планов этажа стадии П, дисциплина ВК, желательно с парой РД, отсортированных по:
векторный PDF с текстовым слоем → есть пара `AUTO_OK` → типовой жилой этаж → читаемый штамп. У каждого —
причины выбора и чего не хватает. Выбор делает владелец.

### 4.8. Отчёт и манифест

- `$QUANTOR_DATASET_ROOT/mep/inventory/report.md` — полный отчёт с названиями (вне git).
- `$QUANTOR_DATASET_ROOT/mep/inventory/manifest.json` — SHA-256 всех выходных файлов, версия инструмента и
  правил, git-коммит, отпечаток исходного каталога, время.
- `docs/mep/02a-dataset-discovery.md` в git — **только агрегаты без названий объектов, адресов и шифров**:
  - архивы: всего / распаковано / HOLD по причинам;
  - файлы по типам; PDF-страницы: vector / raster_scan / mixed; DWG по версиям;
  - проекты; альбомы П и РД по дисциплинам; доля `unknown` по каждому полю;
  - пары П↔РД ВК: AUTO_OK / REVIEW / HOLD; оценка числа пригодных пар «этаж-система»;
  - сравнение с целями PoC: 20–30 проектов, 40–60 парных комплектов, 150–300 пар «этаж-система»;
  - файлы-кандидаты ВОР и спецификаций — только число;
  - вопросы владельцу (раздел 6).
