# Quantor — пакет промтов Opus 5 для быстрого запуска рабочего пилота

Цель пакета — не продолжать бесконечную инфраструктурную разработку, а довести текущий Quantor до состояния, в котором инженер уже может работать с реальным PDF и проходить сквозной MEP-пайплайн вручную, пока AI-модели (модели ИИ) ещё не подключены.

## Исходная точка

По актуальному архиву `Quantor-main(4).zip` уже есть:

- загрузка проектов/документов и хранение PDF;
- `PageGeometry` и геометрия обычного PDF;
- PDF-viewer (просмотрщик PDF) на pdf.js;
- ручная калибровка;
- ручные Count / Line / Polyline / Polygon (счёт / линия / ломаная / полигон);
- `takeoff.manual` — принятый пилот Stage 2A;
- MEP contracts v0.3 (контракты MEP v0.3);
- Quantity Engine 0.3.1 (движок расчёта количеств 0.3.1);
- MOCK-страница `/experiments/mep` и сценарии A/B/C/D;
- решение Р-MEP-16: синтетическая фаза заморожена.

Критический продуктовый разрыв: обычный PDF получает `geometry_status=ready`, но карточка проекта всё ещё открывает workspace (рабочую область) только по `processing_status=ready`, то есть фактически требует распознанный пакет. Это нужно убрать первым.

## Целевой промежуточный продукт

```text
Реальный PDF стадии П
→ ручная разметка исходных MEP-сущностей
→ MepEvidenceGraph (HUMAN_GT / HYBRID_REVIEWED)
→ ручная отрисовка инженерной сети
→ MepNetworkGraph (HUMAN_CONFIRMED)
→ существующий Quantity Engine 0.3.1
→ Physical BOQ / Calculated Takeoff (физический ВОР / рассчитанный обмер)
→ CSV/XLSX экспорт
```

AI-модели (модели ИИ) на этом этапе не требуются. В будущем они заменят ручные шаги, не ломая контракты и Quantity Engine.

## Порядок запуска

1. `00_BASELINE_AND_DAMAGE_CONTROL.md`
2. `01_RAW_PDF_WORKSPACE.md`
3. `02_MANUAL_TAKEOFF_READY_FOR_WORK.md`
4. `03_REAL_MEP_MANUAL_PILOT_FOUNDATION.md`
5. `04_HUMAN_GT_EVIDENCE_EDITOR.md`
6. `05_MANUAL_NETWORK_EDITOR.md`
7. `06_REAL_BOQ_AND_EXPORT.md`
8. `07_LIVE_E2E_ACCEPTANCE_AND_BUGFIX.md`
9. `08_PILOT_RELEASE_FREEZE.md`

Если цель — начать пользоваться порталом максимально быстро, уже после промтов **01–02** должен появиться полезный режим ручного обмера реальных PDF. Промты **03–08** доводят именно ручной MEP-конвейер.

## Жёсткие ограничения всего пакета

- Не менять base recognition (базовое распознавание).
- Не запускать PROMPT 02/03/04 из `mep_p_to_rd_v3` и не начинать обучение.
- Не менять замороженные MEP-сценарии A/B/C/D и их эталоны без отдельного решения владельца.
- Не строить OCR, новый общий PDF-recognition pipeline (конвейер распознавания PDF), PageRasterProvider или модели MEP.
- Не делать pricing (расценивание), Customer VOR mapping (сопоставление ВОР Заказчика), Revit/IFC export (экспорт Revit/IFC), fitting rules (правила фитингов).
- Не переписывать viewer/takeoff с нуля. Переиспользовать существующие DrawingViewport, ToolController, Measurement, ScaleCalibration, API-patterns и MEP contracts.
- Не делать «идеальную платформу разметки». Нужен минимальный рабочий пилот.
- Существующий `/experiments/mep` остаётся замороженным MOCK-стендом. Реальный ручной MEP-пилот делать рядом, а не превращать MOCK в production.
- Любой новый feature flag (флаг возможности) — `default=False`, workspace-scoped (на пространство), deny-by-default (запрет по умолчанию).
- Не коммитить без отдельной команды владельца.
- Не удалять/перезаписывать незнакомые незакоммиченные изменения.

## Формат работы с Opus 5

Каждый промт рассчитан на отдельный проход. После каждого промта агент обязан:

1. показать, что изменено;
2. показать тесты и фактические команды;
3. перечислить оставшиеся риски/блокеры;
4. создать review ZIP (архив ревью) в `review/`;
5. остановиться и не переходить к следующему промту.

Имена review ZIP:

`QUANTOR_FASTSTART_P00_REVIEW.zip`, `...P01...`, и т. д.

В review ZIP не включать `.git`, `node_modules`, `.venv`, клиентские PDF/DWG/DXF, dataset root, секреты и большие generated caches (сгенерированные кэши).

Отчёты писать по-русски. Английские термины в пользовательской части отчёта сопровождать русским пояснением; имена кода, путей, API и идентификаторы не переводить.
