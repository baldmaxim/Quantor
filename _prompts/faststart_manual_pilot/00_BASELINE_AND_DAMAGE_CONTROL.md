# PROMPT 00 — Baseline & Damage Control (базовая проверка и защита текущего состояния)

**Модель:** Opus 5  
**Режим мышления:** высокий  
**Цель:** за 1 проход понять фактическую готовность репозитория, убрать только блокирующие регрессии и получить безопасную точку для дальнейшей работы.

Работай в текущем репозитории Quantor. Не начинай новую архитектуру.

## 0. Сначала прочитай

Обязательно прочитай:

- `CLAUDE.md`;
- `docs/mep/MEP_EXPERIMENT_STATE.md`;
- `docs/mep/05-contracts-v0.3.md`;
- `docs/mep/09-quantity-engine.md`;
- `docs/mep/11-experiment-page-mock.md`;
- ADR-0027, ADR-0028;
- корневой `package.json`;
- актуальный `git status`, `git diff`, текущий branch/HEAD.

Решение Р-MEP-16 считать обязательным: контракты v0.3, Quantity Engine 0.3.1, `/experiments/mep` MOCK и сценарии A/B/C/D заморожены.

## 1. Не потеряй текущую работу

До любого изменения:

- зафиксируй в отчёте все modified/untracked files;
- не удаляй и не откатывай незнакомые изменения;
- не используй destructive git commands (разрушительные команды git);
- если рабочее дерево грязное, продолжай аккуратно поверх него и отделяй свои изменения в отчёте.

## 2. Полная проверка baseline (базовой версии)

Запусти по возможности:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm lint:licenses
pnpm api-client:check
```

Если локальная инфраструктура доступна безопасно:

```bash
pnpm db:migrate
```

Не поднимай/не очищай production-like БД (рабочую БД), если не доказано, что это локальная dev/test БД.

`pnpm test:e2e` запусти только если существующая среда и фикстуры позволяют это без внешних клиентских данных. Если нет — укажи `ENV_BLOCKED`, а не имитируй PASS.

## 3. Классифицируй все падения

Для каждого падения только один статус:

- `REGRESSION` — код реально сломан;
- `ENV_BLOCKED` — нет сервиса/БД/браузера/переменной окружения;
- `STALE_EXPECTATION` — тест/документация не соответствует уже принятому продукту;
- `OUT_OF_SCOPE` — не влияет на ручной пилот.

Исправляй в этом промте только `REGRESSION` и очевидные `STALE_EXPECTATION`, если исправление локально и не меняет архитектуру.

## 4. Проверь конкретные продуктовые узкие места

Подтверди кодом, а не предположением:

1. обычный PDF получает `geometry_status=ready` после `pdf_geometry_extract`;
2. у обычного PDF `processing_status` может оставаться `unprocessed` — это нормально;
3. `apps/web/src/app/(portal)/projects/[projectId]/page.tsx` сейчас ищет openable revision (открываемую ревизию) по `processing_status === 'ready'`;
4. `takeoff.manual` реально пилотный и default OFF;
5. workspace умеет рендерить PDF независимо от `Region`, если sheets/content доступны;
6. MEP MOCK API не используется как хранилище реального проекта;
7. обычный `Measurement` имеет `measurement_metadata`, но публичные схемы могут его не использовать — зафиксируй это как потенциальную точку reuse (переиспользования), не меняй пока.

## 5. Создай один readiness-документ

Создай/обнови:

`docs/pilot/MANUAL_PILOT_READINESS.md`

Кратко зафиксируй:

- baseline commit/dirty state;
- какие команды PASS/FAIL/ENV_BLOCKED;
- что уже готово для ручной работы;
- что блокирует raw PDF (сырой PDF) и MEP manual pilot (ручной MEP-пилот);
- порядок P01–P08 из этого пакета.

Не переписывай исторические ADR.

## 6. Review ZIP

Создай:

`review/QUANTOR_FASTSTART_P00_REVIEW.zip`

Включи:

- readiness-документ;
- список изменённых файлов;
- компактный test report;
- patch/diff только своих изменений, если это возможно без утечки клиентских данных.

## Гейт PROMPT 00

PASS только если:

- состояние репозитория понятно;
- нет известных baseline-регрессий, способных ломать P01;
- текущие MEP freeze-правила не нарушены;
- review ZIP создан.

После отчёта остановись. Не выполняй PROMPT 01.
