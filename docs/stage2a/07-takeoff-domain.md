# Промт 07 — домен ручного обмера

Дата: 2026-09-09. Решение — [ADR-0019](../adr/0019-takeoff-item-i-measurement.md).

## 1. Что появилось

Первая пользовательская сущность подсчёта. До сих пор портал хранил только свидетельства
распознавалки; теперь есть место, куда человек кладёт **свои** обмеры.

```text
TakeoffItem   рабочая строка проекта: «Двери», «Перегородка ПГ-1»
  └── Measurement × N   геометрия на конкретном листе
```

| Часть                            | Где                                                                           |
| -------------------------------- | ----------------------------------------------------------------------------- |
| Единица величины и границы точек | `app/domain.py`: `QuantityUnit`, `UNIT_BY_GEOMETRY`, `MIN_POINTS_BY_GEOMETRY` |
| Модели                           | `app/models/takeoff.py`                                                       |
| Миграция                         | `alembic/versions/20260909_0010_takeoff_domain.py`                            |
| Инварианты и операции            | `app/services/takeoff.py`                                                     |
| Тесты                            | `apps/api/tests/test_takeoff_domain.py`                                       |

API здесь нет намеренно: это промт 08. UI — промты 09–11.

## 2. Чего не сделано специально

**Иерархии строк нет.** Соблазн на этом шаге один и большой: сделать сразу «правильное»
дерево сметных позиций с кодами и разделами. Но никто ещё не измерил ни одной стены, и любая
иерархия окажется придуманной — а переделывать её придётся уже с данными. Поле `parent_id`
«на всякий случай» немедленно обрастает кодом обхода, который потом никто не решается удалить.

Тест закрепляет отсутствие: `test_takeoff_item_has_no_hierarchy`.

**PostGIS не используется.** Расширение в базе есть, но пространственных запросов на Stage 2A
нет ни одного — попадание курсора считается на клиенте. Тип ради типа усложнил бы миграции
и не дал бы ничего.

## 3. Разделение обязанностей: база и сервис

| Инвариант                                | Кто держит                    |
| ---------------------------------------- | ----------------------------- |
| число точек соответствует типу           | **база** (CHECK) и сервис     |
| единица показа соответствует типу        | **база** (CHECK)              |
| точки конечны и лежат в [0, 1]           | сервис                        |
| проект строки совпадает с проектом листа | сервис                        |
| калибровка относится к тому же листу     | сервис                        |
| архивная строка не принимает измерений   | сервис                        |
| источник не подделывается                | сервис (параметра просто нет) |
| калибровка не исчезает из-под измерения  | **база** (внешний ключ)       |

Проверка в приложении ловит ошибку пользователя, проверка в базе — ошибку программиста.
Два теста бьют по базе **сырым SQL** в обход сервиса: многоугольник из двух точек и площадь
с единицей «метры». Иначе неизвестно, доехал ли CHECK до схемы или остался намерением в модели.

### Почему совпадение проектов не в базе

Композитный ключ, как у заданий, потребовал бы денормализовать проект и на лист, и на
измерение — широкое изменение схемы. Путь API проверяет это дважды: и лист, и строка
достаются запросами, уже ограниченными рабочим пространством. Инвариант закреплён тестом,
включая попытку связать строку и лист из **разных пространств**.

Решение записано в ADR как осознанное, а не пропущенное.

## 4. Решения, которые стоит назвать

**Тип геометрии — у строки, а не у измерения.** Иначе в «Дверях» оказались бы и точки, и
площади, а сложить их было бы нечем.

**Единица выводится из типа**, а не принимается снаружи. Свободное поле однажды разошлось бы
с типом и показало площадь в метрах — это закреплено CHECK в базе.

**Многоугольник не замыкается** повторением первой точки: замыкание — свойство типа, а не
данных, и дублирующая точка ломала бы счёт вершин. Порядок вершин сохраняется как есть:
это то, что пользователь видит и может отредактировать.

**Ссылка на калибровку явная.** Измерение хранит ту калибровку, по которой посчитано, а не
«действующую на сейчас». Отсюда свойство, ради которого всё и делается: смена масштаба листа
не меняет уже посчитанное. Проверено тестом.

**Архивация и мягкое удаление вместо `DELETE`.** Строка и измерение — основание чисел,
которые могли уйти заказчику. Жёсткое удаление уносит возможность объяснить, почему вчера
в отчёте было другое число.

**Итог требует явной области.** Сложить измерения двух ревизий одного документа значило бы
посчитать одни и те же двери дважды: вторая ревизия — тот же чертёж после правок, а не
соседнее здание. `count_for_item` без `revision_id` или `sheet_id` отказывает.

**Версия для конкурентного редактирования.** Двое, тянущие одну вершину, получают
`MEASUREMENT_VERSION_CONFLICT`, а не молчаливую перезапись.

**Предел 10 000 вершин.** Не про производительность: многоугольник из ста тысяч точек — это
способ положить сервер одним запросом.

## 5. Что поймал линтер

`ruff` пометил `color_token` как возможный пароль (`S105`/`S107` реагируют на слово «token»
в имени). Подавлять правило нельзя по правилам проекта — переименовал в `color_key`.
Смысл не потерялся: это ключ палитры темы, а не значение цвета.
