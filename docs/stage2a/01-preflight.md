### Два дефекта, которые нашёл только живой прогон

Оба — в коде, написанном для этого промта, и оба невидимы без базы:

1. **`downgrade` не работал.** `op.drop_constraint("ck_jobs_workspace_scope", ...)` без
   `op.f()` второй раз проходил через соглашение об именовании: шаблон
   `ck_%(table_name)s_%(constraint_name)s` превращал имя в `ck_jobs_ck_jobs_workspace_scope`,
   и откат падал на несуществующем констрейнте. Исправлено обёрткой `op.f()` — ровно так,
   как это уже сделано в 0006.
2. **Тест бэкфилла падал на вставке.** `INSERT INTO workspaces` перечислял колонку
   `is_active`, которой у модели нет: состояние пространства хранится в `status`
   (`active` / `suspended`).

Оба подтверждают правило, записанное ещё в приёмке Stage 1.5: **код, работающий с базой,
проверяется только базой.** Ни линтер, ни типизация, ни прогон без БД их поймать не могли:
первый — потому что имя собирается в рантайме, второй — потому что SQL здесь строка.

Ручная проверка закрытой дыры (остаётся к сценарию live-приёмки): создать общесистемное
задание, затем `GET /api/v1/jobs/{id}` под `engineer` — ожидается 404;
`GET /api/v1/admin/jobs/{id}` под `platform_admin` — 200 со `scope: "system"` и пустым
`workspace_id`.

## 2. Явная область видимости задания

### Что было

`Job.project_id IS NULL` означало «видно любому рабочему пространству». Дыра нашлась в
**трёх** местах, а не в одном, как указывал reference:

| Место                                               | Достижимость до правки                                            |
| --------------------------------------------------- | ----------------------------------------------------------------- |
| `services/jobs.py:117` — публичный `GET /jobs/{id}` | достижимо: право `jobs.read` есть уже у роли `reviewer`           |
| `api/v1/admin/jobs.py:190` — `_job_or_404`          | недостижимо, но оживало бы при выдаче `system.admin` кому-то ещё  |
| `services/jobs.py:99` — `find_by_idempotency_key`   | ключ содержит `project_id` — соглашение вызывающего, не инвариант |

Утечки данных не произошло: общесистемных заданий никто не создавал. Но Stage 2A вводит
новые типы заданий, и чинить надо было до них.

### Как стало

Область кодируется парой колонок. Отдельного дискриминатора нет намеренно: он был бы
производным от той же пары и однажды разошёлся бы с ней.

| `workspace_id` | `project_id` | Смысл                           |
| -------------- | ------------ | ------------------------------- |
| NOT NULL       | NULL         | задание пространства            |
| NOT NULL       | NOT NULL     | задание проекта                 |
| NULL           | NULL         | общесистемное                   |
| NULL           | NOT NULL     | непредставимо — запрещено CHECK |

`workspace_id` остаётся nullable: NULL здесь не «неизвестно», а «вне арендаторов».
Инвариант держит `ck_jobs_workspace_scope`, а не nullability.

Совпадение арендатора задания с арендатором его проекта держит **составной внешний ключ**
на `projects (id, workspace_id)`, заменивший одноколоночный. Проверка в сервисе оставлена
тоже, но у неё другая роль: она даёт понятную ошибку. Одна проверка в сервисе не годилась
бы — запись мимо API (та же миграция) её не заметит.

Составной ключ работает в режиме MATCH SIMPLE: при пустом `project_id` он не проверяется,
что и нужно заданиям пространства. Промежуток закрыт CHECK: как только `project_id` задан,
`workspace_id` обязан быть.

### Миграция

`0007_job_workspace_scope`, `down_revision = 0006_job_worker_lease`. Порядок upgrade
обязателен: nullable-колонка → backfill из `projects` → CHECK и ключи → индекс. До backfill
CHECK упал бы на живых данных.

Строки с пустым `project_id` становятся общесистемными, и их количество печатается. Когда
принадлежность строки неизвестна, безопасен только отказ в доступе — не выдача его наугад.

Цепочка ревизий линейна, голова одна: `0007_job_workspace_scope`.

### Что не менялось

`CLAIM_SQL`, `claim`, `heartbeat`, `release_expired` — ни строки. Очередь одна на установку,
и воркер намеренно слеп к арендаторам: область видимости — граница чтения через API, а не
признак исполнимости. Это закреплено тестом
`test_claim_takes_jobs_of_every_scope`.

### Контракт

Публичный `JobRead` **не расширялся**. После правки он физически не может вернуть чужое или
общесистемное задание, поэтому поля `workspace_id`/`scope` не несли бы в нём информации.
Контракт Stage 1 остался байт-в-байт.

`AdminJobRead` получил `workspace_id` и `scope`, `GET /admin/jobs` — фильтр `?scope=`.
Изменение аддитивное: 46 добавленных строк в `openapi.json`, ни одного удалённого поля.
Умолчание для администратора платформы — все области, включая системную: это эксплуатационный
список, и прятать в нём обслуживание установки значило бы прятать её поломки.

## 3. Администратор платформы без членства

### Воспроизведение

Кейс воспроизведён чтением кода до написания тестов, как требует промт.
`get_auth_context` (`auth/resolver.py:65`) всегда вызывает `_resolve_workspace`, а тот при
пустом списке членств и отсутствии заголовка бросал `WORKSPACE_FORBIDDEN` — **до** проверки
прав. Следствие: администратор платформы без членства не мог вызвать ни одну системную
операцию. Ровно та ситуация, что возникает при первичной настройке установки: администратор
назначен переменной окружения, членств у него ещё нет.

Хорошая новость: молчаливой подстановки «первого попавшегося» пространства не было и до
правки — код честно отказывал. Проблема была обратной: системный администратор оказывался
заперт.

### Решение

`AuthContext.workspace_id` стал `uuid.UUID | None`. Пусто — контекста арендатора нет вовсе.
Появилось свойство `tenant`, которое возвращает пространство или отказывает понятной ошибкой:

```python
@property
def tenant(self) -> uuid.UUID:
    if self.workspace_id is None:
        raise DomainError(ErrorCode.WORKSPACE_FORBIDDEN, "…укажите X-Workspace-Id")
    return self.workspace_id
```

Отдельное свойство, а не проверка на каждом маршруте: забытая проверка выглядела бы как
работающий код, а здесь пропуск ловится типом. Смена типа на опциональный заставила mypy
перечислить все 26 мест, где пространство обязательно, — рефактор получился полным по
построению, а не по внимательности.

`_resolve_workspace` возвращает пустой контекст **только** администратору платформы.
Обычный пользователь без членства по-прежнему получает отказ.

Два места потребовали отдельного внимания, потому что молча меняли смысл:

- запись переопределения настройки или флага с областью «пространство» при пустом контексте
  получила бы `workspace_id = NULL` и стала бы **системной**. Переведено на `tenant` —
  явный отказ вместо тихой подмены области;
- счётчик связанных проектов TenderHUB сравнивался с пустым `workspace_id` и выдал бы ноль,
  то есть соврал бы «связей нет». Для контекста без арендатора считается по всей установке.

## 4. ADR-0004 и Canvas2D

Выпущен [ADR-0015](../adr/0015-sloi-nalozheniya-na-canvas2d.md): слои наложения на Stage 1
и 2A — Canvas2D; WebGL рассматривается только после benchmark, и в порядке «измерить →

запись. В его заголовок добавлена ссылка вперёд, чтобы читатель не начал с WebGL, от которого
уже отказались.

### Про `create_all` и миграции

Тесты поднимают схему через `Base.metadata.create_all`, поэтому расхождение модели и
миграции они не заметили бы в принципе. Работа «Миграции» в CI закрывает это частично:
`alembic check` не сравнивает CHECK-констрейнты, `ondelete`/`onupdate`, предикаты частичных
индексов и `server_default` — то есть ровно то, на чём держится инвариант области видимости.

Добавлен `tests/test_schema_matches_migrations.py`: поднимает отдельную базу **миграциями**
и сравнивает её с моделями по системному каталогу PostgreSQL (`pg_constraint`, `pg_indexes`,
`information_schema.columns`). Alembic запускается подпроцессом: `env.py` берёт DSN из
закэшированных настроек, и подменять кэш ради теста значило бы чинить тест правкой того,
что он проверяет.
