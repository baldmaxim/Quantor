## 2. Численная граница

**Хранение десятичное, расчёт — `float64`, граница проходит при чтении из базы.**

```text
Numeric(12,4) → Decimal → [PageGeometryValue.from_decimal] → float → геометрия
```

`float64` выбран не как компромисс: это единственный числовой тип, который Python и
TypeScript разделяют **побитово**. Оба IEEE-754 binary64, и стандарт задаёт сложение,
умножение и квадратный корень как корректно округляемые. Одинаковая последовательность
операций даёт одинаковый результат до последнего бита.

Отсюда следствие важнее самого типа: **порядок операций — часть контракта**. Сумма длин
звеньев накапливается слева направо; площадь обходит вершины по возрастанию индекса,
замыкание на нулевую — последним слагаемым. Переставить их «для красоты» нельзя.

Считать в `Decimal` целиком отвергнуто: корень требует выбранной разрядности, в браузере
нужна библиотека, и совпадение двух реализаций пришлось бы обеспечивать вручную вместо
того, чтобы получить его от стандарта.

## 3. Общие векторы

Один файл `tests/fixtures/coordinate_vectors.json` читают **и** тесты Python, **и** тесты
просмотрщика. Сравнение точное — `assert ==` и `toBe`, без `pytest.approx` и `toBeCloseTo`.

Допуск здесь был бы не осторожностью, а слепым пятном: он скрыл бы ровно то расхождение
реализаций, ради поимки которого векторы и заведены.

Ожидаемые значения подобраны **аналитически**, а не сняты с реализации:

| Случай                                    | Почему значение известно заранее       |
| ----------------------------------------- | -------------------------------------- |
| страница 1000×1000, катеты 300 и 400      | треугольник 3-4-5 даёт ровно 500       |
| страница 3000×4000, диагональ угол в угол | те же 3-4-5, масштаб 1000 → ровно 5000 |
| прямоугольник в половину листа            | произведение сторон                    |
| весь лист целиком                         | площадь страницы                       |
| обход против часовой стрелки              | та же площадь: знак задаёт направление |

Тест, сверяющийся с собственным выводом, доказывает воспроизводимость, но не правильность.
Это различие здесь принципиально: ошибка в реализации была бы записана в вектор и стала бы
эталоном.

### Вектор поймал ошибку сразу

Первый прогон дал расхождение в случае «диагональ на A1»: я вписал в файл значение,
посчитанное вручную, и оно оказалось неверным — реализация была права. Случай заменён на
аналитически точный (3000×4000 → 5000), где ошибиться в ожидании невозможно.

## 4. Совпадение сред подтверждено измерением

Крайний случай оказался лучшим доказательством, чем рассуждение.

`hypot(3e200, 4e200)`:

|                                  | Результат                 |
| -------------------------------- | ------------------------- |
| Python `math.hypot`              | `4.9999999999999995e+200` |
| JavaScript `Math.hypot`          | `4.9999999999999995e+200` |
| Наивный `sqrt(x² + y²)` в Python | `OverflowError`           |

Значение **не** равно `5e200`: ни один из аргументов точно не представим в double. Обе
среды дали одну и ту же неточность до последнего бита — именно это и утверждает ADR-0017.
Заодно видно, зачем `hypot`: наивная формула здесь просто переполняется.

## 5. Решения, принятые в ядре

**Угол листа — законная точка.** Границы 0 и 1 допустимы. Отвергать их значило бы
запретить обмер по краю чертежа, что на планах происходит постоянно.

**Обратное преобразование не зажимает результат в [0, 1].** Точка за пределами страницы —
ошибка вызывающего. Молча подвинуть её к краю значило бы получить правдоподобную геометрию
вместо явного отказа, а правдоподобная ошибка дороже заметной.

**Самопересечения не проверяются и не запрещаются.** Формула шнурков даёт на них разность
площадей, а не отказ. Политика для таких фигур — вопрос правил подсчёта, а не
преобразования координат, и решается в промте 12.

**Поворот не применяется.** Он уже в размерах страницы (ADR-0016), а нормализованные
координаты относятся к уже повёрнутой странице (ADR-0008). Старые `rotateUnitPoint` и
`unrotateUnitPoint` в `coordinates.ts` **не тронуты**: они ждут формат пакета v2 и к
измерениям отношения не имеют.

**Ловушка прямоугольной страницы закреплена тестом** в обеих средах: на странице 3000×4000
шаг 0,1 по X даёт 300 pt, а по Y — 400 pt. Это и есть причина, по которой старый
`units_per_normalized` был математически неверен.

## 6. Что всплыло в TypeScript

У портала включён `noUncheckedIndexedAccess`: индексация массива даёт `T | undefined`.
Первая версия обхода по индексу не прошла типизацию.

Заглушать это утверждением типа (`!` или `as`) нельзя — правила проекта запрещают, и
правильно: утверждение спрятало бы реальный случай. Обход переписан:

- длина — через переменную `previous`, порядок слева направо сохранён;
- площадь — пары вершин строятся заранее списком, замыкание добавляется последним. Так
  порядок слагаемых виден глазами и дословно совпадает с серверным.

Второе даже читается лучше исходного: порядок суммирования перестал быть неявным следствием
арифметики индексов.
