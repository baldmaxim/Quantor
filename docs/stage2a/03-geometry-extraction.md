# Промт 03 — реализация извлечения геометрии PDF

Дата: 2026-09-09. Решение и схема — [ADR-0016](../adr/0016-kanonicheskaya-geometriya-stranicy-pdf.md)
и [отчёт промта 02](02-canonical-geometry-design.md).

## 1. Что заработало

Сервер впервые знает размер страницы документа. До этого он знал только пиксели растра
распознавалки, а у обычной загрузки PDF не было даже листов.

| Часть                                  | Где                                                        |
| -------------------------------------- | ---------------------------------------------------------- |
| Провайдер геометрии (протокол + pypdf) | `app/services/geometry/provider.py`                        |
| Извлечение и запись                    | `app/services/geometry/extract.py`                         |
| Постановка задания                     | `app/services/geometry/schedule.py`                        |
| Тело задания                           | `app/services/job_runner.py::execute_pdf_geometry_extract` |
| Реестр обработчиков                    | `app/worker/registry.py`                                   |
| Чтение геометрии                       | `GET /api/v1/sheets/{sheet_id}/geometry`                   |
| Состояние в ревизии                    | `DocumentRevisionRead.geometry_status`                     |

Зависимость: **pypdf 6.18.0**, закреплена точно, лицензия BSD-3.

## 2. Замер на эталонном пакете

Прогон на настоящем `01-03-00-01-12_ПД-00260560-АР` — том же, на котором закрывался Stage 1.5.
Числа измерены, а не оценены.

| Показатель                      | Значение                                |
| ------------------------------- | --------------------------------------- |
| Размер PDF                      | 47,6 МБ                                 |
| Страниц                         | 77                                      |
| Время разбора                   | **0,40 с**                              |
| Повороты                        | 30 страниц по 0°, **47 страниц по 90°** |
| Различных отображаемых размеров | 8                                       |

Наиболее частые размеры:

| Отображаемый размер | Листов | Формат       |
| ------------------- | ------ | ------------ |
| 2384 × 1684 pt      | 34     | A1 альбомный |
| 595,22 × 842 pt     | 25     | A4 книжный   |
| 3370 × 2384 pt      | 11     | A0 альбомный |
| 4768 × 3370 pt      | 2      | 2×A0         |

### Независимое подтверждение ADR-0008

ADR-0008 утверждал, опираясь на сравнение пропорций растра: «на 47 повёрнутых листах
координаты расходятся с `MediaBox`». Здесь то же число получено **другим способом** —
прямым чтением `/Rotate` из документа: ровно 47 страниц с поворотом 90°, и у всех 47
отображаемая ширина не совпадает с шириной `MediaBox`.

Два независимых метода дали одно число. Это и есть причина, по которой поворот к
нормализованным координатам не применяется второй раз.

Время разбора — 0,40 с на 47 МБ и 77 страниц. Опасение промта 02, что разбор PDF растянет
полуторасекундный импорт, оказалось несущественным для этого документа, но задание всё равно
отдельное: длительность зависит от файла, а не от наших ожиданий.

## 3. Поток задания

```text
DocumentRevision(PDF)
  → потоковая выгрузка в ограниченный временный файл
  → pypdf читает страницы (в отдельном потоке)
  → проверка: число страниц, положительные размеры, кратность поворота
  → одна транзакция: листы созданы или найдены → геометрия записана → ready
  → succeeded
```

Разбор вынесен в `asyncio.to_thread`: он синхронный, и держать на нём цикл событий нельзя —
воркер перестал бы слать пульс и потерял бы аренду. Временный каталог удаляется даже при
исключении. PDF в память целиком не читается.

### Два сценария, одна операция

Идентификаторы листов детерминированы формулой `uuid5(namespace, "{revision_id}:sheet:{index}")` —
той же, что у импортёра, дословно. Поэтому создание и обогащение это один upsert, а не две
ветки: прямая загрузка создаёт листы, импорт пакета их обогащает, повтор ничего не дублирует.

Растровые `width_px`/`height_px` и `rotation` листа из пакета не трогаются: это свидетельство
распознавалки, а не факт документа.

### Отказ откатывает всё

Расхождение числа страниц — `PDF_PAGE_COUNT_MISMATCH`, откат транзакции, ревизия остаётся
`failed` без единой строки геометрии. Документ, часть которого меряется, а часть нет, причём
молча, — хуже, чем документ, который не меряется вовсе.

Проверяются три условия: число листов против числа страниц, совпадение номеров страниц и
объявленное пакетом `page_count`.

## 4. Что не попадает в журнал

Содержимое PDF не логируется ни в сообщениях об ошибках, ни в трассировках: там чужая
проектная документация. При неожиданном исключении записывается имя класса — этого хватает,
чтобы понять, куда смотреть.

## 5. Контракт

`GET /api/v1/sheets/{sheet_id}/geometry` — отдельный ресурс, не поле листа: список на 77
листов не должен тащить геометрию каждого, а причина отсутствия у геометрии своя.

- **200** — геометрия;
- **404** — листа нет в этом пространстве (не 403: он подтвердил бы существование);
- **409 `GEOMETRY_NOT_READY`** — лист есть, геометрии нет.

Размеры уходят строками: `JSON.parse` превратил бы их в `float64` и потерял каноническую
десятичную запись, на которой построен отпечаток.

`DocumentRevisionRead` расширен полями `geometry_status` и `geometry_error_code` — аддитивно.
Так интерфейс отвечает на «почему у листа нет геометрии» тем же запросом, который и так
делает, различая «не извлекали», «извлекаем», «готово» и «не удалось».

Клиент перегенерирован, ручных TypeScript-DTO нет.

## 6. Тесты

Добавлено 25 тестов в `tests/test_page_geometry.py`: 14 идут без базы, 11 требуют PostgreSQL.

| Группа               | Что проверяется                                                                                                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Провайдер            | книжная, альбомная, повороты 90/180/270, порядок страниц, отрицательный поворот, битый файл, зашифрованный файл, версия парсера                                                              |
| Отпечаток            | одинаковая геометрия даёт одинаковый отпечаток, другой размер — другой                                                                                                                       |
| Ключ идемпотентности | включает версию парсера                                                                                                                                                                      |
| Извлечение           | прямой PDF создаёт листы, существующие обогащаются без дублей, геометрия записана для каждой страницы, повтор заменяет, расхождение числа страниц отвергается, объявленное число проверяется |
| Постановка           | задание проектное, повтор возвращает то же задание                                                                                                                                           |
| Реестр               | у нового типа есть обработчик                                                                                                                                                                |
| API                  | чужой лист 404, до извлечения 409, успешный ответ с точными десятичными                                                                                                                      |

### Пограничный тест, сломавшийся справедливо

`test_only_one_real_job_type` утверждал, что исполняемый тип задания ровно один. Stage 2A
добавил второй, и тест переписан осознанно — не подогнан.

На его месте два: `test_real_job_types_are_named_explicitly` сверяет список целиком (новый
тип попадает туда решением, а не молча) и `test_no_job_type_invokes_a_model` — настоящая
граница этапа: ни один исполняемый тип не соответствует этапу конвейера, использующему
модели. Список заданий будет расти, а этот запрет — нет.

### Синтетические фикстуры

PDF для тестов строятся тем же pypdf, который их читает. Компромисс осознанный: проверяется
не разбор чужого формата, а собственная логика — отображаемый размер, поворот,
согласованность с листами, откат. Совпадение с настоящим документом проверено отдельно, на
эталоне (раздел 2).

### Чего здесь проверить нельзя

11 тестов требуют PostgreSQL и на этой машине пропускаются: извлечение с базой, откат при
расхождении, API-граница. Их и миграцию `0008` закрывает прогон на стенде:

```bash
pnpm infra:up
pnpm db:migrate                      # применит 0008
node scripts/py.mjs -m alembic check
node scripts/py.mjs -m alembic downgrade base && pnpm db:migrate
pnpm test
```

Живой сквозной прогон — импорт эталонного пакета воркером и появление геометрии у всех 77
листов — относится к промту 15. Флаг `takeoff.manual` остаётся выключенным.

## 8. Остаток

- эндпоинт есть, но фронтенд его пока не читает: это промты 06 и 11;
- сверка серверных размеров с `pdf.js` лист в лист на живом стенде — промт 15. Косвенно она
  уже подтверждена совпадением числа повёрнутых листов с ADR-0008;
- существующие ревизии PDF переведены миграцией `0008` в `pending`, но задания для них не
  созданы: миграция меняет схему, а не запускает работу. Для уже загруженных документов
  геометрия появится после повторной загрузки либо ручной постановки задания.
