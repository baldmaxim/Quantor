# ADR-0010. Оркестратор будущего конвейера: лёгкая очередь или durable-платформа

Статус: принято, 2026-09-04

## Контекст

[ADR-0005](0005-abstrakciya-zadanij.md) зафиксировал абстракцию заданий и отложил выбор
исполнителя. Сейчас реальная нагрузка одна — импорт распознанного пакета, — и она выполняется
фоновой задачей внутри процесса API.

Будущий конвейер выглядит иначе: `ingest → sheet_parse → ocr_layout → vector_extract →
symbol_detect → semantic_link → measure → quantity_calculate → verify → export`. Это
десять шагов, часть из которых идёт параллельно по листам, обращается к моделям, занимает
минуты и падает по внешним причинам. Такой конвейер требует повторов, возобновления с места
падения, отмены и наблюдаемости.

Решение нужно принять заранее, чтобы шаги проектировались под будущего исполнителя, но
не устанавливать платформу до появления нагрузки.

## Решение

**Сейчас** — исполнение внутри процесса API. Состояние в базе, контракт шага описан в
`app/contracts/pipeline.py`: идемпотентность, повторяемость, отменяемость, возобновляемость,
происхождение результата.

**При появлении второго-третьего реального шага** — лёгкая очередь (Redis + собственный
воркер или RQ). Порог перехода: обработка перестаёт помещаться в процесс API либо появляется
второй одновременный пользователь.

**Durable-платформа (Temporal или аналог)** — когда одновременно выполняются три условия:

1. конвейер длиннее трёх шагов и шаги зависят друг от друга;
2. требуется возобновление длинного прогона с середины после падения процесса;
3. появились внешние вызовы с ненадёжной задержкой — удалённые модели.

Пока хотя бы одно условие не выполнено, платформа приносит эксплуатацию без отдачи.

Любой переход не должен затрагивать API и интерфейс: они работают с `Job` и его состоянием,
а не с исполнителем.

## Последствия

- Контракт шага написан заранее, поэтому шаги сразу проектируются идемпотентными и
  возобновляемыми — переезд на очередь не потребует их переписывать.
- Пока исполнение внутри API, несколько одновременных импортов займут рабочие потоки
  приложения. Это известное ограничение и одновременно ясный сигнал к переходу.
- Ни Celery, ни Temporal сейчас не в зависимостях — это проверяется тестом.

## Отвергнутые альтернативы

- **Поставить Temporal сразу.** Отдельная платформа с собственной эксплуатацией ради одной
  операции импорта.
- **Celery сразу.** Требует Redis и отдельного процесса; при одной нагрузке даёт только
  накладные расходы.
- **Не планировать вовсе.** Тогда шаги напишут без идемпотентности и возобновления,
  и переход обойдётся переписыванием конвейера.
