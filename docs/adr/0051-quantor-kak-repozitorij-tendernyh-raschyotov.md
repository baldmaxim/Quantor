# ADR-0051. Quantor как репозиторий тендерных расчётов (обмен с TENDER)

Статус: принято, 2026-11-16 (решение владельца). Дополняет ADR-0036, ADR-0039, ADR-0041, ADR-0044.

## Контекст

Механику (ОВ, ВК, пожаротушение, кондиционирование, холод) и ЭОМ/СС владелец считает в TENDER навыками
`raschet-*`. Их геометрия живёт в трёх несовместимых системах (пункты листа PDF, метры от осей, мм IFC) и
наружу не выходит: результат — Excel и альбомы PDF. Движок CAD Quantor по каждому плану даёт понятную
сетку координат: кадр вида в мм, оси, уровни, зоны, конструкции, стояки, размещение этажа в здании.
Владелец хочет, чтобы расчёты систем загружались в Quantor и хранились у проекта с версиями, а Quantor
показывал их в 2D и 3D поверх документации — как GitHub для расчётов объекта. Трассы ВИС движка
(`cad_mep`) при этом можно отключить.

## Решение

1. **Два пакета** ([формат](../tender-exchange/01-format.md)):
   - «База объекта» `quantor.object_base.v1`, Quantor → TENDER: кадр, оси, уровни, зоны, конструкции,
     стояки, размещение этажей. Выпуск — действие координатора (право `tender.base.release`, роль
     администратора пространства) по видам проекта; выпуск неизменяем, ZIP хранится в объектном
     хранилище, скачивается кнопкой и вручную кладётся в `TENDER/Работа/Quantor/Базы/`.
   - «Расчёт» `quantor.tender_calc.v1`, TENDER → Quantor: трассы и приборы в мм кадра вида (Z от чистого
     пола), объёмы по этажам, вопросы. Загружается навыком `quantor-obmen` напрямую на боевой портал по
     персональному токену.
2. **Репозиторий расчёта** = проект + раздел (`mech`/`eom`/`ss`) + система + название. Каждая загрузка —
   неизменяемая версия (номер, автор, сообщение, выпуск базы, sha256 пакета); тот же ZIP повторно — та же
   версия. Новая версия делает прежнюю `superseded`; отзыв версии — координатором.
3. **Координаты** — только кадр вида базы. Навыки считают как прежде и при выгрузке переводят точки
   аффинно по общим осям; качество привязки — в манифесте, `max > 500 мм` — отказ.
4. **Хранение** — ZIP и файлы видов в объектном хранилище (ADR-0002), в PostgreSQL — метаданные, манифест,
   свод объёмов и ключи/sha256. Геометрия в базу не пишется.
5. **Показ**: страница «Расчёты» проекта (репозитории, история версий, объёмы, вопросы, разница объёмов с
   прошлой версией); слой «Расчёты» в 2D-наложении вида и в 3D этажа и здания тем же кодом, что трассы
   движка (`routes3d.v2` — подмножество формата вида расчёта). Вид, перестроенный после выпуска базы
   (`dxf_sha256` другой), показывается с пометкой «база устарела».
6. **Флаги**: `tender.exchange` (пилот, на пространство) закрывает обмен в интерфейсе и на сервере;
   `cad.mep_engine` (пилот, выключен по умолчанию) закрывает построение и показ трасс ВИС движка — кнопки,
   слои 2D и 3D, `POST …/mep-routes` → 409 `CAD_MEP_ENGINE_DISABLED`. Данные трасс движка не удаляются.
7. **Персональные API-токены** (`qtk_…`): создаёт пользователь у себя в профиле, токен виден один раз, в
   базе — только sha256; токен привязан к пространству, ограничен областью `tender` (чтение выпусков базы,
   загрузка и чтение расчётов) и не даёт ничего сверх прав роли владельца токена. Отзыв — сразу.

## Границы

- **Цен нет**: в пакете расчёта ключи и значения про стоимость — отказ загрузки. ПЗ, расценка, HUBTender —
  только в TENDER. Запрет стоимости из CLAUDE.md не ослабляется.
- Объёмы расчёта — внешний результат с происхождением (навык, версия, автор), не `Measurement`, не
  `ExpectedQuantity` calc и не ВОР Quantor; в итоги обмера и calc не входят.
- Геометрия расчёта не меняет зоны, конструкции, реестр стояков и трассы движка.
- Клиентские данные покидают портал только к владельцу (ручная выгрузка базы); во внешние API не уходят.
