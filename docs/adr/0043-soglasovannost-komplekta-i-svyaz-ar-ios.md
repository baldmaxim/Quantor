# ADR-0043. Согласованность комплекта: паспорт листа, каркас здания, связь АР ↔ ИОС

Дата: 2026-11-11
Статус: черновик; решения 1–3 (флаг, мост в calc, ТЗ списком) приняты владельцем 2026-11-11

## Контекст

Разбор кода 2026-11-11:

- У листа (`Sheet`) нет раздела, типа листа, корпуса, секции и этажа. `Document.discipline` — свободная строка,
  заполняется вручную. Марка раздела по шифру штампа известна только адаптеру calc (кортеж в
  `services/calc/adapters/recognized.py`) и только для распознанного ZIP.
- Модели здания нет. Корпус, секция и этажи разбираются из заголовка плана в `cad_walls`, совмещение этажей по осям
  есть только в 3D здания (`cad_building3d`).
- Трассы CAD строятся на одном листе. Геометрия листов ИОС не используется. Стояк связан с шахтой АР только по
  `shaft_id` внутри листа (ADR-0041); непрерывность по этажам не проверяется.
- calc не читает CAD. Сверок «экспликация ↔ зоны», «квартирография ↔ квартиры», «ПЗ ↔ этажность и отметки»,
  «схема ИОС ↔ план АР», «ТЗ ↔ решения» нет. Есть две: итог квартир «документ ↔ квартирография» (паспорт ВК) и
  покрытие групп конструкций ВОР (`cad_vor`).

Нужен слой, общий для любых объектов: что за лист, к какому этажу он относится, где на этаже его объекты и
совпадает ли это с текстовыми документами.

## Решение

**1. Отдельный контур за флагом `project.consistency`.** Пилотная возможность на пространство: выключена по
умолчанию, включается в админке, закрывает и интерфейс, и сервер (ADR-0023). Контур не пишет в таблицы обмера, MEP,
`Region`, calc и CAD — только в свои.

**2. Универсальность через словари, а не через код.** Марки разделов (ПП РФ № 87, ГОСТ Р 21.101: ПЗ, АР, КР,
ИОС1–ИОС7, ПБ, …), типы листов, синонимы помещений, подписи шахт и коды систем (В1, Т3, Т4, К1, ВПВ, АУП…) —
версионированные словари в коде контура (`consistency.dict.*.v1`), только общедоступные нормативные обозначения.
Отклонение конкретного проекта решает человек при подтверждении, а не правка словаря под объект. Кортеж марок calc
переходит на общий словарь без изменения поведения.

**3. Паспорт листа.** Сущность `SheetPassport` (один на лист и вид): раздел, тип листа (план этажа, разрез, фасад,
схема, таблица, текст, прочее), стадия, корпус, секция, диапазон уровней (`level_from`…`level_to` — типовой план
покрывает несколько), отметка, шифр, номер листа; статус `candidate` / `confirmed` / `rejected`; доказательства
каждого поля (`stamp`, `cad_title`, `page_label`, `file_name`, `manual`). Кандидат собирает исполнитель заданий
по текстовому слою PDF (pypdf, без растра и OCR) и данным распознанного пакета, если он есть. Подтверждает человек,
в том числе пачкой в таблице листов. В проверки идёт только подтверждённый паспорт.

**4. Каркас здания.** Сущности корпус → секция → уровень (код, порядковый номер, отметка, высота) на проект и
версию тендера (ADR-0035). Строится из подтверждённых паспортов и фактов ПЗ; расхождения источников — замечания,
не молчаливый выбор. Подтверждает человек.

**5. Совмещение листа с уровнем.** Для плана: поворот и сдвиг из системы координат откалиброванного листа в систему
координат уровня — по совпадающим маркам осей; запасной путь — две точки, указанные человеком. Масштаб берётся
только из калибровки листа человеком; автоопределения масштаба и чтения размерных линий нет. Хранится метод и
невязка; невязка выше порога правила — статус «проверить». Схемы не в масштабе не совмещаются, они связываются только
по топологии (п. 6).

**6. Сквозные якоря.** Объект уровня — шахта, стояк, помещение, квартира, ось — со ссылками на объекты листов
разных разделов (шахта плана АР, стояк реестра или схемы ИОС, точка плана ИОС, зона CAD). Автоматическая ссылка —
кандидат с доказательством; в проверки и calc идёт только подтверждённая.

**7. Проверки — версионированный каталог.** Каждая проверка: код, версия, входы, допуск как параметр правила,
итог `match` / `mismatch` / `not_run` с причиной («нет данных» не равно «совпадает»). Результат —
замечание со ссылками на оба источника и подсветкой на листах; выгрузка списка вопросов Заказчику. Реестр замечаний
контура свой; объединение с вопросами calc — отдельным решением.

**8. Мост в calc (поправка к ADR-0030, принята владельцем).** Подтверждённые данные каркаса, якорей и зон CAD
поступают в Facts Registry через новый адаптер источника с происхождением «структура проекта, подтверждено
человеком». Неподтверждённое в реестр не попадает. Приоритеты источников задаёт версия политики calc.
Остальные запреты calc действуют.

**9. ТЗ — ручной список требований.** Требование ТЗ вводит человек: текст, ссылка на страницу, статус
«выполнено» / «не выполнено» / «вопрос». Автоизвлечения из ТЗ нет.

## Что не меняется

- Модель не выдаёт чисел; LLM и шлюз моделей не используются.
- PyMuPDF, растр, OCR, OpenCV и Shapely в `apps/api` не появляются; разбор PDF — только в исполнителе заданий.
- ВОР Заказчика — объект сверки, не вход расчёта.
- Данные объектов (PDF, паспорта реальных листов, результаты сверок) в git не попадают; в тестах — синтетика.

## Приёмка

Объекты TENDER: 328 «Остров 14» (АР П и РД, ИОС1–5, ТЗ) и 314 «События 6.1» (архив, АР П и РД, ИОС1–5, ПЗ,
ТЗ); пилот 342 — регрессия. Критерии — по этапам плана [docs/consistency/00-plan.md](../consistency/00-plan.md).
Ни одного правила, словаря или порога под конкретный объект.
