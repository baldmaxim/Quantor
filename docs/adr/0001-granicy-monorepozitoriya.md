# ADR-0001. Границы монорепозитория

Статус: принято, 2026-09-04

## Контекст

Портал состоит из нескольких частей с разным темпом изменений: интерфейс, API, будущие
воркеры распознавания и расчёта. Главный риск проекта — слипание всего в один сервис,
после чего правка модели ломает интерфейс и наоборот.

## Решение

Один репозиторий, workspaces на pnpm, границы по приложениям:

```text
apps/web            интерфейс (Next.js)
apps/api            HTTP API и вся серверная логика (FastAPI)
packages/api-client сгенерированный TypeScript-клиент
infra               docker-compose с локальными зависимостями
docs                архитектура, ADR, отчёты этапов
scripts             кроссплатформенные команды разработчика
```

Контракт между `web` и `api` — единственный: OpenAPI. `apps/api` выгружает схему в
`packages/api-client/openapi.json`, из неё генерируется TypeScript-клиент. Сгенерированный
код коммитится, а CI перегенерирует его и падает при расхождении (`pnpm api-client:check`).
Ручных DTO на TypeScript в проекте нет.

Команды разработчика — npm-скрипты в корне, а не Makefile: основная машина разработки под
Windows, где `make` недоступен без дополнительной установки. Всё, что сложнее одной строки,
вынесено в `scripts/*.mjs` на Node.

`apps/worker` не создаётся: пустой каркас без нагрузки только вводит в заблуждение. Граница
для будущих воркеров описана в [ADR-0005](0005-abstrakciya-zadanij.md).

## Последствия

- Изменение схемы API без перегенерации клиента не пройдёт CI — расхождение видно сразу.
- Turborepo не подключается: сборок две, кэшировать пока нечего.
- Общий пакет UI-примитивов (`packages/ui`) не создаётся, пока примитивы нужны одному
  приложению. Появится второй потребитель — появится и пакет.

## Отвергнутые альтернативы

- **Разные репозитории для web и api.** Синхронизация контракта потребовала бы публикации
  пакета и версионирования на ровном месте.
- **Ручные TypeScript-типы вместо генерации.** Дублирование, которое расходится через месяц.
