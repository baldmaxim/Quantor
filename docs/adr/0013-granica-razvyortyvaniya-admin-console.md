# ADR-0013. Граница развёртывания административного контура

Дата: 2026-09-07
Статус: принято

## Контекст

Stage 1.5 добавляет управление платформой: рабочие пространства, пользователи и доступы,
типизированные настройки, флаги возможностей, диагностика интеграций, реестр провайдеров
моделей, задания и воркеры, журнал аудита.

Дешёвый путь — раздел `/admin` внутри `apps/web`. Он же и опасный: административный код
попадает в тот же бандл и на тот же origin, что и пользовательский портал, а «про этот
адрес никто не знает» выдаётся за меру защиты.

Отдельный вопрос — общие примитивы интерфейса. Копировать кнопки и токены в новое
приложение нельзя: тёмная тема разъедется в первый же месяц, и заметят это на показе.

## Решение

### 1. Административный контур — отдельное приложение `apps/admin`

```text
apps/web    пользовательский портал (порт 3000)
apps/admin  контур управления платформой (порт 3001)
apps/api    единый версионированный API
```

Что это даёт, в порядке значимости:

**Service worker портала перестаёт быть проблемой.** `apps/web/public/sw.js` кэширует
`/_next/static/` бессрочно и захватывает всех клиентов. Внутри раздела админские чанки
попали бы в тот же кэш и на тот же origin, и требование приёмки «service worker не кэширует
привилегированные ответы» превратилось бы в предмет спора вместо факта. У `apps/admin`
service worker не заводится вовсе.

**Изоляция бандла становится структурной, а не намеренной.** `apps/admin/package.json` не
содержит `pdfjs-dist`. Требование «в админке нет чанков просмотрщика» доказывается
отсутствием зависимости, а не надеждой на то, что разделение кода не отъехало. Внутри
раздела проверить можно было бы только отсутствие регрессии.

**Появляется возможность отдельного хоста, CSP и сетевой политики.** `admin.<домен>`,
доступ только из корпоративной сети или через VPN — это решения на будущее, но принимать их
можно, только если приложение отдельное.

Цена признаётся: одна дополнительная сборка в CI, ещё один процесс разработки, шаг
извлечения общих примитивов.

### 2. Секретность адреса защитой не считается

Вход в админку разрешён только по разрешению `system.admin`, проверяемому на сервере.
Каждый административный маршрут API закрыт запретом по умолчанию на своём маршрутизаторе.
Неизвестность адреса — деталь удобства, и в модели угроз она не участвует.

### 3. Оболочка не рендерится тому, кому не положено

Проверка выполняется серверным компонентом в корневом макете раздела: cookie из запроса
пересылается в `GET /api/v1/auth/session` по внутреннему адресу API.

- нет сессии → страница входа, оболочка не строится;
- сессия есть, `system.admin` нет → страница отказа, **оболочка не строится**;
- API недоступен → страница о недоступности, а не оболочка с пустыми плитками.

Возврат происходит **до** конструирования оболочки, поэтому её разметки нет в ответе и ни
один привилегированный запрос не отправляется. Клиентская проверка добавляется поверх — для
случая, когда права отозвали посреди сеанса, — но границей не является.

Промежуточного слоя (`middleware.ts`) в приложении нет, хотя при принятии решения он
предполагался как дешёвый отсев запросов без cookie. При реализации выяснилось, что
отсекать нечего: в dev-режиме портала cookie сеанса не существует вовсе, личность выдаёт
сервер, и такой слой всегда пропускал бы запрос дальше. Файл, делающий вид, что проверяет,
хуже отсутствующего — его читают как часть границы.

### 4. Ограничение развёртывания: API и админка — один регистрируемый домен

Серверная проверка возможна ровно потому, что cookie сессии доходит и до сервера админки:
`admin.example.ru` и `api.example.ru` относятся к одному регистрируемому домену, локально
`localhost:3001` и `localhost:8000` — тоже (порт в определение site не входит).

**Если API окажется на другом регистрируемом домене, эта схема перестаёт работать.**
Запасной путь — прокси-маршрут внутри `apps/admin`, который ходит в API от своего имени.
Ограничение записано здесь, чтобы оно не обнаружилось при первом боевом развёртывании.

### 5. Общие примитивы выносятся в `packages/ui`

[ADR-0001](0001-granicy-monorepozitoriya.md) разрешил этот шаг заранее: «Общий пакет
UI-примитивов (`packages/ui`) не создаётся, пока примитивы нужны одному приложению.
Появится второй потребитель — появится и пакет.» Второй потребитель появился, значит
извлечение исполняет действующее решение, а не отменяет его. `pnpm-workspace.yaml` уже
содержит глоб `packages/*`, править его для нового пакета не нужно.

Переносятся токены дизайна, базовые стили и примитивы (`cx`, `Button`, `SearchInput`,
`StatusBadge`, `ProgressRow`, `EmptyState`, `ErrorState`, `Skeleton`, `Field`), тема и
иконки. Остаются в портале то, что принадлежит ему: инспектор рабочей области и доменные
преобразования состояний.

Переносится с оставлением реэкспортирующего модуля на прежнем месте: `@/components/ui`
импортируют 20 файлов, и менять их все ради нулевого изменения поведения незачем. Критерий
приёмки шага — существующие тесты портала проходят **без единой правки**.

Токены остаются одним файлом целиком, включая переменные, нужные только просмотрщику.
Разделение файла переменных — это способ, которым светлая и тёмная темы начинают тихо
расходиться; несколько сотен байт неиспользуемых свойств этого не стоят.

### 6. Отдельный процесс исполнения заданий не нарушает ADR-0001

Тот же ADR-0001 отказывается создавать `apps/worker` как пустой каркас. Вынос исполнения
заданий, который делает Stage 1.5, этого решения не нарушает: воркер остаётся **вторым
входом в `apps/api`** (`python -m app.worker`), разделяя с ним модели, сервисы и настройки,
а не становится третьим приложением. Каркас перестал быть пустым — нагрузка появилась
вместе с многопользовательским режимом, чего [ADR-0005](0005-abstrakciya-zadanij.md) прямо
и ожидал.

### 7. Админка показывает только подтверждённые данные

Отсутствующая метрика выводится словами «не измерено» или «неизвестно», но никогда нулём
или «в порядке». Плитка состояния различает `healthy`, `degraded`, `unavailable`,
`not_configured`, `unknown` и показывает время и источник проверки.

Панель, показывающая ноль вместо «не знаю», хуже пустой: по ней принимают решения.

## Последствия

- Административный код физически не может попасть в бандл портала — это свойство
  структуры, а не дисциплины.
- CI получает ещё одну сборку фронтенда (порядка полутора минут) и отдельные шаги проверок.
- `pnpm dev` поднимает четыре процесса: API, воркер, портал, админка.
- Появляется `packages/ui` — общий пакет, изменение которого затрагивает оба приложения.
  Это цена единой темы, и она дешевле расхождения.
- Развёртывание получает жёсткое требование к доменам, записанное в пункте 4.
- У админки нет PWA и офлайн-режима. Это осознанно: контур управления платформой без сети
  бесполезен, а закэшированное состояние системы вводит в заблуждение.

## Отвергнутые альтернативы

- **Раздел `/admin` внутри `apps/web`.** Дешевле на день работы, но общий origin, общий
  service worker и общий бандл; изоляция превращается из факта в обещание. Пришлось бы
  оформлять отступление от промта отдельным решением — и защищать его на приёмке.
- **Скрытый адрес вместо проверки прав.** Не защита. Адрес попадает в историю браузера,
  логи прокси и закладки.
- **Третье приложение `apps/worker`.** Разошлось бы с ADR-0001 без выигрыша: воркеру нужны
  те же модели, сервисы и настройки, что и API, и отдельный пакет означал бы либо
  дублирование, либо ещё один общий пакет.
- **Копирование примитивов в админку.** Ноль связности сегодня и разъехавшаяся тёмная тема
  через месяц.
- **Полный перенос всех компонентов портала в `packages/ui`.** Пакет превратился бы в
  свалку: инспектору рабочей области в админке делать нечего.
- **Отдельный административный API вместо `/api/v1/admin/*`.** Второй контракт, вторая
  генерация клиента, второй шлюз дрейфа — ради границы, которую и так даёт проверка прав
  на маршрутизаторе.
