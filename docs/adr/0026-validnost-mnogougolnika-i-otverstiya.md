# ADR-0026. Валидность многоугольника и отверстия: `points` + `holes`, отказ вместо починки

Статус: принято, 2026-09-14. Промт 05 Stage 2B. Меняет зафиксированное в Stage 2A поведение
«самопересечения не проверяются» (`services/geometry/transform.py`, датасет `measurement_v1`).

## Контекст

- Пилот Stage 2B — площадь плиты с отверстиями по PlanSwift ground truth. У `Measurement` был
  только один контур `points`; отверстие выразить было нечем.
- Stage 2A сознательно не выбрал политику для самопересечений: формула шнурков на «бантике» даёт
  разность долей — на эталонном случае 0 м². Ноль — это утверждение о величине, и ложное.
- Кандидаты модели (промты 16–21) придут в тот же `Measurement`: валидатор нужен до них, а не после.

## Решение

### 1. Политика валидности

Многоугольник **недействителен**, если хотя бы одно:

| Код                  | Что                                                                    |
| -------------------- | ---------------------------------------------------------------------- |
| `too_few_vertices`   | в кольце меньше трёх вершин                                            |
| `duplicate_vertex`   | две соседние вершины совпадают (включая замыкание последней на первую) |
| `degenerate_ring`    | все вершины на одной прямой                                            |
| `self_intersection`  | рёбра одного кольца пересекаются, **касаются** или накладываются       |
| `ring_intersection`  | кольцо пересекает или касается другого кольца                          |
| `hole_outside_outer` | отверстие вне внешнего контура                                         |
| `hole_inside_hole`   | отверстие внутри другого отверстия                                     |
| `too_complex`        | проверка вышла бы за предел работы — отказ, а не «вероятно, годится»   |

- Касание — тоже дефект: у «восьмёрки» с общей вершиной площадь неоднозначна.
- Предикаты **точные**: ориентация с фильтром Шевчука по double и откатом на `Fraction`. Допуска нет:
  вершина в 1e-12 от ребра — не касание, и ответ не зависит от порядка обхода.
- Вершина посреди прямого участка законна; разворот ребра назад по той же прямой — наложение.
- **Геометрия не чинится молча.** Убранная вершина или «исправленный» обход дали бы площадь другой
  фигуры, чем нарисовал человек.

### 2. Где проверяется

- **Запись** (создание, пакет, правка вершин): недействительный многоугольник отвергается —
  `422 GEOMETRY_INVALID`, в теле `detail.issue` — код, кольцо, вершина или пара рёбер.
- **Расчёт**: движок проверяет контур сам. Строка, легшая в базу до политики или ручным SQL, получает
  состояние `invalid_geometry` с `geometry_issue` и пустую величину — никогда не 0 м². Состояние
  проверяется раньше масштаба: калибровка такую фигуру не исправит.
- **База** держит форму, но не топологию: CHECK `holes_match_geometry` — массив, отверстия только у
  `polygon`, каждое кольцо — массив минимум из трёх элементов (`strict` jsonpath).

### 3. Хранение отверстий: `points` + `holes`

`points` остаётся внешним контуром, рядом — `holes jsonb not null default '[]'`, список колец в том же
каноне нормализованных точек. Сравнивались:

| Вариант                                   | Против                                                                                                                                                            |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`points` + `holes`** (выбран)           | —                                                                                                                                                                 |
| GeoJSON-подобная `geometry: [[outer], …]` | переломил бы контракт `points` у всех четырёх типов, клиент, счёт, линии и CHECK числа точек; миграция данных с риском сдвинуть величины `area.v1`                |
| Колонка PostGIS `geometry(Polygon)`       | координаты нормализованные, не проекция; `ST_IsValid` допускает касание в вершине по OGC — политика здесь строже; второй источник правды рядом с `points` в JSONB |
| Shapely / GEOS в `apps/api`               | новая нативная зависимость и ADR лицензии; `is_valid` — та же OGC-семантика касаний; нужен детерминированный отказ `too_complex`, а не время без предела          |

Старые строки получают `[]`: их геометрия, правило и отпечаток не меняются.

### 4. Правило величины

- Многоугольник **без отверстий** — прежнее `area.v1`, прежний отпечаток входа байт в байт.
- С отверстиями — **`area_with_holes.v1`**: площадь контура минус сумма площадей отверстий, каждая —
  формулой шнурков по модулю через каноническую геометрию PDF и сохранённую калибровку. Порядок
  вычитания — порядок хранения; отверстия дописываются в отпечаток входа только когда они есть.
- Итог строки называет все правила, по которым сложен (`area.v1+area_with_holes.v1`), и считает
  недействительные отдельно (`invalid_count` внутри `unavailable_count`).
- Никакой семантики «найди проёмы»: отверстие — чистая геометрия, нарисованная или принятая человеком.

### 5. Пределы

- до `MAX_POLYGON_HOLES = 200` отверстий и `MAX_HOLE_POINTS_TOTAL = 10 000` вершин в них суммарно —
  в схеме запроса и в сервисе;
- валидатор: перебор пар до 64 рёбер, дальше равномерная сетка; оценка заполнения сетки больше
  400 000 записей или пар-кандидатов больше 250 000 — `too_complex`.

## Последствия

- Случай `polygon.bowtie_self_intersecting` меняет ожидание с 0 м² на `invalid_geometry`: датасет
  `measurement_v2` стал умолчанием замера, `measurement_v1` оставлен для воспроизведения отчётов 2A.
- Расчёт многоугольника дороже: валидатор на каждом чтении величин. Шестиугольник — 0,05 мс на
  валидатор при 0,16 мс полного расчёта; контур на 1 000 вершин — 18 мс; 10 000 — 161 мс (стенд без
  GPU, `docs/stage2b/05-geometry-validity-and-holes.md`). Если это станет узким местом листа —
  кэшировать результат проверки по отпечатку геометрии, а не отключать проверку.
- Просмотрщик показывает отверстия (заливка чёт-нечет, обводка колец, клик в отверстие не выбирает
  фигуру); рисование отверстий вручную — вместе с проверкой кандидатов AI (промты 21–22).
