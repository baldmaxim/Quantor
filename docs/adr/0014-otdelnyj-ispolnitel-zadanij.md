# ADR-0014. Отдельный исполнитель заданий

Дата: 2026-09-08
Статус: принято

## Контекст

[ADR-0005](0005-abstrakciya-zadanij.md) оставил исполнение внутри процесса API и назвал
условие, при котором это надо менять: «явная причина вынести исполнение в воркер при
первой же многопользовательской нагрузке». Условие наступило — портал получил
аутентификацию и рабочие пространства ([ADR-0012](0012-granica-autentifikacii-i-avtorizacii.md)),
и пользователей стало больше одного.

Измеренная цена сегодняшнего устройства: один импорт эталонного пакета — полторы секунды
работы внутри процесса API. Пока пользователь один, это незаметно. Когда их десять и
каждый загружает альбом, рабочие потоки приложения заняты разбором архивов, и портал
перестаёт отвечать на чтение — то есть на всё остальное, что он умеет.

К Stage 2 положение станет хуже на порядок: распознавание и вычисление объёмов — это
минуты, а не секунды.

## Решение

### 1. Отдельный процесс, а не отдельное приложение

```text
uvicorn app.main:app     # API
python -m app.worker     # исполнитель
```

Тот же образ, тот же код, разные команды. Воркеру нужны те же модели, сервисы и настройки,
что и API; третий пакет означал бы либо дублирование, либо ещё один общий пакет.

Это не нарушает [ADR-0001](0001-granicy-monorepozitoriya.md), отказавшийся создавать
`apps/worker`: пустой каркас там и не создаётся — появляется второй вход в существующее
приложение, и появляется он вместе с нагрузкой.

### 2. Очередь — сама таблица заданий, захват — `FOR UPDATE SKIP LOCKED`

```sql
update jobs set status = 'running', worker_id = :me, attempt = attempt + 1, …
where id = (
    select id from jobs
     where status = 'queued' and available_at <= now()
     order by available_at, created_at
     limit 1 for update skip locked
)
```

Ни Redis, ни Celery, ни Temporal. Состояние задания уже живёт в базе (ADR-0005), а
`skip locked` даёт ровно то, ради чего заводят брокера: двое одновременно пришедших
исполнителей не возьмут одно и то же — второй пропустит занятую строку и посмотрит
следующую.

Брокер добавил бы отдельную систему, которую надо поднимать, обновлять и мониторить, ради
свойства, которое у нас уже есть. Он понадобится, когда потребуется то, чего база не даёт:
распределение по нескольким машинам с приоритетами, отложенные цепочки, гарантированная
доставка вовне.

Порядок `available_at, created_at`, а не только `created_at`: иначе отсрочка повтора
игнорируется, и упавшее задание берут снова немедленно.

### 3. Владение — арендой с пульсом, а не блокировкой на всё время работы

Захват фиксируется сразу, короткой транзакцией. Работа идёт в другой сессии, а владение
держится сроком аренды, который исполнитель продлевает пульсом.

Держать строку заблокированной всё время импорта было бы проще ровно до первого вопроса
«почему задание не видно как выполняющееся»: заблокированная строка не видна ни интерфейсу,
ни диагностике.

Пульс не только продлевает аренду, но и проверяет, наша ли она ещё. Ответ «нет» означает,
что сборщик брошенных решил, будто исполнитель умер, и отдал задание другому. Продолжать
в этом случае нельзя: ту же работу уже делает кто-то ещё.

### 4. Все времена — из часов базы

`Job.created_at` ставит приложение — это осознанный компромисс Stage 1, записанный в
известных ограничениях. Аренду так мерить нельзя: процессов теперь два, часы у них свои,
и расхождение в полминуты превращает живого исполнителя в мёртвого, а его задание — в
добычу соседа.

Поэтому `now()` в SQL, а не `datetime.now()` в Python — во всех местах, где речь о
владении: захват, пульс, сборка брошенных, признак живого исполнителя.

### 5. Отдельная таблица `workers`

Пустая очередь и отсутствующий исполнитель выглядят в `jobs` одинаково. «Заданий нет» и
«брать их некому» — разные состояния установки, и без отдельной записи диагностика их
не разведёт.

Корректно остановленный исполнитель убирает свою запись сам: иначе плановое выключение
выглядело бы в админке как поломка.

### 6. Повтор — только там, где он что-то меняет

```text
повторяемо:    STORAGE_UNAVAILABLE, DATABASE_UNAVAILABLE, TENDERHUB_UNAVAILABLE,
               TENDERHUB_RATE_LIMITED, JOB_LEASE_LOST, JOB_TIMEOUT
не повторяемо: ARCHIVE_UNSAFE_PATH, ARCHIVE_LIMIT_EXCEEDED, CORRUPT_ARCHIVE, LEGACY_*
```

Битый архив останется битым сколько его ни повторяй. Кнопка «повторить» для него —
обещание, которого система не выполнит, поэтому она отключена, а API отвечает отдельным
кодом.

Повтор возвращает **то же** задание в очередь, а не создаёт второе: ключ идемпотентности
уникален, и вставка дубликата превратилась бы в непонятную ошибку вместо повтора.

### 7. Отмена — только ожидающего задания

`cancelled` в перечислении был с Stage 1 и никогда никем не выставлялся. Теперь его
выставляет отмена, и только для задания, которое ещё не начали.

Прерывать выполняющийся импорт нечем: он оставит полуразобранный пакет, и разбираться
с этим дороже, чем дождаться. Совместная отмена — с признаком запроса и остановкой по
пульсу — появится тогда, когда для неё будет настоящий механизм. Заводить колонку заранее
значит повторить ошибку, от которой ADR-0001 отказался: пустой каркас вводит в заблуждение.

### 8. Исполнитель — необязательный компонент готовности

`/health/ready` различает обязательные компоненты и необязательные. Без базы, схемы и
хранилища API не может ответить почти ни на что — это 503. Без исполнителя портал
по-прежнему показывает проекты, документы и чертежи; не работает только запуск новых
импортов.

Отдавать 503 в этом случае значит увести трафик с полностью исправного API и превратить
частичную поломку в полную.

### 9. Прежнее поведение остаётся под флагом

`JOB_EXECUTOR=inline` возвращает исполнение внутрь процесса API. Нужен для запуска без
воркера и потому, что тесты выполняют задание явно, а не гоняются за фоновой задачей.
Умолчание — `worker`.

## Последствия

- Тяжёлый импорт больше не занимает рабочие потоки API.
- `pnpm dev` поднимает четыре процесса вместо трёх.
- Публичный контракт `Job` не изменился: эксплуатационные поля отдаются отдельной схемой
  в административном контуре. Ровно это ADR-0005 и предусматривал, когда требовал, чтобы
  замена исполнителя не затрагивала API и интерфейс.
- Появился второй движок базы: настройки API рассчитаны на короткий запрос (предел 15 с),
  и импорт на 47 МБ в них не укладывается. Менять их ради воркера значило бы ослабить
  защиту API от зависшего запроса.
- Задание, брошенное умершим исполнителем, возвращается в очередь автоматически, но не
  мгновенно: до истечения аренды оно числится выполняющимся.
- Переходы состояний пополнились двумя возвратами в очередь, и оба узкие: `running → queued`
  только через сборщик брошенных, `failed → queued` только через повтор.

## Отвергнутые альтернативы

- **Celery или RQ.** Требуют Redis и отдельного процесса-брокера. Состояние заданий всё
  равно пришлось бы держать в своей базе — иначе интерфейс не покажет ход работы, — то есть
  получилось бы два источника правды вместо одного.
- **Temporal.** Даёт durable-исполнение, повторы и длинные цепочки. Разумный вариант, когда
  конвейер распознавания станет многошаговым; сейчас это отдельная платформа со своей
  эксплуатацией ради одной операции.
- **`LISTEN/NOTIFY` вместо опроса.** Убирает секундную задержку между постановкой и
  захватом. На фоне полутора секунд импорта выигрыш незаметен, а надёжность падает:
  уведомление теряется при обрыве соединения, и опрос всё равно нужен как страховка.
- **Блокировка строки на всё время работы.** Проще на вид, но выполняющееся задание
  перестаёт быть видимым, а зависший исполнитель держит блокировку до разрыва соединения.
- **Отдельный процесс-сторож для брошенных заданий.** Ещё одно, что надо запускать и
  мониторить, ради одного запроса раз в полминуты. Сборку делает сам исполнитель.
