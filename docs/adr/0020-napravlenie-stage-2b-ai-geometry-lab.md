# ADR-0020. Направление Stage 2B: AI Geometry Lab вместо Auto Count

Статус: принято, 2026-09-11

## Контекст

Stage 2A закрыт: ручная линия на известном размере даёт верные метры, ошибки живой приёмки на
настоящем чертеже — от 0,05 до 0,349 %.

Передача `docs/stage2a/HANDOFF_TO_STAGE2B.md` (§11) предлагала начать Stage 2B с Auto Count:
шлюз моделей в runtime, локальные и внешние зрительные модели, сравнение детектора и VLM, модель
сразу создаёт обычный `Measurement(source=ai)`.

После передачи появился вход, которого тогда не было, — PlanSwift-разметка двух реальных объектов:

- кладка «ЖК Stories» — осевые линии стен;
- монолит «Мосфильмовская 31А» — контуры плит с отверстиями.

Это ground truth той самой геометрии, которую портал уже умеет считать. У Auto Count такого
эталона нет, а подход «большая VLM, посчитай проект» не даёт проверяемой геометрии вообще.

## Решение

Stage 2B — сравнительная лаборатория геометрии на PlanSwift ground truth:

```text
PlanSwift GT
  → A. малая семантическая сегментация и осевые линии
  → B. SAM 2 / MobileSAM
  → C. Qwen3-VL + Unsloth SFT: локализация или ограниченная геометрия
  → D. Qwen3-VL → SAM → точная маска
  → маска или вектор → Mask→Vector → кандидат → проверка человеком
  → Measurement(source=ai) → существующий Quantity Engine
```

Пилотных доменов два: площадь плиты с отверстиями и осевые линии кладки.

Правила этапа:

- модель не выдаёт физическую величину — метры и м² считает только существующий детерминированный
  движок после канонической геометрии и ручной калибровки;
- автоматическое определение масштаба и чтение размерных линий по-прежнему запрещены;
- победителя выбирает единый QTO-бенчмарк по гейтам, объявленным до теста, а не IoU;
- в портал интегрируется только прошедшая гейт задача и только после того, как владелец явно
  утвердил конкретные pipeline и checkpoint;
- результат на двух проектах называется **within-project proof of feasibility**, а не точностью на
  новых объектах.

Пакет промтов — `_prompts/stage2b_ai_geometry_qwen/`. Направление Auto Count из HANDOFF не
выполняется. Сам HANDOFF не переписывается: к нему добавлено закрывающее обновление.

## Последствия

- Первыми идут не модели, а то, без чего их результат нельзя принять: масштабируемый просмотрщик,
  валидность геометрии, отверстия многоугольника, импорт и проверка ground truth, разбиение без
  утечки.
- Появляется отдельный ML-контур вне `apps/api` (ADR-0021).
- Предсказание живёт отдельно от измерения, пока его не принял человек (ADR-0022).
- Auto Count, семантическая классификация и VLM-помощники откладываются за пределы Stage 2B.
- На двух проектах обобщение не доказывается: для этого нужны новые независимые PlanSwift-проекты.

## Отвергнутые альтернативы

- **Auto Count первым.** Нет эталона для сравнения, а счёт элементов не проверяет геометрию, на
  которой держится QTO.
- **Большая VLM считает объёмы.** Число без цепочки «измерение → лист → геометрия → калибровка →
  правило» объяснить нельзя (ADR-0008).
- **Внешние модели для клиентских чертежей.** Данные PlanSwift частные: без отдельного решения
  владельца они не покидают локальный контур.
- **Одна заранее выбранная модель.** Это выбор по вкусу вместо измерения. Сравнить архитектуры на
  одном разбиении дешевле, чем интегрировать не ту.
