# ADR-0008. Координаты и происхождение данных

Статус: принято, 2026-09-04

## Контекст

Распознавалка отдаёт координаты в нормализованном пространстве страницы с началом в левом
верхнем углу (`normalized_page_top_left`), значения в диапазоне [0, 1]. Просмотрщик работает
в пикселях экрана с произвольным масштабом, PDF — в своей системе координат, у страниц бывает
поворот. Смешение этих систем — классический источник «разметка не совпадает с чертежом».

## Решение

**Канонические координаты — нормализованные, от левого верхнего угла страницы.** В таком виде
они хранятся в базе и передаются по API. Прямоугольник — `[x0, y0, x1, y1]`, полигон — список
точек в том же пространстве.

Перевод в экранные координаты выполняется только в момент отрисовки, с учётом поворота
страницы. Обратное преобразование (экран → нормализованные) — единственный путь записи
геометрии, созданной пользователем.

Пространство координат исходного пакета сохраняется явным полем: если распознавалка когда-нибудь
сменит систему, старые данные останутся читаемыми.

**Разделение понятий, обязательное к соблюдению:**

```text
Region       что увидела распознавалка — свидетельство
Measurement  геометрия, созданная для подсчёта — намерение пользователя или ИИ
Quantity     детерминированно вычисленная величина с указанием правила
```

Это три разные сущности. `Region` не превращается в `Measurement` и не переиспользуется под него.

**Инвариант происхождения.** Любой производный объект должен прослеживаться по цепочке:

```text
проект → документ → ревизия → лист → геометрия/свидетельство → версия алгоритма или правила
```

Величину, которую нельзя объяснить этой цепочкой, нельзя показывать как результат.

## Последствия

- Совпадение разметки с чертежом проверяется отдельными тестами преобразования координат.
- Хранение не зависит от разрешения растеризации: те же данные корректны при любом масштабе.
- Запрет на переиспользование `Region` под измерения экономит болезненную миграцию на Stage 2.

## Отвергнутые альтернативы

- **Хранить координаты в пикселях страницы.** Привязка к конкретному разрешению растеризации.
- **Пространство PDF с началом внизу слева.** Требует конверсии на каждом шаге импорта и
  расходится с форматом источника.

## Уточнение по формату legacy-v1 (проверено на эталонном пакете)

Координаты в пакете распознавалки нормализованы относительно **уже повёрнутой** страницы —
той, которую видит человек, а не относительно исходного `MediaBox`. Проверено на всех
77 страницах эталона: пропорции растра совпадают с `page.rect` (страница после `/Rotate`)
и на 47 повёрнутых листах расходятся с `MediaBox`.

Отсюда два правила для просмотрщика:

1. **Размер страницы берётся у отрисовщика, а не из `width_px`/`height_px` пакета.** Это
   пиксели растра, снятого с непостоянной плотностью: 4,17 px/pt на листах A1 и 3,16 на
   листах другого формата в том же документе. Пересчитать одно в другое, не зная плотности
   конкретной страницы, нельзя.
2. **Поворот к координатам областей повторно не применяется.** Поле `rotation` в пакете
   описывает исходную страницу PDF; отрисовщик уже применил тот же поворот сам. Двойной
   поворот разворачивал разметку поперёк чертежа — штамп уезжал из правого нижнего угла
   в левый нижний.

Механизм поворота координат остаётся в `coordinates.ts` не про запас, а под формат
пакета v2: если он начнёт хранить координаты до поворота, разница ляжет именно туда.
