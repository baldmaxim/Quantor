# ADR-0002. Объектное хранилище для бинарных файлов

Статус: принято, 2026-09-04

## Контекст

Портал работает с PDF проектной документации по 50–500 МБ и с ZIP-пакетами распознавалки.
Эталонный тестовый архив — 47 МБ, внутри PDF на 50 МБ и 77 страниц. В будущем добавятся
RVT/NWD/NWC/IFC, которые ещё больше.

## Решение

Бинарные файлы хранятся только в S3-совместимом объектном хранилище. В PostgreSQL — исключительно
метаданные: имя, размер, MIME, SHA-256, ключ объекта.

Доступ к хранилищу идёт через протокол `ObjectStorage` (`apps/api/app/storage/base.py`).
Реализация на Stage 1 одна — S3 (`aioboto3`), локально за ней MinIO из `infra/docker-compose.yml`.
Целевая продовая площадка — Yandex Object Storage: тот же S3-протокол, меняются только
endpoint и креды из окружения.

Правила, обязательные для всех будущих операций:

- загрузка и выгрузка потоковые, с ограниченным потреблением памяти; никакого base64 в JSON;
- ключ объекта строится из UUID, а не из имени файла — имя сохраняется отдельным полем
  метаданных и может содержать кириллицу и пробелы;
- отдача больших файлов браузеру — через presigned URL, а не проксированием через API;
- SHA-256 считается потоково при приёме файла.

## Последствия

- Резервное копирование состоит из двух частей: дамп PostgreSQL и бакет. Это учитывается
  в эксплуатационной документации.
- Локальная разработка требует запущенного Docker (MinIO). Проверка доступности бакета
  входит в `/health/ready`.
- Смена площадки на Yandex Cloud не затрагивает бизнес-код: правятся переменные окружения.

## Отвергнутые альтернативы

- **BYTEA/Large Objects в PostgreSQL.** Раздувает базу и дампы, ломает потоковую отдачу,
  прямо запрещено требованиями Stage 1.
- **Локальная файловая система.** Работает на одной машине и не переносится в облако.
- **Supabase Storage.** Рассматривался как готовая площадка, но добавляет привязку к платформе
  там, где достаточно чистого S3, и хуже сочетается с планом переезда в Yandex Cloud.
