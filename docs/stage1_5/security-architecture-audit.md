# Аудит безопасности и архитектуры перед Stage 1.5

Дата: 2026-09-07. Аудит read-only: runtime-код при его составлении не изменялся.

Задача — зафиксировать фактическое состояние портала перед тем, как в него войдут
аутентификация, разграничение доступа и административный контур. Всё, что ниже, проверено
чтением кода и запуском, а не выведено из документации этапа.

## Как измерено

| Величина                  | Значение                                                           | Чем получено               |
| ------------------------- | ------------------------------------------------------------------ | -------------------------- |
| Операций в OpenAPI        | 21 (19 в `/api/v1`, 2 в `/health`)                                 | `create_app().openapi()`   |
| Тестов pytest             | 246 собрано                                                        | `pytest --collect-only -q` |
| Сценариев Playwright      | 23 (`smoke` 15, `mobile` 8), размножаются по разрешениям           | `grep -c "test("`          |
| Таблиц в БД               | 7                                                                  | `Base.metadata`            |
| Головная ревизия миграций | `0002_project_source`                                              | `alembic/versions/`        |
| Версии бэкенда            | FastAPI 0.141.1, Pydantic 2.13.5, SQLAlchemy 2.0.52, Python 3.12.8 | импорт в venv              |
| Версии фронтенда          | Next 16.3.4, React 19.2.8, Tailwind 4.3.3                          | `apps/web/package.json`    |

поднят, 79 тестов базы данных пропускаются. Отражено в разделе «Что не проверено».

## 1. Бэкенд

### 1.1 Каркас и цепочка middleware

`app/main.py::create_app` собирает приложение в таком порядке:

```text
CORSMiddleware              (добавлен последним → внешний)
  RequestContextMiddleware  (X-Request-ID, access-лог)
    обработчики ошибок      (DomainError, отказ БД, отказ хранилища)
      health.router  +  api_v1_router (/api/v1)
```

Существенное для Stage 1.5: **аутентифицирующего слоя в цепочке нет вообще**, и его место —
не middleware, а зависимость маршрутизатора. Middleware не умеет отличать публичный маршрут
от защищённого, не участвует в OpenAPI и не подменяется в тестах.

`generate_unique_id_function=operation_id` возвращает `route.name`, поэтому **имена
обработчиков обязаны быть уникальны в пределах приложения**. При добавлении админского
контура это начинает жать: `list_projects` в портале и в админке не могут называться
одинаково.

Приложение обязано импортироваться без живой БД и хранилища (`get_engine` — ленивый
`lru_cache`). На этом держатся офлайн-выгрузка OpenAPI и тесты оболочки в CI. Любая
аутентификация обязана сохранить это свойство.

### 1.2 Откуда берётся `workspace_id`

`app/core/workspace.py` — 33 строки, и в них весь текущий контроль доступа:

```python
DEV_WORKSPACE_ID = uuid.UUID("00000000-0000-4000-8000-000000000001")

def get_workspace_context() -> WorkspaceContext:
    return WorkspaceContext(workspace_id=DEV_WORKSPACE_ID, is_dev_mode=True)
```

Значение константно, в базу не ходит, ни от чего не зависит. `WorkspaceDep` из
`app/api/v1/deps.py` стоит в **каждом** маршруте `projects`, `documents`, `jobs`,
`uploads`, `integrations`.

Это одновременно главная дыра и главная удача этапа: **менять придётся тело одной функции,
а не двадцать обработчиков.**

### 1.3 Эндпоинты и фильтрация по рабочему пространству

Все 19 операций `/api/v1` и обе проверки здоровья доступны без каких-либо учётных данных.

Фильтрация по `workspace_id` при этом сделана добросовестно и уровнем ниже маршрутов:

- `projects.py` — `_scoped(workspace_id)` в основе каждой выборки;
- `documents.py` — `get_document`, `get_revision`, `get_sheet` соединяются с `projects` и
  фильтруют по `Project.workspace_id`;
- `jobs.py` — `get_job` требует либо `project_id is null`, либо совпадения пространства.

Отдельно проверено место, которое выглядит подозрительно: `list_documents` и
`count_documents` принимают голый `project_id` без пространства. Но оба вызова в
`projects.py` идут **после** `get_project(workspace_id=…)` и используют `project.id`,
а не параметр пути. Граница не течёт.

**Вывод:** объектная проверка доступа не потребует переписывания выборок. Требуется
подставить в `workspace_id` подлинное значение и добавить проверку прав.

### 1.4 CORS, cookies, заголовки, presigned-ссылки

- CORS: `allow_origins` из `API_CORS_ORIGINS` (список, не `*`), `allow_credentials=True`,
  методы и заголовки `*`, наружу отдаётся `X-Request-ID`. Для будущей cookie-сессии
  конфигурация уже пригодна.
- Cookies: **не используются нигде**. Сессии нет.
- Заголовков аутентификации нет. `X-API-Key` живёт только в исходящих запросах к TenderHUB.
- Presigned-ссылка (`GET /revisions/{id}/content-url`) выдаётся на
  `content_url_ttl_seconds` (по умолчанию 3600 с). Ссылка — предъявительский мандат: кто ею
  владеет, тот час читает файл в обход портала. Сегодня её получает кто угодно; после
  Stage 1.5 — только прошедший проверку прав, но сама ссылка остаётся предъявительской,
  и это надо назвать вслух, а не считать закрытым вопросом.

### 1.5 Флаги возможностей

`app/core/features.py`: два кортежа (`STAGE1_FEATURES`, `STAGE2_FEATURES`), `DEFAULTS` как
`MappingProxyType`, `parse_overrides` и `resolve(raw, *, tenderhub_configured)`. Источник
переопределений — переменная окружения `FEATURE_FLAGS`. Персистентности, пространств и
записи через API нет. Отдаются в `GET /api/v1/meta`.

Принцип этапа сформулирован в самом модуле и его стоит сохранить дословно: «включение флага
не создаёт функциональность, а лишь перестаёт её прятать». `integrations.tenderhub`
намеренно выведен не из флага, а из наличия ключа.

### 1.6 Загрузка конфигурации и секреты

`app/core/config.py` — `pydantic-settings`, `env_file` из корня и из `apps/api`,
`extra="ignore"`. Пароль БД, ключ S3 и ключ TenderHUB — `SecretStr`. `database_url`
собирается свойством, пароль подставляется в одном месте.

Проверка утечки существует и настоящая: `test_health.py` роняет соединение с DSN,
содержащим пароль `hunter2`, и требует, чтобы `hunter2` не встретился в теле ответа.

Хранилища настроек в базе нет — вся конфигурация приходит из окружения. Это ровно та точка,
куда Stage 1.5 добавляет типизированный реестр, **не перенося туда инфраструктурные
параметры**.

### 1.7 Интеграция с TenderHUB и модель её отказов

`app/integrations/tenderhub.py` (см. [ADR-0011](../adr/0011-integraciya-s-tenderhub.md)):
ключ уходит единственным заголовком `X-API-Key`, только на чтение, из портала наружу не
попадает; в лог пишутся адрес и код ответа. Отказы внешней системы разложены на семь
отдельных кодов (`TENDERHUB_AUTH_FAILED`, `…_RATE_LIMITED`, `…_UNAVAILABLE` и прочие),
а не слиты в общий «сервис недоступен».

Каноническая связь проекта с тендером уже существует: `source`, `external_id`,
`external_ref` и уникальность `(workspace_id, source, external_id)`. `ProjectUpdate`
принимает только `name` и `status`, поэтому **обычное редактирование проекта не способно
перепривязать тендер уже сейчас**. Не хватает не запрета, а закрепляющего теста и
привилегированной операции rebind/unlink с записью в журнал.

### 1.8 Генерация OpenAPI

`app/openapi_export.py` выгружает схему офлайн в `packages/api-client/openapi.json`,
`scripts/gen-api-client.mjs` генерирует TypeScript-клиент, задание CI «Контракт API»
падает при расхождении. Ручных DTO на TypeScript нет.

**Находка, важная для реализации deny-by-default.** В FastAPI 0.141 включённые
маршрутизаторы больше не расплющиваются в `app.routes`: там лежат три служебных маршрута
документации и два объекта `_IncludedRouter`. Тест «у каждой операции объявлено право»
обязан обходить `app.openapi()["paths"]` либо рекурсивно спускаться в
`_IncludedRouter.router.routes`. Наивный `for route in app.routes` пройдёт по трём
маршрутам, ничего не найдёт и будет зелёным — то есть даст ровно то ложное чувство защиты,
ради борьбы с которым его и пишут.

### 1.9 Задания и их исполнитель

`Job` в базе — единственный источник правды ([ADR-0005](../adr/0005-abstrakciya-zadanij.md)).
Исполнитель — фоновая задача внутри процесса API: `schedule_legacy_import` создаёт
`asyncio.Task`, ссылки держатся в модульном множестве `_running`.

Разделение уже правильное: тело задания `execute_legacy_import(session, job, *, storage,
settings)` отделено от диспетчера и принимает хранилище и настройки аргументами. Вынос в
отдельный процесс заменяет диспетчер, не трогая тело.

Чего нет для отдельного исполнителя: счётчика попыток, аренды и пульса, идентификатора
воркера, времени доступности для повтора. `Job.created_at` ставит приложение, а не БД
(осознанно, зафиксировано в ограничениях этапа) — значит времена аренды обязаны приходить
из часов базы, иначе два процесса дадут два времени.

### 1.10 Логи и модель ошибок

`structlog`, сквозной `X-Request-ID` (принимается клиентский либо генерируется), access-лог
с методом, путём, кодом и длительностью. Тела запросов и ответов не логируются.

Ошибки: `ErrorCode` (StrEnum) и два параллельных словаря — `MESSAGES` и `STATUS_CODES` —
плюс `DomainError`. Наружу уходит `{"detail": {"code", "message"}}`; подробности остаются
в логах. Обработчики отказа БД и хранилища превращают исключение драйвера в 503 со
стабильным кодом.

`test_errors.py` перебирает **все** члены `ErrorCode`, поэтому новый код без сообщения или
без статуса роняет сборку. Забыть половину контракта не получится.

Кодов 401/403 не существует — их предстоит добавить.

### 1.11 Миграции и транзакции

Две ревизии, `0001_domain_stage1` → `0002_project_source`. CI прогоняет `upgrade head`,
`alembic check` и `downgrade base`, поэтому необратимая миграция сборку не пройдёт.

Транзакции: `get_session` даёт сессию на запрос с откатом при исключении; фиксация — явная
в обработчике. Задание выполняется в собственной сессии, потому что сессия запроса
закрывается раньше, чем работа заканчивается.

## 2. Фронтенд

### 2.1 Фактическая версия и структура

Next **16.3.4**, React 19.2.8, App Router, Tailwind v4 **без файла конфигурации** — токены
объявлены прямо в `apps/web/src/app/globals.css` через `@theme inline`.

```text
src/app/layout.tsx           ThemeScript, Providers, ServiceWorkerBridge
src/app/(portal)/layout.tsx  SideNav + BottomNav
src/app/(portal)/projects/…  список, создание, карточка, рабочая область
src/app/(portal)/settings/   страница возможностей
```

Маршрута `/admin` нет, маршрутов входа нет, `middleware.ts` нет.

### 2.2 Клиент API и обёртка аутентификации

Обёртки аутентификации не существует. Клиент — сгенерированный `@quantor/api-client`;
единственный рукописный файл в пакете, `packages/api-client/runtime.ts`, задаёт базовый
адрес.

**Находка.** В `createClientConfig` нет `credentials`. API живёт на другом origin (`:8000`
против `:3000`), поэтому cookie-сессия по умолчанию **не будет отправлена**, и
аутентификация «не заработает» без единой ошибки в коде. Правка — одна строка в рукописном
файле, шлюза дрейфа контракта она не касается.

Все обращения собраны в `src/lib/queries.ts` (хуки `useMeta`, `useFeatures`, `useProjects`,
…); мутации живут в компонентах диалогов. Единая точка для перехвата 401 есть — это
`QueryClient` в `src/app/providers.tsx`.

### 2.3 PWA и service worker

`apps/web/public/sw.js` осознанно минимален и **уже безопасен** для Stage 1.5:

- `/api/` не кэшируется никогда;
- чужой origin пропускается без вмешательства (а API как раз чужой origin);
- кэшируется только `/_next/static/` — файлы с хешем в имени;
- обновление по запросу, без молчаливого `skipWaiting`.

Требование приёмки «service worker не кэширует привилегированные ответы» закрывается
регрессионным тестом, а не переделкой.

### 2.4 Дизайн-система и где админка может делить компоненты

Токены — CSS-переменные в `globals.css`, тёмная тема через `data-theme` и
`prefers-color-scheme`, хардкод цветов в компонентах запрещён и по факту отсутствует.
Примитивы — `src/components/ui/index.tsx` (`cx`, `Button`, `SearchInput`, `StatusBadge`,
`ProgressRow`, `EmptyState`, `ErrorState`, `Skeleton`, `Field`).

[ADR-0001](../adr/0001-granicy-monorepozitoriya.md) **уже разрешил** нужный шаг заранее:
«Общий пакет UI-примитивов (`packages/ui`) не создаётся, пока примитивы нужны одному
приложению. Появится второй потребитель — появится и пакет.» Второй потребитель появляется,
значит извлечение пакета исполняет действующее решение, а не отменяет его.

Практическая деталь: `@/components/ui` импортируют 20 файлов. Извлекать надо переносом с
оставлением реэкспортирующего модуля на прежнем месте — иначе получится диф на 20 файлов
ради нулевого изменения поведения. `pnpm-workspace.yaml` уже содержит глоб `packages/*`,
так что для нового пакета правок в нём не нужно.

Тот же ADR-0001 запрещает создавать `apps/worker` как пустой каркас. Отдельный процесс
исполнения заданий это решение **не нарушает**: он остаётся вторым входом в `apps/api`
(`python -m app.worker`), а не новым приложением.

## 3. Тесты и CI

- **Тестов аутентификации и авторизации нет ни одного** — их нечего проверять.
- Проверка утечки секретов существует и работает (`hunter2` в `test_health.py`).
- Шлюз дрейфа контракта — задание `contract`, `pnpm api-client:check`.
- Playwright настроен, браузеры установлены, 23 сценария на нескольких разрешениях,
  включая WebKit.
- Настоящий PostgreSQL есть в CI (`postgis/postgis:17-3.5`); MinIO в тестах подменяется
  хранилищем в памяти, контракт которого проверяется отдельно (`test_storage_contract.py`).
- Пропуск тестов базы данных в CI считается ошибкой сборки — задание грепает вывод pytest.
- Скриптов развёртывания нет: есть команды разработчика в корневом `package.json`.

### Ограничения тестового стенда, задающие форму реализации

Три существующих теста жёстко ограничивают то, как можно сделать аутентификацию:

1. `test_errors.py::test_unreachable_database_returns_503_with_stable_code` — при сломанной
   сессии `/api/v1/projects` обязан отдать **503, а не 401**. Значит проверка учётных
   данных в dev-режиме не должна ходить в базу.
2. `test_performance.py::test_sheet_list_does_not_grow_with_sheets` — не более четырёх
   запросов при текущих трёх. Значит аутентификация в тестах добавляет **ноль** запросов.
3. `test_meta.py` работает на фикстуре `client` **без базы**, а в CI база `quantor` не
   мигрируется вовсе (тесты создают `quantor_test` из метаданных). Значит `/api/v1/meta`
   обязан деградировать до кодовых умолчаний, когда таблиц флагов нет. Это требование
   контракта, а не перестраховка.

Отдельно: фикстура `db_session` после каждого теста делает `truncate … cascade` по всем
таблицам, а тестовая база создаётся через `Base.metadata.create_all`, а не Alembic. Значит
строка рабочего пространства, вставляемая миграцией, в тестах не появится, и после
добавления внешнего ключа на `projects.workspace_id` **упадут все 79 тестов базы данных**,
пока фикстура `workspace_id` не начнёт эту строку создавать.

| 11  | Утечка presigned-ссылки                                 | Ссылка выдаётся кому угодно на час                         | Выдавать только после проверки прав. Ссылка остаётся предъявительской — сократить срок жизни до нужд просмотрщика и признать остаточный риск                                    |
| 12  | Подделка журнала аудита                                 | Журнала нет                                                | Таблица без операций изменения и удаления в API **и** триггер базы, запрещающий `update`/`delete`                                                                               |

Две угрозы вне списка промта, всплывшие при аудите:

- **Порядок решения зависимостей.** Если проверка учётных данных окажется после
  `SessionDep`, недоступная база начнёт отвечать 401 вместо 503, и диагностика уйдёт в
  ложную сторону: пойдут чинить вход вместо базы. Зависимость аутентификации должна
  решаться раньше сессии.
- **Первый администратор.** Появление ролей создаёт задачу «кто выдаст права первому».
  Решать её миграцией с зашитым идентификатором нельзя; нужен явный список из окружения,
  срабатывающий при первом входе и попадающий в журнал.

## 5. Что не проверено

- Живой стенд не поднимался: Docker на машине разработки не запущен, 79 тестов базы данных
  пропущены. Утверждения о поведении с настоящей базой основаны на чтении кода.
- Нагрузочные измерения не делались — они относятся к промту 11 и требуют стенда.
- Поведение presigned-ссылки против настоящего MinIO не перепроверялось.
