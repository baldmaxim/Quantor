# Приёмка Stage 1.5

Дата: 2026-09-08.

Отчёт разделён на две части, и это разделение — главное в нём. Всё, что помечено
«измерено», получено запуском; всё остальное названо неизмеренным прямо, без округления
в свою пользу. Отчёт, в котором не отличить одно от другого, хуже отсутствующего:
по нему принимают решение о выставлении портала наружу.

## Матрица безопасности

Двенадцать пунктов промта 11. Автоматические проверки собраны в
[test_security_matrix.py](../../apps/api/tests/test_security_matrix.py) — в одном файле
намеренно: приёмка отвечает на один вопрос целиком, а не по крупицам из двадцати файлов.

| #   | Требование                                       | Как проверено                                                        | Итог     |
| --- | ------------------------------------------------ | -------------------------------------------------------------------- | -------- |
| 1   | Неаутентифицированный не читает проекты          | `GET /api/v1/projects` без учётных данных → 401 + `WWW-Authenticate` | **PASS** |

| 3   | Инженер не администратор                         | состав `ROLE_PERMISSIONS[engineer]`                                  | **PASS** |
| 4   | Администратор пространства не выходит за границу | чужой проект → 404                                                   | **PASS** |
| 5   | Доступ администратора платформы явный            | без заголовка → 404, с заголовком → 200                              | **PASS** |
| 6   | Угаданный UUID не пробивает границу              | три маршрута чужого проекта → 404 с кодом `NOT_FOUND`                | **PASS** |
| 7   | Ссылка на файл подчиняется границе               | `content-url` чужой ревизии → 404                                    | **PASS** |
| 8   | Административный API запрещает по умолчанию      | перебор всех операций контракта: у каждой объявлено право            | **PASS** |
| 9   | Секрет не попадает в контракт, ответ и бандл     | поиск по именам полей в OpenAPI и в сгенерированном клиенте          | **PASS** |
| 10  | Разрушительное действие в журнале                | изменение настройки оставляет запись с актором                       | **PASS** |
| 11  | Service worker не кэширует привилегированное     | `/api/` и чужой origin пропускаются; у админки SW нет вовсе          | **PASS** |
| 12  | Выход обесценивает сеанс                         | после `revoke` токен не разрешается                                  | **PASS** |

Пункт 9 проверяет **имена полей**, а не значения: значение может быть пустым на одной
машине и заполненным на другой, а поле с таким именем опасно само по себе.

Пункт 11 проверяет исходник service worker, а не поведение браузера. Правило простое —
`/api/` не кэшируется никогда, — и прогон в настоящем браузере проверял бы браузер,
а не наше решение.

## Известные ограничения этапа

- **Presigned-ссылка остаётся предъявительской.** Выдаётся только после проверки прав,
  но выданная живёт свой срок независимо от сеанса. Сокращение срока жизни до нужд
  просмотрщика — открытый вопрос.
- **Управления пространствами и пользователями из админки нет.** Разрешения заведены,
  разделы объявлены, API управления доступом появится отдельно; сейчас членство
  заводится в базе.
- **Поставщики моделей только читаются.** Описываются развёртыванием; управление
  появится вместе со шлюзом на Stage 2, когда будет чем управлять.
- **Совместной отмены выполняющегося задания нет.** Отменяется только ожидающее:
  прерывать импорт на середине нечем.
- **Кэш диагностики межпроцессный не заводился.** При нескольких процессах API каждый
  считает состояние сам; на текущих объёмах это дешевле, чем согласовывать кэш.

## Живой прогон выноса заданий

Главный вопрос этапа — выполняется ли импорт вне процесса API — проверяется одним
наблюдением, и оно сделано на стенде 2026-09-08. В потоке `worker`, а не `api`:

```
worker | job_claimed job_id=… job_type=legacy_import attempt=1
worker | legacy_import_finished sheets=77 regions=383
```

Строка `job_claimed` в потоке `api` означала бы, что вынос не работает, — и это
единственный способ отличить настоящий отдельный исполнитель от переименованного
внутреннего вызова. В админке задание показано выполненным, попытка `1 из 1`,
«Повторить» заблокирован; `Исполнитель заданий` — «в порядке», источник
«сообщено процессом». Числа листов и областей совпали с показателями до этапа.

## Дефекты, найденные приёмкой на стенде

Шесть дефектов поймались только запуском, и ни один из них офлайн-проверка поймать
не могла. Первые четыре — поведение драйвера и сессии на живой базе; пятый и шестой
нашлись сквозным прогоном на настоящем пакете:

1. `asyncpg` не принимает несколько команд в одном запросе — триггер журнала не ставился;
2. `SET search_path` открывал транзакцию, и откат миграций коммитил только savepoint;
3. повторный именованный аргумент в тестовом помощнике;
4. устаревший статус задания после сырого `UPDATE` — `session.get` отдавал объект из
   identity map;
5. повторный `start()` после `claim()`. Захват уже переводит задание в `running`, а тело
   задания вызывает `start()` ради стадии — автомат состояний запрещал переход
   `running -> running` и валил импорт. `start` сделан идемпотентным. Заодно из текста
   ошибки убрана стрелка «→»: в логе Windows (cp1251) она роняла процесс исполнителя
   ровно в тот момент, когда он сообщал о падении задания;
6. `PDF_RENDER_FAILED` при открытии листа. Первая вписка листа и перерисовка после зума
   шли параллельно, каждая со своим `AbortController`, и обе звали `render()` на одном
   холсте: pdf.js 6 на это отвечает отказом. Отрисовка сведена в одну очередь, вызов
   приведён к контракту pdf.js 6 (только `canvas`, без `canvasContext`).

Вывод для Stage 2, записанный здесь намеренно: **код, работающий с базой, проверяется
только базой.** Офлайн-сверка DDL с моделями полезна, но подтверждает структуру, а не
поведение драйвера.

Пятый и шестой добавляют второй вывод, отдельный от первого: **стык двух исполнителей
проверяется только запуском обоих.** Захват задания и его выполнение, первая вписка листа
и перерисовка по зуму — в каждой паре обе стороны были покрыты тестами и по отдельности
верны. Несовместимыми они оказались там, где начинают работать одновременно. Причём в
пятом случае убийственной была не сама ошибка, а то, что сообщение о ней роняло
исполнителя раньше, чем успевало быть записанным.

Оба дефекта закрыты не только исправлением, но и проверкой, которая падает без него:
`test_jobs_service.py` — повторным `start()` после `claim()`, `DrawingViewport.test.tsx` —
отрисовщиком, который не завершается сам, и требованием, чтобы живых задач на холсте
никогда не было больше одной. Второй проверен обратным прогоном: на коде до исправления
он показывает две.
