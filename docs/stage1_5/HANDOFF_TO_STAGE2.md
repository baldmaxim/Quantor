# Передача Stage 1.5 → Stage 2

Дата: 2026-09-08.

Stage 1.5 закрывал одно: сделать платформу управляемой и безопасной **до** того, как на
неё придёт тяжёлый QTO. Главное ограничение Stage 1 — «аутентификации нет, `workspace_id`
фиксирован, наружу выставлять нельзя» — снято.

QTO- и AI-функциональность не появилась и не должна была: подсчёт, масштаб, инференс,
ВОР остаются за Stage 2.

## 2. Поток входа

```text
браузер → GET /api/v1/auth/login?next=…
        → 307 на провайдера (Authorization Code + PKCE, state и nonce в короткой cookie)
        → провайдер → GET /api/v1/auth/callback?code=…&state=…
        → сервер меняет код на токены, проверяет id_token по JWKS
        → JIT-создание UserIdentity по паре (issuer, subject)
        → строка в auth_sessions, cookie quantor_session (HttpOnly) + quantor_csrf
        → 307 обратно в портал
```

Токены провайдера в браузер не попадают. Сеанс — строка в базе, а не самодостаточный
токен: только так выход действительно обесценивает сеанс.

Машинные клиенты ходят с `Authorization: Bearer` и проверяются по JWKS того же провайдера;
алгоритмы ограничены подписью открытым ключом.

## 3. Роли и разрешения

Бизнес-код проверяет **разрешение**, не имя роли. Состав меняется в
`app/auth/permissions.py`, обработчики не трогаются.

| Роль              | Уровень      | Что даёт                                                         |
| ----------------- | ------------ | ---------------------------------------------------------------- |
| `platform_admin`  | платформа    | все 21 разрешение                                                |
| `service`         | платформа    | только чтение: пространство, проекты, документы, задания         |
| `workspace_admin` | пространство | всё в своём пространстве, кроме `system.admin` и `models.manage` |
| `engineer`        | пространство | создание и изменение проектов, загрузка документов               |
| `reviewer`        | пространство | чтение плюс задания, интеграции, настройки                       |
| `viewer`          | пространство | чтение проектов и документов                                     |

Системный уровень переопределения настроек и флагов дополнительно требует `system.admin`:
иначе арендатор менял бы поведение всей установки.

## 4. Изоляция пространств

`Project.workspace_id` — внешний ключ на `workspaces` с `RESTRICT`. Все выборки документов,
ревизий, листов, областей и заданий соединяются с `projects` и фильтруются по пространству;
это было верно ещё в Stage 1 и не потребовало переписывания.

Политика ответов зафиксирована и проверена: **401** — не знаю, кто; **403** — знаю, но
нельзя; **404** — в твоём пространстве такого нет. Третий случай важнее прочих: 403 на
чужой объект подтверждал бы его существование.

Администратор платформы входит в чужое пространство только заголовком `X-Workspace-Id` —
намеренным действием, а не молча.

## 6. Реестр настроек и порядок старшинства

```text
умолчание кода  <  системное  <  пространство  <  переменная окружения
```

Последняя ступень — аварийный рычаг на случай, когда неудачное значение в базе положило
портал и добраться до админки нельзя. Из интерфейса она только читается.

Определения живут в коде; база хранит проверенное значение и его происхождение.
Инфраструктурные параметры сюда не переезжают — тест следит, чтобы ключ реестра не совпал
с полем `Settings`.

Настроек три, у каждой настоящее место чтения: предел размера загрузки, время жизни ссылки
на файл, порядок списка проектов по умолчанию.

## 7. Флаги возможностей

Тот же порядок старшинства. Принцип Stage 1 сохранён дословно: **включение флага не
создаёт функциональность**. Отсюда два следствия, закреплённые кодом:

- незавершённые возможности Stage 2 имеют `admin_editable=false` и из админки не
  включаются вовсе;
- `integrations.tenderhub` выводится из наличия ключа и не включается переопределением.

Вычисление оформлено провайдер-нейтрально (форма, близкая к OpenFeature), но внешнего
сервиса нет. Межпроцессного кэша нет намеренно: источник правды один, и переопределение
действует со следующего запроса в любом процессе.

## 8. Канонические связи TenderHUB

```text
source = tenderhub
external_id = идентификатор тендера       ← каноническая связь
external_ref = номер тендера
name = каноническое название из внешней системы
local_alias = местное имя, заданное в портале
```

Обычное переименование проекта пишется в `local_alias`: каноническое название принадлежит
внешней системе, и затирать его молча нельзя. `ProjectUpdate` полей связи не принимает.

Перепривязка и отвязка — привилегированные операции с предпросмотром, обнаружением
конфликта, обязательным подтверждением и записью в журнал `old → new`. Данные проекта
не трогаются.

## 9. Контракты поставщиков моделей

`app/contracts/models.py`: `ProviderKind`, `DataPolicy`, `Capability`, `CredentialRef`,
`EndpointSpec`, `ModelSpec`, `ProviderSpec`, `ProviderHealthReport`.

Реестр читается из `MODEL_PROVIDERS` — описывается развёртыванием, а не заводится из
админки. У `CredentialRef` два поля: имя переменной окружения и признак «задана».
Поля под значение секрета не существует.

**Ни одного вызова модели.** Проверка связи щупает доступность адреса и выполняется
по кнопке; открытие страницы к моделям не обращается, и это проверяется тестом,
роняющим любой сетевой вызов.

## 10. Исполнение заданий

```text
uvicorn app.main:app     # API
python -m app.worker     # исполнитель
```

Очередь — сама таблица `jobs`, захват — `FOR UPDATE SKIP LOCKED`. Владение держится
арендой с пульсом, а не блокировкой строки. Все времена владения — из часов базы.

Отдельная таблица `workers` разводит «заданий нет» и «брать их некому».

Повтор доступен только для отказов, которые имеет смысл повторять, и возвращает то же
задание в очередь. Отмена — только для ожидающего.

Прежнее поведение сохранено под `JOB_EXECUTOR=inline`.

## 11. Журнал действий

Только добавление, на двух уровнях сразу: в API нет ни одной операции изменения, база
отвергает `update` и `delete` триггером. Внешних ключей нет намеренно — журнал переживает
удаление того, о чём рассказывает; актор продублирован текстом.

Секреты вычищаются **на записи**: вычищенное на чтении уже лежит в базе и в резервной
копии.

## 12. Диагностика

`GET /api/v1/admin/diagnostics`, только `system.admin`. Восемь проб: API, база, схема,
хранилище, исполнитель, TenderHUB, провайдер входа, реестр моделей.

У каждой пробы свой предел времени и сверх того общий бюджет страницы. Состояния:
`healthy`, `degraded`, `unavailable`, `not_configured`, `unknown` — и последние два
не превращаются ни в «в порядке», ни в ноль.

`/health/live` остался минимальным и публичным. `/health/ready` разделил компоненты на
обязательные и необязательные: мёртвый исполнитель даёт `degraded` с кодом 200.

## 14. Изменения API

Операций стало 46 против 21 на входе в этап. Публичные контракты Stage 1 не ломались:

## 16. Измерения

Что измерено — в [отчёте приёмки](acceptance-report.md). Что не измерено, названо там же
прочерком: первая загрузка страниц, пагинация журнала на тысяче записей, живой импорт

## 17. Нерешённое

- **Presigned-ссылка остаётся предъявительской.** Выдаётся после проверки прав, но живёт
  свой срок независимо от сеанса.
- **Управления доступом из админки нет.** Разрешения заведены, разделы объявлены, API
  ещё нет: членство заводится в базе.
- **MFA портал не реализует.** Требование к политике IdP, записано в ADR-0012.
- **Совместной отмены выполняющегося задания нет.**
- **Первый администратор** назначается переменной окружения при первом входе.
- **Пакет распознавания v2 и двойное хранение PDF** — вопросы, оставшиеся с Stage 1.
