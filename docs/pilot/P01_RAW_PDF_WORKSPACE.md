# Промт 01 — рабочая область для обычного PDF

Дата: 2026-09-21. Базовая точка: коммит `9ba4bea` (принятый итог промта 00).

Обычный PDF с готовой геометрией теперь открывается в рабочей области без распознанного
пакета. Решение об открываемости вынесено в один предикат, выбор документа и ревизии стал
определённым, а распознавание окончательно отделено от просмотра.

## Итог

```text
Гейт P01              PASS
Регрессий             0
Живая приёмка         выполнена на уровне API (реальные PostgreSQL и MinIO)
Не покрыто живьём     браузер на реальной загрузке — ENV_BLOCKED по памяти машины
```

## 1. В чём была ошибка

Карточка проекта считала ревизию открываемой по `processing_status === 'ready'`, а у обычного
PDF этот статус по устройству навсегда остаётся `unprocessed`
(`apps/api/app/models/document.py:83-86`). Кнопка не включалась никогда.

Сверх того, ревизии запрашивались только у **первого** подходящего документа
(`documents.items.find(isRenderable)`), поэтому готовый второй документ терялся, а выбор
ревизии зависел от порядка выдачи.

## 2. Предикат открываемости

Новый модуль `apps/web/src/lib/openability.ts` — единственное место, где принимается это
решение. Состояния разделены, а не свёрнуты в булево:

| Состояние         | Когда                                        | Что видит пользователь         |
| ----------------- | -------------------------------------------- | ------------------------------ |
| `openable`        | PDF, геометрия не в работе, листы есть       | действие «Открыть»             |
| `preparing`       | `geometry_status` = `pending` / `extracting` | «Подготавливаем листы»         |
| `geometry_failed` | `geometry_status` = `failed`                 | причина и код ошибки           |
| `no_sheets`       | листов нет                                   | открывать нечего               |
| `not_viewable`    | документ не PDF                              | ни состояния листов, ни кнопки |

`processing_status` в предикате не участвует. Распознавание — независимый слой (ADR-0016), и
на открытие чертежа не влияет ни в какую сторону.

Отдельная ветка — `geometry_status = not_applicable` при непустом списке листов: это ревизия
из пакета, импортированного до появления извлечения геометрии. Её листы существуют, показать
её можно, и прежний сценарий распознанного пакета не ломается.

## 3. Листы стали видимой частью контракта

Условие «листы есть» клиент проверить не мог: в `DocumentRevisionRead` не было ничего про
листы. Добавлено поле `sheet_count` (`apps/api/app/schemas.py`), которое считается одним
подзапросом вместе со списком ревизий (`RevisionWithCount` в
`apps/api/app/services/documents.py`) — по образцу уже существовавшего `SheetWithCount`.

Иначе карточке пришлось бы запрашивать листы каждой ревизии по очереди только ради того,
чтобы решить, рисовать ли кнопку.

Затронуты три места, отдающие ревизию: список, одиночное чтение и ответ загрузки. Клиент
`packages/api-client` перегенерирован (`pnpm api-client:generate`), вручную не правился.

## 4. Определённый выбор документа и ревизии

- **Ревизия документа.** `latestOpenableRevision` идёт от конца списка к началу. Опора —
  гарантия API: `list_revisions` сортирует по `created_at`, затем по идентификатору. Гарантия
  закреплена тестом `test_revisions_are_listed_from_oldest_to_newest`, где порядок вставки
  нарочно не совпадает с порядком времени. Повторной сортировки на клиенте нет.
- **Верхняя кнопка.** `chooseOpenTarget` берёт самую свежую открываемую ревизию проекта, при
  совпадении времени — наибольший идентификатор. Результат не зависит от порядка списка;
  тест прогоняет оба порядка документов и ожидает один и тот же ответ.
- **Каждый документ.** У строки документа своё действие «Открыть» с именем документа в
  `aria-label`. Ревизии всех документов запрашиваются одним `useQueries` по тем же ключам,
  поэтому заголовок страницы и строки читают один кеш, а не два.

Пока листы готовятся, список ревизий опрашивается раз в 2 с: иначе «Подготавливаем листы»
висело бы до ручной перезагрузки.

## 5. Распознавание необязательно

Вкладка «Распознавание» при пустом списке областей показывает одно честное объяснение:

> Для этого PDF нет импортированной разметки распознавания. Просмотр и ручной обмер работают
> и без неё.

Это не ошибка и не требование загрузить пакет. Прежний текст кнопки «Нужен распознанный PDF:
загрузите пакет и дождитесь импорта» удалён; на карточке проекта слова «распознанный пакет»
остались только там, где речь действительно о пакете.

## 6. Права не расширялись

Серверные проверки не менялись: все эндпоинты документов остались под
`require(Permission.DOCUMENT_READ)` с выборкой по `workspace_id`. Новое поле `sheet_count`
считается внутри той же уже проверенной выборки. Тесты `TestCrossProjectAccess` не менялись и
проходят.

зелёная — расхождение ровно в одном добавленном поле.

### Новые тесты

Сервер (`apps/api/tests/test_api_documents.py`, класс `TestOpenability`):

- `sheet_count` приходит и в списке ревизий, и в одиночном чтении;
- обычный PDF открываем при `processing_status=unprocessed` и `geometry_status=ready`;
- ревизия без геометрии честно показывает 0 листов;
- ревизии выдаются от старой к новой при перепутанном порядке вставки.

Клиент: `openability.test.ts` (17 проверок предиката и выбора цели) и
`DocumentRow.test.tsx` (6 проверок строки документа).

Браузер (`apps/web/e2e/smoke.spec.ts`, раздел «карточка проекта», прогон на собранном
приложении): нераспознанный PDF с готовыми листами даёт рабочую ссылку и в заголовке, и в
строке документа; при `geometry_status=pending` кнопка неактивна, её подпись объясняет
причину, а текста «Нужен распознанный PDF» на странице нет. Оба сценария зелёные
(`2 passed`).

## 8. Живая приёмка

Выполнена на настоящих службах: PostgreSQL и MinIO (обе в WSL), API `uvicorn` и обработчик
заданий запущены локально, режим входа — `dev`. Документ — синтетический PDF на две страницы,
созданный `pypdf`; клиентские чертежи не использовались.

| Шаг                          | Результат                                                                                 |
| ---------------------------- | ----------------------------------------------------------------------------------------- |
| загрузка обычного PDF        | `document_kind=pdf`, задание `pdf_geometry_extract` поставлено                            |
| сразу после загрузки         | `processing_status=unprocessed`, `geometry_status=pending`, `sheet_count=0`               |
| после отработки задания      | `geometry_status=ready`, `sheet_count=2`, `processing_status` так и остался `unprocessed` |
| листы ревизии                | 2 листа, у каждого `region_count=0`                                                       |
| области первого листа        | `total=0` — разметки нет, и это не ошибка                                                 |
| каноническая геометрия листа | HTTP 200                                                                                  |
| ссылка на файл               | HTTP 206 на Range-запрос — просмотрщик получает то, что ему нужно                         |

То есть сочетание, которое до P01 не открывалось никогда, теперь приходит с сервера в том
виде, на который опирается предикат.

**Что не проверено живьём:** одна связка — этот самый загруженный PDF, открытый браузером
через настоящий API. Браузерная часть проверена отдельно, на собранном приложении с
подменёнными ответами API (раздел 7), а серверная — отдельно, на настоящих службах (таблица
выше). Свести их в один прогон не дала память: на машине оставалось 0,5 ГБ из 16, порт 3000
занят посторонним приложением, и попытка поднять рядом ещё один экземпляр портала уже падала
с `process out of memory`. Помечено `ENV_BLOCKED` и за PASS не выдаётся; снимается
освобождением памяти и порта.

Побочное: в локальной dev-базе остался проект «P01 live acceptance» с синтетическим PDF.
