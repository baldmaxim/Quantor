**Инфраструктура.** Docker не запущен: обращение к `npipe:////./pipe/dockerDesktopLinuxEngine`
не проходит. `pnpm infra:up` не выполнялся — поднятие инфраструктуры меняет состояние машины

падения: §2 промта запрещает трогать БД, пока не доказано, что она локальная dev/test. Снятие
блокировки: `pnpm infra:up`, затем `pnpm db:migrate`.

**Браузерные тесты.** Первый прогон дал стену красного и оказался полностью ложным: Playwright
переиспользовал чужой сервер. Порт 3000 занят посторонним приложением (`node server.js`,
Express, не Quantor), а `reuseExistingServer` вне CI включён — браузер ходил на чужой сервер и
получал `Cannot GET /projects`. Повтор с `WEB_PORT=3100` дал настоящий результат: **web —
53 passed**, **admin — 17 passed**, падений тестов нет.

Три теста (2 в web, 1 в admin) не завершились с подписью
`browserContext.newPage: Target page, context or browser has been closed`, и каждый из них
прошёл на других разрешениях. Причина измерена: на машине свободно **0,7 ГБ из 16**, а
прицельная перепроверка упала ещё раньше — `next build` завершился
`FATAL ERROR: Zone Allocation failed - process out of memory`. Это нехватка памяти на машине, а
не поведение кода; перепроверка остановлена, чтобы не отбирать память дальше. Снятие
блокировки: освободить порт 3000 и память, затем `pnpm test:e2e`.

Побочное: зависший воркер Playwright удерживал `next start` на 3100 и был снят принудительно —
отсюда `ERR_CONNECTION_REFUSED` в хвосте лога. Прогон к тому моменту уже закончился.

## 4. Продуктовые узкие места, подтверждённые кодом

### 4.1. Обычный PDF доходит до `geometry_status=ready`

`apps/api/app/services/geometry/extract.py:143` — единственное во всём коде присвоение
`GeometryStatus.READY`. Тест `test_direct_pdf_creates_its_sheets`
(`apps/api/tests/test_page_geometry.py:245`) проверяет и статус, и то, что листы у прямого PDF
создаются самим извлечением: `sheets_created == 2`, `sheets_enriched == 0`.

**ПОДТВЕРЖДЕНО.**

### 4.2. `processing_status=unprocessed` у обычного PDF — норма

`apps/api/app/services/uploads.py:66-75`: у `RAW_PDF` сразу `processing_status=UNPROCESSED` и
`geometry_status=PENDING`, с комментарием, что это два независимых процесса над одним файлом
(ADR-0016). Тест `test_raw_pdf_schedules_geometry_but_stays_unprocessed`
(`apps/api/tests/test_uploads.py:162`) утверждает то же как продуктовое решение:
`processing_status == "unprocessed"` плюс поставленная задача `pdf_geometry_extract`.

**ПОДТВЕРЖДЕНО.**

### 4.3. Карточка проекта гейтит открытие по `processing_status`

`apps/web/src/app/(portal)/projects/[projectId]/page.tsx:52-54`:

```tsx
const renderableDocument = documents.data?.items.find(isRenderable) ?? null;
const revisions = useDocumentRevisions(renderableDocument?.id ?? null);
const openable = revisions.data?.items.find((revision) => revision.processing_status === 'ready');
```

Фильтр документа сырой PDF пропускает (`isRenderable` — это `document_kind === 'pdf'`,
`apps/web/src/lib/queries.ts:247`), режет именно условие по ревизии. Подпись неактивной кнопки
на `:77` — «Нужен распознанный PDF: загрузите пакет и дождитесь импорта».

Ключевое: `geometry_status` **не используется во фронте ни разу** — ноль вхождений в
`apps/web/src` и `apps/admin/src`, при том что поле отдаётся сервером
(`apps/api/app/schemas.py:497`) и присутствует в сгенерированном клиенте
(`packages/api-client/src/types.gen.ts:670`). Данные до клиента доезжают, клиент их не смотрит.
Это и есть разрыв, который закрывает P01.

**ПОДТВЕРЖДЕНО.**

### 4.4. `takeoff.manual` — пилот, выключен по умолчанию

Реестр `apps/api/app/core/features.py:112-118`: фабрика `_pilot`, то есть `default=False`,
`admin_editable=True`, `workspace_scoped=True`. Сервер закрывает возможность сам:
`require_feature` (`apps/api/app/api/v1/deps.py:86`) висит на роутерах `takeoff.py:43` и
`scale.py:23` целиком — ADR-0023. Тесты `apps/api/tests/test_pilot_flag.py`:
`test_manual_takeoff_is_a_pilot`, `test_every_takeoff_route_checks_the_flag`,
`test_disabled_flag_closes_takeoff_and_scale`, `test_override_reaches_only_its_workspace`.

**ПОДТВЕРЖДЕНО.**

### 4.5. Рабочая область рисует PDF независимо от `Region`

Путь рендера в `apps/web/src/app/(portal)/projects/[projectId]/workspace/page.tsx:94-96` —
`useSheets` + `useContentUrl` → `useDocumentBackend` → pdf.js; `Region` в нём не участвует.
Области распознавания подключаются отдельно (`:128`) и кормят только собственный слой наложения.
Проверок `processing_status` и `geometry_status` на маршруте рабочей области нет ни одной.
Сильнейшее доказательство — тесты: `DrawingViewport.test.tsx` рендерит просмотрщик с
`regions={[]}` в четырёх сценариях, и они зелёные.

Оговорка для P01: реальное предусловие рендера — наличие `Sheet`. У сырого PDF листы появляются
только после `pdf_geometry_extract` (`extract.py:114-131`), поэтому гейт открытия должен
опираться на `geometry_status`, а не просто на наличие файла.

**ПОДТВЕРЖДЕНО.**

### 4.6. MEP MOCK API не является хранилищем реального проекта

`apps/api/app/api/v1/mep.py` — два маршрута, оба `GET` (`:77`, `:87`), весь роутер под
`require_feature("mep_rd_hypothesis_v1")` (`:25`). `apps/api/app/services/mep/scenarios.py`
читает JSON-фикстуры: ноль упоминаний `session`, `AsyncSession`, `commit`, `insert`. MEP-моделей
в `apps/api/app/models/` нет ни одной — таблицы, куда писать, не существует. Хранить реальный
проект здесь не «не принято», а физически негде.

Вывод для P03: реальный ручной MEP-пилот строится рядом, `/mep/experiment` не расширяется.

**ПОДТВЕРЖДЕНО.**

### 4.7. `measurement_metadata` — чистая, никем не занятая точка переиспользования

Колонка есть: `apps/api/app/models/takeoff.py:182-184`, JSONB, `nullable=False`,
`server_default="{}"`. В публичных схемах её нет: ноль вхождений в `apps/api/app/schemas.py`,
ноль в `packages/api-client/src/types.gen.ts`; `MeasurementRead` (`schemas.py:620`) отдаёт
геометрию, происхождение, калибровку и версию — метаданных среди них нет. Записи тоже нет: поле
не упоминается нигде в `apps/api/app`, кроме объявления модели, то есть в базе всегда `{}`.

Наружу контракт этим не сломать — его туда никогда не выводили. P03
(`_prompts/faststart_manual_pilot/03_REAL_MEP_MANUAL_PILOT_FOUNDATION.md`) предлагает
`measurement_metadata.mep_manual_v1` как быстрый путь хранения ручной MEP-разметки. **В P00 поле
не менялось.**

**ПОДТВЕРЖДЕНО.**

## 6. Что блокирует сырой PDF

Единственный блокер — раздел 4.3: клиент требует `processing_status === 'ready'`, а у обычного
PDF этот статус по устройству навсегда остаётся `unprocessed`
(`apps/api/app/models/document.py:83-86`).

Серверных препятствий нет: ни один эндпоинт выдачи листов, ссылки на содержимое, областей и
геометрии страницы не смотрит на `processing_status`. `GET /sheets/{id}/geometry` отвечает 409
`GEOMETRY_NOT_READY`, только если геометрии действительно нет.

Сопутствующее, тоже на P01: устаревшая подпись кнопки; выбор документа по первому найденному
PDF, из-за чего готовый второй документ теряется; отсутствие показа `geometry_status`, в том
числе состояния `failed`.
