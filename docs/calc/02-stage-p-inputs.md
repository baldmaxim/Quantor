# PROMPT 02 — сбор и проверка расчётных исходных данных стадии П

Дата: 2026-09-28. Пакет — [`_prompts/calc_portal_stage_p/`](../../_prompts/calc_portal_stage_p/Quantor_Opus_5.5_Prompts_Calculation_Portal.md),
задание PROMPT 02 — в редакции владельца от 2026-09-28. Решение — [ADR-0030](../adr/0030-raschyotnyj-kontur-stadii-p.md).
Предыдущий шаг — [01-facts-registry.md](01-facts-registry.md).

```text
текст блоков распознанного пакета (Region.raw_content_md, штамп листа)
→ разбор таблиц GFM и смысл таблицы → кандидаты адаптеров
→ детерминированная проверка: тип, место, единица, значение, свидетельство
→ реестр фактов PROMPT 01: утверждения, версии, конфликты, решения
→ матрица готовности: найдено / расходится / выводимо / нужен ввод / не проверено / не определено / не найдено
```

Расчёта систем нет. Распознавание не повторяется и не меняется. LLM не используется.

## A. Что реализовано

- Слой адаптеров `app/services/calc/adapters/`: чистый код без базы. Он превращает текст блоков
  распознанного пакета в кандидатов утверждений с местом, методом, уверенностью, свидетельством
  до таблицы и строки и техническим пояснением способа извлечения.
- Классификатор смысла таблицы по названию и шапке — 10 видов, расширяемый.
- Сбор фактов `app/services/calc/inspections.py`. Человек заявляет документ: что это, какой
  стадии, какого корпуса. Дальше работают адаптеры, результат идёт в реестр фактов PROMPT 01 —
  единственное место хранения нормализованных фактов. Запись о сборе хранит, что проверено и что
  не удалось.
- Каталог требований к исходным данным `CalcInputRequirement` и каталог ВК для В1, Т3, Т4, К1 —
  48 требований в `app/services/calc/systems/vk/requirements.py`.
- Матрица готовности `app/services/calc/readiness.py` — представление при чтении, без таблицы.
  Различает MISSING, NOT_INSPECTED, UNKNOWN и CONFLICTED.
- Реестр типов фактов v2: +31 тип, квалификатор места (тип квартиры, вид прибора), единицы
  давления, расхода, суточного объёма и температуры с защитой от ложной точности.
- API — 6 операций, экран «Расчёты → Исходные данные» за флагом, миграция 0013.

## B. Какие существующие артефакты используются

| Артефакт Quantor                              | Как используется                                                   |
| --------------------------------------------- | ------------------------------------------------------------------ |
| `Region.raw_content_md` блоков `text`         | таблицы GFM (экспликации, квартирография) и явные фразы текста     |
| строка `> **Stamp:**` в теле текстового блока | шифр → марка раздела, стадия, название листа → отметки этажей      |
| `Region.coords_norm`, `Sheet.page_index`      | место свидетельства на листе                                       |
| `DocumentRevision.source_sha256`              | отпечаток файла источника: один файл — одно подтверждение          |
| `source_metadata.imported_from_revision_id`   | линия документа: новая ревизия пакета заменяет утверждения прежней |
| `Document`, `DocumentRevision`                | список документов, последняя ревизия, распознан или нет            |

Не используются намеренно:

- описания блоков `image` — их написала модель распознавалки, наблюдением они не считаются;
- `crop_url` — сервер его не загружает никогда;
- растр, OCR, текстовый слой PDF — нового распознавания нет;
- артефакт `results_md` для перечитывания обрезанных блоков. Импорт режет раздел на 64 КБ без
  пометки; сбор такие блоки находит и пишет в сводку, но не перечитывает.

## C. Адаптеры

| Адаптер (серия источника) | Откуда                                | Что даёт                                                                             | Метод                     | Класс источника       |
| ------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------- | --------------------- |
| `apartment_explication`   | экспликации квартир этажа             | квартир, кухонь, санузлов на этаже или группе этажей                                 | TABLE_COUNTED             | квартирография        |
| `room_explication`        | экспликации МОП, помещений, коммерции | помещений с водой вне квартир на этаже                                               | TABLE_COUNTED             | экспликация помещений |
| `apartment_summary`       | квартирография                        | квартир по типам, по этажам, итог корпуса                                            | TABLE_EXPLICIT            | квартирография        |
| `sheet_titles`            | название листа в штампе               | отметки этажей «План 9 этажа на отм. +27.900»                                        | DOCUMENT_EXPLICIT         | заявленный            |
| `document_text`           | явные фразы текста                    | этажность, секции, квартиры, жители, высоты этажей, напор, t ГВС, системы ВК, ±0,000 | DOCUMENT_EXPLICIT         | заявленный            |
| `customer_vor`            | ВОР Заказчика                         | только «Заказчик ожидает систему В1»                                                 | TABLE / DOCUMENT_EXPLICIT | ВОР Заказчика         |

Устройство:

- **Разбор таблиц.** Без строки-разделителя таблицы нет. Однострочная шапка — это название
  таблицы, настоящая шапка идёт первой строкой. Строки групп «Секция № …» и «Квартира № …»,
  итоги, `\n` в ячейках и разделители страниц `## Page N` учтены.
- **Экспликации этажа.** На листе это колонки одной длинной таблицы, а порядок блоков
  распознавалки не совпадает с порядком чтения. Поэтому счёт идёт по этажу целиком: квартира
  узнаётся по номеру, повтор со страницы не считается дважды. Разбивка по секциям не делается —
  хвост секции в соседней колонке нельзя надёжно отнести к своей секции. Секции остаются в
  тексте пояснения.
- **Новый метод `TABLE_COUNTED`.** Число квартир — подсчёт явно перечисленных строк, самого
  числа в ячейке нет. Метод отдельный, чтобы проверяющий это видел; вручную он не принимается.
- **Проверка кандидата — одна для всех адаптеров** (`validate_candidate`): тип из реестра,
  место по типу, единица и значение по канонизации PROMPT 01, свидетельство из этого документа,
  допустимость факта из ВОР. Логику конфликтов адаптеры не дублируют: одинаковые значения внутри
  документа сливаются в одно утверждение с несколькими свидетельствами, разные — противоречие
  документа, ни одно не записывается.
- **Единица без слова не угадывается.** Правил, задающих единицу, два: отметки «отм.» и
  «±0,000=» — метры по ГОСТ 21.101; напор «25 м» — метры водяного столба. «Высота этажа 3,3» —
  проблема UNIT_MISSING, а не 3,3 м. Приблизительное («≈», «около») не принимается.
- **Точность источника сохраняется.** В утверждение идёт запись документа («3300 мм»,
  «162.050»), каноническая форма («3.3 м») — рядом. Перевод, который дал бы бесконечную дробь
  (м³/ч → л/с), отклоняется, а не округляется.
- **Идемпотентность.** Повторный сбор того же документа новых версий не создаёт. Исчезнувшее
  значение отзывается с причиной «не найдено при повторном сборе». Утверждения прежней ревизии
  той же линии отзываются с причиной «заменено новой ревизией документа». Ручные утверждения и
  решения человека сбор не трогает: у адаптеров свои источники серий `calc:recognized:*`, и
  вручную в них писать нельзя.

**LLM.** Не используется: шлюз моделей закрыт. Граница из ADR-0030 сохраняется — позже модель
может предлагать смысл таблицы или кандидата, но запись пройдёт ту же детерминированную проверку
с обязательным свидетельством.

## D. Модель требований к исходным данным

`CalcInputRequirement` — декларация калькулятора в коде, таблицы нет:

| Поле                                             | Смысл                                                                              |
| ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `id`, `title`, `group`                           | идентификатор, название, группа: геометрия, квартирография, нежилые, ВС, К, прочее |
| `systems`                                        | для каких систем каталога действует                                                |
| `fact_type`, `scope`                             | тип факта и область: корпус, этаж, система                                         |
| `level`                                          | REQUIRED, DESIRABLE, OPTIONAL, DERIVABLE — необходимость, не уверенность           |
| `derivable_from`                                 | из каких фактов значение выведет правило расчёта (PROMPT 03–04)                    |
| `assumption`                                     | NOT_ALLOWED, MANUAL (допущение инженера с основанием), REGISTERED_RULE             |
| `description`                                    | зачем данное расчёту — без чисел и коэффициентов                                   |
| `expected_sources`, `manual_when_sources_absent` | где обычно искать; «ТУ не найдены — нужен ручной ввод»                             |

Состояния матрицы проверяются в таком порядке:

| Состояние       | Когда                                                                                        |
| --------------- | -------------------------------------------------------------------------------------------- |
| CONFLICTED      | источники расходятся, расхождение не решено                                                  |
| FOUND           | есть действующее значение без открытого расхождения                                          |
| DERIVABLE       | прямого значения нет, но есть всё, из чего его выведет расчёт, с учётом цепочек              |
| MANUAL_REQUIRED | нет документа ожидаемого класса («ТУ не найдены») или адаптеры это не извлекают              |
| UNKNOWN         | нет распознанных документов; значение не привязано к месту; таблица найдена, но не разобрана |
| NOT_INSPECTED   | есть распознанный документ, не проверенный на этот факт                                      |
| MISSING         | все распознанные документы проверены — значения нет                                          |

Счётчики — по уровням («обязательные 4/9, желательные 5/16»), а не общим процентом. Закрыто —
FOUND или DERIVABLE. MISSING — не ноль: у отсутствующего значения нет числа ни в ответе, ни в
снимке для ядра.

## G. Пример: таблица → факты

Экспликация одного этажа — две колонки листа, во второй повторена квартира № 22:

```text
| Экспликация квартир 3 этажа | | | |        ← название вместо шапки
| № п/п | Имя | Площадь, м² | Кат. пом. |    ← настоящая шапка
| Квартира № 23 | | | |
| 1 | Кухня-столовая | 14,0 | |
| 2 | Ванная | 5,0 | |
| Секция № 2 | | | |
| Квартира № 24 | | | |  …  | Квартира № 22 | | | |
```

Вместе с первой колонкой (квартиры 21 и 22) это даёт этаж 3: 4 квартиры, 4 кухни, 5 санузлов и
ванных. Каждое значение — TABLE_COUNTED со свидетельствами обеих таблиц.

Квартирография «Тип квартиры | Количество квартир типа, шт. | %» даёт R1 = 96, R2 = 64, R3 = 16 и
итог 192. Это TABLE_EXPLICIT: ячейка столбца количества, строка и столбец в свидетельстве. Столбец
«%» за количество не принят. Строка «2Е» — евроформат, тип не угадывается; в сводке сбора она
видна как UNMAPPED_LABEL.

## H. Пример MISSING

В проекте два распознанных документа — альбом АР и записка без чисел; собраны оба:

```json
{
  "requirement_id": "vk.building.floors_above",
  "status": "MISSING",
  "reason": "Проверено документов: 2 — не найдено",
  "values": []
}
```

В снимке для ядра ключа этажности нет вовсе — не ноль.

## I. Пример NOT_INSPECTED

До сбора этажность и квартиры — NOT_INSPECTED, «Не проверено документов: 2 из 2». После сбора
альбома квартиры на этажах — FOUND, а этажность остаётся NOT_INSPECTED, «1 из 2»: она могла бы
быть в записке, которую ещё не смотрели. Система не говорит «данных нет», пока не просмотрела
документ.

## J. Пример конфликта

Два альбома по-разному перечисляют квартиры 3 этажа: 4 и 2. Оба — квартирография стадии П, одного
ранга политики. Итог: `UNRESOLVED`, конфликт `OPEN`, значения нет. Проверяющий выбирает 4 с
причиной «во втором альбоме не все листы» — `DECIDED`. Повторный сбор первого альбома ничего не
меняет (`created = 0`), решение остаётся в силе. Решения PROMPT 01 работают поверх собранных фактов
без изменений.

## K. Пример качественного факта ВОР, исключённого из расчёта

```text
| 1 | Трубопровод В1 из PP-R Ø50 | м | 1280 |
| 2 | Стояк К1 канализации Ø110 | м | 320 |
```

- Утверждения: только `system.present` для В1 и К1, `calculation_eligible = false`.
- Сводка сбора: количества не приняты — 2, диаметры не приняты — 2.
- Ни одного утверждения со значениями 1280, 320, 50 или 110.
- Снимок для ядра пуст.
- В матрице В1 «диаметры магистралей» не закрыты. «Система предусмотрена» не найдена, а рядом —
  «в ВОР Заказчика: 1 — только сверка».
- В таблице фактов: «нет — ВОР, только сверка».
- Ограничение базы запрещает утверждению ВОР участвовать в расчёте, как в PROMPT 01.

## M. Интерфейс

Экран `/projects/[projectId]/calc`. Вход — кнопка «Расчёты» на карточке проекта, только при
включённом флаге; при выключенном флаге страницы нет. Три раздела:

- **Готовность к расчёту** — карточки В1, Т3, Т4, К1 со счётчиками по уровням и таблица
  требований: статус, значения с местом и единицей, источник или причина, отдельно — ВОР.
- **Факты** — Факт | Значение | Ед. | Область | Система | Источник | Статус | Уверенность | В
  расчёте. Запись документа показана, если отличается от канонической.
- **Документы** — распознан ли документ, подсказка по штампу, последний сбор. Окно сбора:
  класс документа, стадия, корпус, раздел для инженерного документа. После сбора — сводка:
  принято, заменено, отозвано, что не взято и почему.

Таблицы на телефоне разворачиваются в карточки. Подписи — в `lib/calc/format.ts`, расчётов в
интерфейсе нет. Действия человека с фактами — раздел S.

## N. Миграция 0013 и зачем она

`20260928_0013_calc_stage_p_inputs`:

- таблица `calc_source_inspections` — без неё «проверено, не найдено» не отличить от «не
  проверено», а это требование промта;
- `calc_fact_evidence`: `region_id`, `region_sha256`, `region_locator` и ограничение
  «свидетельство блока — с блоком и местом». Иначе свидетельство до строки таблицы пришлось бы
  прятать в текст;
- `calc_facts`: `qualifier` для типа квартиры и вида прибора и `inspection_id`;
- частичный уникальный индекс источников сбора.

Требования и матрица готовности не хранятся. Откат удаляет только свидетельства блоков.

## P. Известные ограничения

- Сбор возможен только из распознанного пакета. У сырого PDF текста нет, а нового OCR не будет:
  для таких документов остаётся ручной ввод, матрица честно пишет, что распознанных документов нет.
- Счёт квартир по экспликациям — по этажам, без разбивки по секциям.
- Экспликация на группу этажей («4-5») и отдельная на этаж 4 дают разные ключи. Их сведение —
  задача расчёта.
- Шаблоны текста узкие и проверены только на синтетике: реальных ПЗ и ТУ стадии П в проекте нет.
  Расходы по системам из записок не извлекаются.
- Квартирография — два вида сводки. Евроформаты не сопоставляются. Таблицы приборов и
  потребителей распознаются по смыслу, но не разбираются: по ним матрица пишет «не определено».
- Корпус заявляется на документ: альбом с несколькими корпусами пока не разбирается по корпусам.
- Отметки берутся только из названий планов в штампе. Отметки кровли и разрезы не читаются.
- Блоки, обрезанные импортом на 64 КБ, только помечаются; перечитывания из `results_md` нет.
- Полнота по этажам не проверяется: матрица говорит «найдено», если есть значения, но не сверяет,
  все ли этажи закрыты. Это задача входа калькулятора.
- Подсказка по штампу опирается на формат штампа этой распознавалки.

## Q. Что намеренно не реализовано

- **Отдельный импорт XLSX и CSV** — не нужен и долгом не считается (решение владельца при приёмке,
  [ADR-0030](../adr/0030-raschyotnyj-kontur-stadii-p.md), «Уточнения владельца после PROMPT 02»).
  Факты объекта извлекаются из документации общим конвейером документов; XLSX и CSV как документ
  проекта — в будущем ещё один адаптер источника этого конвейера.
- **Адаптер обмеров** (`GEOMETRY_MEASURED`). Ручной обмер — резервный путь, как и ручной ввод;
  метод по-прежнему не принимается вручную.
- LLM, выполнение выводов (DERIVABLE только объявлено), правила и калькуляторы, правила старого
  портала, обязательность MEP semantic.

## R. Готовность к PROMPT 03

Каталог требований уже называет, какие правила понадобятся реестру правил. Это требования с
`REGISTERED_RULE` и `derivable_from`:

- кухни из квартир;
- санузлы из типов квартир;
- приборы из санузлов и кухонь;
- жители из типов квартир;
- высоты этажей и здания из отметок;
- зоны и насосная из высоты и напора;
- узлы учёта;
- нормативная температура горячей воды;
- стояки из шахт и квартир.

Для PROMPT 03 это список правил, которые нужно завести со статусом и источником. Вход ядра
PROMPT 04 — снимок реестра: сбор в него пишет, ВОР в него не попадает.

Открыто для владельца: объект и порог гейта после PROMPT 06.

## S. Доработка после аудита (2026-09-29): ручной ввод и решения человека

Экран «Исходные данные» теперь не только показывает, но и позволяет закрыть недостающее — через
готовые API PROMPT 01, без новых таблиц и маршрутов.

| Действие                       | Где                                                                                 | Право         | Что проверяет сервер                                                         |
| ------------------------------ | ----------------------------------------------------------------------------------- | ------------- | ---------------------------------------------------------------------------- |
| Ввести значение                | строка матрицы: не найдено, не определено, нужен ввод, не проверено                 | `calc.edit`   | основание обязательно; место и единица по типу факта; источник «Ручной ввод» |
| Добавить этаж                  | найденная поэтажная строка (квартиры, кухни, санузлы): недостающий этаж или явный 0 | `calc.edit`   | то же, что при вводе значения                                                |
| Допущение вместо значения      | та же форма, только если политика требования `MANUAL`                               | `calc.edit`   | основание и альтернативы; метод `ASSUMPTION`, уверенность низкая             |
| Варианты расхождения           | строка матрицы «расходится», строка факта «нет — расхождение»                       | чтение        | —                                                                            |
| Решить расхождение             | окно вариантов: выбор утверждения и причина                                         | `calc.verify` | причина обязательна; решение перепроверяется при новом утверждении           |
| Подтвердить, отклонить         | строка факта                                                                        | `calc.verify` | отклонение — с причиной; автор своё утверждение не проверяет                 |
| Отозвать                       | строка факта, только ручной ввод                                                    | `calc.edit`   | причина обязательна; значение документа отзывается новым сбором              |
| Основание                      | строка факта: свидетельства, выдержка, лист, ссылка на блок в рабочей области       | чтение        | —                                                                            |
| Только незакрытые обязательные | фильтр матрицы                                                                      | чтение        | —                                                                            |

Уточнения матрицы готовности (`services/calc/readiness.py`):

- ВОР Заказчика не считается проверенным документом: его сбор не делает исходное «не найденным».
  Сбор ВОР записывает проверенными только `system.present` — то, что ищет его адаптер.
- «Не найдено» называет PDF без распознавания: «…; PDF без распознавания не проверялись: N».
  Архивы пакетов и BIM не в счёт.
- Таблица, найденная, но не разобранная (санприборы, потребители воды), даёт «не определено» с
  подсказкой ввести значение по этой таблице, а не «нет в проекте — нужен ручной ввод».
- Допущение там, где политика требования `NOT_ALLOWED`, требование не закрывает: строка остаётся
  «нужен ввод» с причиной, значение видно.
- Ручное значение без основания сервер не принимает (`CALC_EVIDENCE_REQUIRED`); своё утверждение
  автор не подтверждает и не отклоняет (`CALC_FACT_SELF_REVIEW`, 403). Утверждение, записанное
  сбором, автором запустившего сбор не считается — его написал документ.

Экран ВК «Исходные данные» ведёт сюда ссылкой и показывает, на что недостающее влияет и на что нет.

Остаётся ограничением:

- матрица не делит данные по корпусам: значение корпуса 1 закрывает требование и для корпуса 2;
  для объекта из одного корпуса это не важно. Готовность паспорта ВК тоже считается по проекту;
- журнал сбора после закрытия окна — только API `GET /calc/projects/{id}/inspections`;
- в каталоге нет «корпусов» и точек подключения К1 к наружной сети; душевые, гостевые санузлы и
  помещения персонала — через общие счётчики;
- в API политика допущений не проверяется при записи: запрет стоит в интерфейсе и в матрице, а
  ядро расчёта читает снимок фактов без неё;
- решение конфликта может принять тот же инженер, что внёс одно из значений: запрет — только на
  подтверждение и отклонение своего утверждения (решение владельца — в ADR-0030).
