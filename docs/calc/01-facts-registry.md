# PROMPT 01 — контракты данных и реестр фактов

Дата: 2026-09-28. Пакет — [`_prompts/calc_portal_stage_p/`](../../_prompts/calc_portal_stage_p/Quantor_Opus_5.5_Prompts_Calculation_Portal.md).
Решение — [ADR-0030](../adr/0030-raschyotnyj-kontur-stadii-p.md), принято 2026-09-28 с уточнениями владельца.
Архитектура — [00-audit-and-architecture.md](00-audit-and-architecture.md), раздел 3.

## 1. Что появилось

Реестр фактов проекта — первое, из чего будет считать расчётный контур. Факт хранится не
значением, а **утверждением**: кто, откуда и каким методом сообщил значение. Одно место может
иметь несколько утверждений; какое из них пойдёт в расчёт, решает детерминированный выбор, а при
расхождении — человек.

```text
CalcSource            источник: ревизия документа проекта или ручной ввод
  └── CalcFact × N    утверждение «тип@место = значение»: метод, уверенность, версия, проверка
        └── CalcFactEvidence × N   фрагмент документа / основание допущения / автор ввода
fact_key ─► CalcFactConflict       значения ключа расходятся — конфликт виден всегда
         └► CalcManualOverride     решение человека с отпечатком набора утверждений
действующие значения ─► снимок для ядра: только calculation_eligible = true
```

| Часть                                     | Где                                                                             |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| Контракты                                 | `app/contracts/calc/`: enums, units, subjects, values, fact_types, facts, draft |
| Политика приоритета источников            | `app/services/calc/facts/policy.py`                                             |
| Выбор значения и снимок — чисто, без базы | `app/services/calc/facts/resolution.py`                                         |
| Хранение, версии, конфликты, решения      | `app/services/calc/facts/registry.py`                                           |
| Модели и миграция                         | `app/models/calc.py`, `alembic/versions/20260928_0012_calc_facts_registry.py`   |
| API                                       | `app/api/v1/calc.py` → `/api/v1/calc/…`                                         |
| Права, ошибки, журнал, флаг               | `auth/permissions.py`, `errors.py`, `domain.py`, `core/features.py`             |
| Тесты                                     | `apps/api/tests/test_calc_*.py`                                                 |

Весь маршрутизатор закрыт флагом `calc.portal`: `default = false`, `admin_editable = false`. Флаг
не включается до PASS инженерного гейта после PROMPT 06 и отдельного решения владельца. Интерфейса
в этом промте нет.

Общие контракты:

- `CalcFactSubject` — место факта: корпус, секция, этаж или диапазон этажей `2..24`, помещение,
  раздел и код системы. Код системы требует раздела: «В1» водопровода и «В1» вытяжки — разные
  системы. Латинские двойники приводятся к кириллице: `B1` → `В1`. Ключ места канонический:
  `building=1|floor=12|discipline=VK|system_code=В1`.
- `CalcFactValue` — значение шести видов с дискриминатором `kind`: NUMBER, COUNT, BOOLEAN, ENUM,
  TEXT, RANGE. Числа передаются десятичной строкой без экспоненты, внутри — `Decimal`.
- Каталог единиц `units.py`: длина (m, cm, mm), площадь (m2) и типизированные счётчики (floor,
  section, apartment, bathroom, kitchen, riser). Счётчики переводятся только в самих себя: этажи
  не превращаются в квартиры. Так ловится двойное умножение старого портала.
- Реестр типов фактов `fact_types.py` (`calc.fact_types.v1`) — 17 типов, у каждого вид значения,
  каноническая единица, обязательное и допустимое место, допуск сравнения и признак «допустим из
  ВОР Заказчика».

Все схемы и перечисления начинаются с `Calc`. Иначе одноимённая схема заставила бы FastAPI
переименовать около 73 неквалифицированных схем MEP (`Parameter`, `RuleRef`, `SourceRef`…), а с
ними — типы фронтенда. Закреплено тестом `test_calc_routes.py`.

## 3. Что хранит утверждение

| Требование промта            | Поле                                                                  |
| ---------------------------- | --------------------------------------------------------------------- |
| тип факта                    | `fact_type`                                                           |
| значение и единица           | `value` — каноническое, `stated_value` — как введено; `unit`          |
| корпус, секция, этаж         | `subject.building`, `subject.section`, `subject.floor`                |
| помещение                    | `subject.room`                                                        |
| инженерная система           | `subject.discipline` + `subject.system_code`                          |
| источник                     | `source_id`, `source_class`; у источника — стадия документа и раздел  |
| документ, страница, лист     | `evidence[].document_revision_id`, `page_index`, `sheet_id`           |
| координаты, ссылка, фрагмент | `evidence[].bbox` (нормализованные 0..1), `locator`, `excerpt`        |
| метод получения              | `method`, 9 значений                                                  |
| уверенность                  | `confidence`: HIGH / MEDIUM / LOW                                     |
| дата                         | `created_at`, `reviewed_at`, `withdrawn_at`                           |
| версия                       | `version`, `supersedes_id`; новое значение того же источника — версия |
| статус проверки человеком    | `review_status`: UNREVIEWED / CONFIRMED / REJECTED, кто и когда       |

Методы. Вручную через API принимаются DOCUMENT_EXPLICIT, TABLE_EXPLICIT, MANUAL и ASSUMPTION.
Остальные объявлены, но записываются только своими производителями: GEOMETRY_MEASURED — адаптером
обмеров (PROMPT 02), INFERRED / NORMATIVE / MANUFACTURER_RULE — правилом реестра (PROMPT 03),
CALCULATED — ядром (PROMPT 04). Ручная запись «вычислено» без запуска подделала бы происхождение,
поэтому ответ — 422 `CALC_METHOD_NOT_AVAILABLE`.

Правила приёма:

- DOCUMENT_EXPLICIT и TABLE_EXPLICIT — только от источника-документа и только с фрагментом
  **его** ревизии. Источник «файл А» не подтверждается фрагментом файла Б.
- Источник-документ обязательно ссылается на ревизию проекта; отпечаток файла (`content_sha256`)
  берётся из ревизии. Один файл, заведённый под двумя источниками, не считается двумя
  подтверждениями.
- MANUAL и ASSUMPTION — только от источника «ручной ввод». У ручного ввода есть автор и основание;
  у допущения — основание и альтернативы, уверенность по умолчанию LOW.
- Утверждения не удаляются: отзыв с причиной (`WITHDRAWN`) или новая версия (`SUPERSEDED`).

## 4. Приоритет источников

Глобальной истины нет. Политика (`calc.priority.v1`) задаётся парой «тип факта × (класс источника,
стадия документа)». По умолчанию — `MANUAL_REQUIRED`: при расхождении значения нет, пока не решит
человек. `AUTO_PREFER` разрешён перечнем:

| Тип факта                      | Порядок                                               |
| ------------------------------ | ----------------------------------------------------- |
| `floor.apartments_count`       | квартирография РД → квартирография П → АР РД → АР П   |
| `floor.height`                 | АР РД → АР П → пояснительная записка                  |
| `building.floors_above_ground` | АР РД → АР П → квартирография → пояснительная записка |

Даже при `AUTO_PREFER` конфликт остаётся открытым, а значение помечено `CONFLICT_OPEN`. Лидеры
одного ранга с разными значениями дают `UNRESOLVED`.

Состояния действующего значения: MISSING, SINGLE, CORROBORATED, AUTO_PREFERRED, DECIDED,
DECIDED_STALE, UNRESOLVED. MISSING и UNRESOLVED в снимок для ядра не попадают — отсутствие не
превращается в ноль.

## 5. Примеры

Ниже реальные ответы API на синтетических данных. Идентификаторы сокращены до `<a>`, `<b>`…,
служебные поля и пустые значения опущены.

### 5.1. Ручной факт

Инженер вводит высоту этажей 2–24 корпуса 1 в миллиметрах — реестр хранит и введённое, и
каноническое значение.

```json
{
  "fact_key": "floor.height@building=1|floor=2..24",
  "value": { "kind": "NUMBER", "value": "3.3", "unit": "m" },
  "stated_value": { "kind": "NUMBER", "value": "3300", "unit": "mm" },
  "method": "MANUAL",
  "confidence": "MEDIUM",
  "review_status": "UNREVIEWED",
  "status": "ACTIVE",
  "version": 1,
  "calculation_eligible": true,
  "evidence": [{ "kind": "MANUAL_ENTRY", "basis": "по разрезу 1-1" }]
}
```

Допущение хранится так же, но с основанием и альтернативами:
`floor.corridor_length` = 30 m, `ASSUMPTION`, LOW, основание «Планы этажей стадии П без размеров
коридора», альтернативы «24 м» и «36 м».

### 5.2. Факт из документа

Число квартир 12 этажа по плану АР П, с листом и рамкой фрагмента:

```json
{
  "id": "<d>",
  "source_class": "ARCHITECTURE",
  "fact_key": "floor.apartments_count@building=1|floor=12",
  "value": { "kind": "COUNT", "value": 8, "unit": "apartment" },
  "method": "DOCUMENT_EXPLICIT",
  "confidence": "HIGH",
  "evidence": [
    {
      "kind": "DOCUMENT_FRAGMENT",
      "document_revision_id": "<g>",
      "sheet_id": "<h>",
      "bbox": [0.1, 0.1, 0.4, 0.3],
      "excerpt": "план 12 этажа"
    }
  ]
}
```

### 5.3. Конфликт

Квартирография П даёт 9 квартир на 12 этаже (`TABLE_EXPLICIT`, «таблица 1, строка „12 этаж“»),
план АР П — 8 (пример 5.2).

| Шаг                                                       | Конфликт   | Значение                              |
| --------------------------------------------------------- | ---------- | ------------------------------------- |
| два утверждения расходятся                                | `OPEN`     | `AUTO_PREFERRED` = 9, `CONFLICT_OPEN` |
| проверяющий выбирает 8: «План РП-12 новее квартирографии» | `RESOLVED` | `DECIDED` = 8                         |
| пояснительная записка сообщает 10                         | `REOPENED` | `DECIDED_STALE` = 8, `DECISION_STALE` |
| утверждение записки отозвано: «опечатка в записке»        | `RESOLVED` | `DECIDED` = 8                         |

Значение при открытом конфликте:

```json
{
  "fact_key": "floor.apartments_count@building=1|floor=12",
  "state": "AUTO_PREFERRED",
  "value": { "kind": "COUNT", "value": 9, "unit": "apartment" },
  "chosen_fact_id": "<i>",
  "claim_ids": ["<d>", "<i>"],
  "conflict_id": "<j>",
  "policy_version": "calc.priority.v1",
  "warnings": ["CONFLICT_OPEN"]
}
```

Решение хранит отпечаток набора утверждений, по которому принималось; новое утверждение меняет
набор, и конфликт снова открывается:

```json
{
  "fact_key": "floor.apartments_count@building=1|floor=12",
  "status": "RESOLVED",
  "claim_set_hash": "8a89640569a8…",
  "decision": {
    "chosen_fact_id": "<d>",
    "reason": "План РП-12 новее квартирографии",
    "claim_set_hash": "8a89640569a8…"
  }
}
```

Решение со своим значением: проектная часть ВК говорит «сталь», записка — «PE-X» для системы
`B1` → `В1`. Проверяющий вводит «сталь оцинкованная» с причиной «Уточнено у ГИПа». Значение
записывается утверждением-носителем в служебной серии `calc:decisions`. Пополнить эту серию в
обход решения нельзя: 422 `CALC_SOURCE_NOT_ALLOWED`.

### 5.4. Ручное подтверждение

Проверяющий подтверждает план и отклоняет квартирографию. Отклонение без комментария не
принимается:

```text
POST /api/v1/calc/facts/<i>/review {"status": "REJECTED"}
→ 422 "отклонение требует комментария"
```

```json
{
  "id": "<d>",
  "review_status": "CONFIRMED",
  "review_comment": "сверено с планом 12 этажа"
}
```

```json
{
  "id": "<i>",
  "review_status": "REJECTED",
  "review_comment": "в квартирографии учтена кладовая как квартира",
  "status": "ACTIVE"
}
```

Отклонённое утверждение в выборе не участвует. Расхождения больше нет: конфликт `OBSOLETE`, значение
`SINGLE` = 8 без предупреждений. Утверждение не удалено: оно остаётся видимым вместе с причиной
отклонения.

### 5.5. ВОР Заказчика

ВОР — объект сверки, не эталон и не вход расчёта.

- Источник класса `CUSTOMER_VOR` создаётся с `calculation_eligible = false`.
- Количества из ВОР в реестр не принимаются вовсе:

  ```json
  {
    "detail": {
      "code": "CALC_SOURCE_NOT_ALLOWED",
      "message": "Из ВОР Заказчика в реестр принимаются только качественные факты: количества и решения ВОР сверяются с расчётом, но не входят в него"
    }
  }
  ```

- Качественный факт — материал К1 «НПВХ» — записывается, но исключён из расчёта. Проект П говорит
  «ПП бесшумный»; конфликта нет, потому что ВОР не спорит с проектом и не подтверждает его:

  ```json
  {
    "fact_key": "system.pipe_material@building=1|discipline=VK|system_code=К1",
    "state": "SINGLE",
    "value": { "kind": "TEXT", "value": "ПП бесшумный" },
    "chosen_fact_id": "<q>",
    "claim_ids": ["<q>"],
    "excluded_claim_ids": ["<r>"]
  }
  ```

- В снимке для ядра — только утверждение проекта. Ключ, известный только из ВОР, в снимок не
  попадает вовсе.

## 6. Инварианты и кто их держит

| Инвариант                                                 | Кто держит                                                                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| ВОР Заказчика не допущен к расчёту                        | CHECK `vor_never_eligible` в `calc_sources` и `calc_facts`; выбор значения; сборка снимка падает; решение не может выбрать недопущенное |
| одна действующая версия утверждения источника по ключу    | частичный уникальный индекс `uq_calc_facts_active_per_source`                                                                           |
| номер версии не повторяется                               | уникальный индекс `uq_calc_facts_version` + блокировка строки источника                                                                 |
| одно действующее решение по ключу                         | частичный уникальный индекс `uq_calc_manual_overrides_active`                                                                           |
| у решения есть причина, у свидетельства — содержание      | CHECK `reason_not_blank`, `kind_has_content`                                                                                            |
| один конфликт на ключ                                     | уникальный индекс `uq_calc_fact_conflicts_key`                                                                                          |
| одновременные расхождения не теряются                     | транзакционная блокировка ключа до чтения его утверждений                                                                               |
| устаревший объект не отзывается и не проверяется повторно | статус перечитывается под блокировкой ключа                                                                                             |
| фрагмент — из документа своего источника                  | сервис, 422 `CALC_EVIDENCE_INVALID`                                                                                                     |
| граница рабочего пространства                             | проект и утверждение ищутся только в пространстве запроса, чужое — 404                                                                  |

Порядок блокировок один: источник → ключ → строки утверждений. Так взаимная блокировка
невозможна.

Права: `calc.read` — наблюдатель и выше, `calc.edit` — инженер (источники, утверждения, отзыв),
`calc.verify` — проверяющий (подтверждение, отклонение, решение). Проверяющий подтверждает, но не
вносит: ответственность за число отделена от ввода. Каждое изменение пишется в журнал аудита.

## 7. Чего не сделано специально

- Таблиц, сервисов и маршрутов для десяти будущих сущностей нет. Тест держит точное число
  операций (11) и отсутствие таблиц `calc_runs`, `calc_steps`, `calc_results`, `calc_vor_items`.
- Интерфейса нет. Экран «Исходные данные проекта» — PROMPT 02.
- Нет импорта xlsx/csv и адаптеров таблиц Region и обмеров — PROMPT 02. Общий приём файлов не
  менялся.
- Нет замещения по серии документа: новая ревизия того же документа — новый источник. Старые
  утверждения остаются, пока их не отзовут; расхождение со старыми видно как конфликт. Серии —
  PROMPT 02, вместе с адаптерами.
- Уверенность — умолчание по методу или заявление автора. Вычисляемая функция надёжности от
  метода, проверки и конфликта — при сборке входа ядра, PROMPT 04. Снимок уже несёт метод,
  проверку и состояние выбора.
- LLM нет. Флаг нигде не включён: тесты включают его системным переопределением в своей базе.

## 8. Найдено при самопроверке и исправлено до отчёта

1. **Гонка расхождений.** Два одновременных расходящихся утверждения не видели друг друга, и
   конфликт не записывался. Теперь любое изменение ключа идёт под транзакционной блокировкой
   ключа. Тест с двумя транзакциями без блокировки падает, с ней — проходит.
2. **Устаревший объект.** Второй одновременный отзыв или проверка работали по статусу,
   прочитанному до ожидания. Теперь статус перечитывается под блокировкой: 409
   `CALC_FACT_NOT_ACTIVE`.
3. **Серия решений была открыта для записи.** Её можно было пополнить обычным утверждением или
   завести вторую такую же. Серии `calc:…` теперь ведёт только реестр.
4. **Провенанс документа.** Источник-документ можно было завести без ревизии, а фрагмент — взять
   из чужого файла. Тогда один файл под двумя источниками считался бы двумя подтверждениями.
   Теперь источник-документ обязан ссылаться на ревизию, а фрагмент — на ревизию своего
   источника; у ручного ввода файла нет.
5. **Неснимаемое «решение устарело».** После отклонения проигравшего утверждения конфликт
   закрывался, а значение навсегда оставалось `DECIDED_STALE`. Теперь решение действует, пока есть
   расхождение. Правило уточнено в [аудите](00-audit-and-architecture.md), раздел 3.
