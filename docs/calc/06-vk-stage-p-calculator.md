## A. Архитектура калькуляторов

Четыре отдельных версионируемых калькулятора ядра и четыре синтезатора, вид `PRODUCTION`:

| Система | Калькулятор       | Синтезатор          | Назначение по документации (`system.function`) |
| ------- | ----------------- | ------------------- | ---------------------------------------------- |
| В1      | `vk.b1.stage_p@1` | `vk.b1.structure@1` | COLD_WATER                                     |
| Т3      | `vk.t3.stage_p@1` | `vk.t3.structure@1` | HOT_WATER_SUPPLY                               |
| Т4      | `vk.t4.stage_p@1` | `vk.t4.structure@1` | HOT_WATER_CIRCULATION                          |
| К1      | `vk.k1.stage_p@1` | `vk.k1.structure@1` | DOMESTIC_SEWER                                 |

Код — `app/services/calc/systems/vk/`, одного большого модуля нет:

| Модуль                                | Что делает                                                                   |
| ------------------------------------- | ---------------------------------------------------------------------------- |
| `spec.py`                             | описание системы: правила, источник, назначение                              |
| `steps.py`                            | общие шаги (этажность, квартирография, вертикаль, повторяемость) и системные |
| `handlers.py`                         | реализации правил — исполняются только утверждённой версией                  |
| `rule_needs.py`, `rule_templates.py`  | заявки на инженерные решения и шаблон версии правила                         |
| `structure.py`, `structure_links.py`  | синтез графа: источник, зоны, стояки, этажи, магистраль, подключения         |
| `volume_base.py`, `volumes*.py`       | слой D: ожидаемые количества из графа                                        |
| `passport.py`, `passport_sections.py` | Расчётный паспорт системы                                                    |
| `readiness.py`                        | назначение систем, готовность данных и правил                                |
| `orchestrator.py`, `reads.py`         | комплект ВК, хранение, чтение, объяснение позиции                            |

Слои расчёта разделены (§7 задания): **A** потребность и **B** структура — шаги ядра
(`demand_*`, `structure_*`), **C** топология — синтезатор, **D** количества — параметры
утверждённых правил (`quantity_*`) в ядре и сборка позиций из графа в слое паспорта. Тендерное
допущение — отдельный шаг `tender_*`, применяется только в TENDER_SAFE.

Расширение ядра PROMPT 04 (минимальное, описано в ADR-0030):

- **шаг-примитив** — счёт, сумма, разность, обход этажей без версии правила. Закрытый реестр
  `engine/primitives.py`, у примитивов нет параметров (константу не спрятать), ключ
  `primitive.*`; версия правила сослаться на примитив не может (проверка содержания правила);
  в цепочке объяснения узел «Вычислительный примитив, не инженерное правило»;
- **набор фактов** — вход «все факты типа по этажам области» (`SeriesBinding`); члены набора —
  входы шага с кодом этажа; повтор восстанавливает членство из снимка и причин блокировки;
- **частичный результат** — калькулятор с `partial=True`: заблокированный шаг блокирует только
  зависимые; неполный набор (`InsufficientInputError`) — шаг «не определён» с причиной
  INPUT_INCOMPLETE. Статус запуска PARTIAL; ограничения `calc_runs` расширены миграцией 0017.

Отпечатки демо-калькуляторов, реализаций и контрольных графов PROMPT 04–05 не изменились.

## B. Исходные данные

Каталог требований ВК `calc.requirements.vk.v2` (было v1) сверен с калькулятором.
Обязательные — только то, без чего расчёт системы не идёт:

| Требование                 | Уровень v2 | Зачем                                                   |
| -------------------------- | ---------- | ------------------------------------------------------- |
| `vk.building.floors_above` | REQUIRED   | покрытие квартирографии, верхний этаж                   |
| `vk.apartments.per_floor`  | REQUIRED   | этажи с квартирами, итог, основание числа стояков       |
| `vk.floor.height`          | REQUIRED   | межэтажный пролёт; выводится из отметок                 |
| `vk.system.function`       | REQUIRED   | назначение обозначения — по легенде или записке (новое) |
| `vk.system.main_length`    | DESIRABLE  | известная часть трасс (новое)                           |

Понижены до DESIRABLE или OPTIONAL: секции, назначение этажей, всего квартир (выводимо), санузлы,
«система предусмотрена» (следует из назначения), напор ТУ, источник горячей воды. Новые типы
фактов: `system.function` (перечень назначений), `system.main_length` (м). Версия типов фактов —
`calc.fact_types.v3`.

## C. Автоматическое получение данных

Порядок не изменился: найдено в документах → выведено → вручную (последний путь). Калькулятор
берёт факты реестра сам; анкеты нет. Сбор PROMPT 02 дополнен узким адаптером назначения систем
(`adapters/system_semantics.py`): строка легенды «Т3 — водопровод горячей воды подающий» или
строка таблицы условных обозначений; две системы в одной строке или два назначения сразу —
пропуск, а не догадка. Готовность ВК показывает: найдено автоматически, введено вручную,
выводится, нужен человек, не проверено — и для каждого недостающего, какие позиции паспорта без
него не определяются.

## D. Готовность правил

22 заявки на инженерные решения с контрактом реализации и две методики без реализации. Ни одна
версия правила не утверждена кодом: проверенного источника в репозитории нет, память модели
источником не считается. Матрица по системам, статусы и пакет для инженера —
[06-rule-readiness.md](06-rule-readiness.md). Статусы в пространстве вычисляются по реестру
правил: READY, DRAFT (блокер гейта), SOURCE_REQUIRED, IMPLEMENTATION_REQUIRED.

## E. В1

Источник — ввод(ы) из документа; зоны — документ, иначе правило по высоте; насосная установка и
узлы учёта — только если названы; стояки — документ, иначе диапазон по правилу; этажные
подключения — по правилу схемы; арматура стояков — по правилу, узлами графа. Расходы документа —
факты; контрольный расчёт расходов не реализован (методика нормативная, источника нет).

## F. Т3

Как В1 по структуре, но своими правилами (`vk.t3.risers.count_range`, изоляция ГВС) и источником —
источник горячей воды (ИТП, ЦТП…) из документа. Полотенцесушители, температура и циркуляционная
схема видны как данные; решения по ним — не приняты без правил.

## G. Т4

Циркуляционный трубопровод — свой калькулятор: стояки по своему правилу (не копия Т3),
балансировочная арматура — отдельным правилом по узлам, подключения — только если правило схемы
Т4 их задаёт (в контрольных примерах 0). Зонирование не повторяется — оно у Т3.

## H. К1

Точки водоотведения — по таблице приборов (примитив суммы по видам) или утверждённым правилом
«санузел/кухня → приборы»; стояки — документ или правило; отводы — правило длины; выпуски — из
документа, их длина до колодцев на стадии П «не определено». Уклоны и координаты не создаются.
Вытяжная часть стояка — верхний участок правила концевых участков К1.

## I. Demand calculation

Потребность стадии П — квартиры и приборы: этажи с квартирами, итог квартир, наибольшее число
квартир на этаже (примитив `floor_structure`), для К1 — приборы. Документальный итог квартир
сверяется с квартирографией: документ, контроль и расхождение хранятся раздельно, документ не
заменяется. Расходы воды — факты документа; независимый расчёт расходов не выполняется.

## J. Zoning

Зоны: OBSERVED — из документа; CALCULATED — по утверждённому правилу `vk.water.zones.by_height`
(высота обслуживаемой части / наибольшая высота зоны, вверх); иначе — структурная
неопределённость. Фиксированного числа зон без правила нет; расхождение документа и правила —
предупреждение, принимается документ.

## K. Risers

Порядок: стояки из П (OBSERVED) → диапазон по утверждённому правилу (CALCULATED) → «не
определено». Шахты — ограничение: узел «шахты» и неопределённость размещения; стояки по шахтам
не раскладываются. Диапазон «2–3» остаётся диапазоном: варианты без вероятностей, в MINIMUM —
нижняя оценка с пометкой «Это нижняя оценка, не проектное решение».

## L. Topology

Правило схемы (`vk.water.topology.scheme`, `vk.t4.…`, `vk.k1.…`) даёт связи: начало системы →
магистраль → стояки → этажные подключения (на стояк и этаж, множители `risers`, `served_floors`).
Без правила элементы есть, связей нет — структурная неопределённость, паспорт PARTIAL.
Обслуживаемые этажи — одна группа с повторяемостью ×N: двойное умножение невыразимо.

## M. Vertical lengths

Межэтажный пролёт стояка — примитив `vertical_span`: отметка верхнего этажа с квартирами минус
отметка 1-го, если обе есть; иначе сумма высот этажей 1…(верхний−1) с проверкой покрытия. Разные
высоты учитываются; 3,3 м не подставляются; пробел или перекрытие этажей — шаг не определён.
Участки ниже 1-го и выше верхнего этажа — только утверждённым правилом концевых участков; без
него длина стояков — «подтверждаемая часть», позиция PARTIAL.

## N. Horizontal lengths

Магистраль — длина из документа или обмера (`system.main_length`), иначе «не определено» (ROUTE).
Этажные подключения — число из топологии × диапазон длины по правилу. Методики грубой
трассировки нет (IMPLEMENTATION_REQUIRED); «коридор × 0,8» старого портала не используется.
Нового распознавателя геометрии нет.

## O. Fittings

Из топологии: ответвление на каждое присоединение подключения к стояку, оконечный элемент на
каждый стояк, переход магистраль—стояк — только если диаметры обоих из документа различаются.
Тип фитинга по материалу не выдумывается. Фитинги трассы (отводы, муфты) — резервный метод по
утверждённому правилу «на метр», помечен FALLBACK и примечанием; без правила — «не определено».

## P. Valves

Только узлами графа: запорная арматура стояков (правило «на стояк»), балансировочная Т4. «N кранов
на этаж» не применяется; модель и производитель не определяются.

## Q. Insulation

Только по документу или утверждённому правилу: признак изоляции по виду участка; длина изоляции
= длина участка с признаком 1 (с его полнотой). Без правила — позиция «не определено»: изоляция не
равна всей длине трубы.

## R. Supports

Только по утверждённому шагу креплений: ⌈длина участка на экземпляр / шаг⌉ × экземпляры,
отдельно стояки и горизонталь. Шаг и коэффициенты старого портала не используются.

## S. Sleeves

Проходки — топология: стояки × перекрытия между 1-м и верхним этажом. Гильзы и огнезащита —
отдельные позиции по утверждённому правилу; без него «не определено».

## T. Equipment

Только названное в документе: насосная установка (1 комплект, производитель, модель и
производительность «не определены»), узлы учёта. Предполагаемого оборудования нет.

## U. ExpectedQuantity

Контракт `CalcExpectedQuantityRead` (`contracts/calc/passport.py`): стабильный ключ
(`vk.b1.pipe.riser`), система, область, сценарий, категория (PIPE, INSULATION, FITTING, VALVE,
EQUIPMENT, SUPPORT, SLEEVE, CONNECTION, OTHER), тип, описание, функция участка, технические
характеристики, материал и типоразмер (пусто — UNKNOWN), значение или диапазон, единица, база и
резерв TENDER_SAFE раздельно, полнота, происхождение (OBSERVED, CALCULATED, TOPOLOGY, RULE,
FALLBACK, AGGREGATE), запуски расчёта и синтеза, элементы графа, результаты, версии правил,
допущения, предупреждения, блокирующие неопределённости, составляющие, пояснение. Хранение —
таблица `calc_expected_quantities` (значение, диапазон, единица, типоразмер, материал — колонками,
тело — JSONB по контракту), уникальность (паспорт, сценарий, ключ).

## V. MINIMUM

Подтверждённые элементы и нижние границы диапазонов; тендерного резерва нет; каждая позиция с
числом несёт «Это нижняя оценка, не проектное решение».

## W. EXPECTED

Утверждённые инженерные правила; невыбранный диапазон остаётся диапазоном; резерва нет.

## X. TENDER_SAFE

EXPECTED плюс только утверждённое тендерное допущение `vk.tender.riser_length_reserve` (резерв
длины на стояк): база, резерв и итог хранятся раздельно. Глобального процента нет; допущение
меняет только свои позиции (трубы стояков и итог) — это закреплено тестом.

## Y. Calculation Passport

Паспорт системы (`calc_passports`): 1) система и назначение по документации; 2) использованные
факты; 3) не найдено — с тем, на что влияет и на что нет; 4) конфликты; 5) расчёт — результаты
ядра и сверки «документ — контроль»; 6) структура — элементы графа; 7) ожидаемые количества трёх
сценариев; 8) допущения; 9) неопределённости; 10) объяснение любой позиции до свидетельства.
Статус: READY / PARTIAL / BLOCKED; сводка «Quantor рассчитал» и «Главные проблемы».

## Z. Unresolved model

Неопределённость — ключ, что известно, что нужно, структурная ли, какие позиции блокирует и какие
нет. Источники: неподтверждённое назначение (`semantics`), неопределённости графа (`risers.count`,
`zones`, `topology`, `main.route`, `connections.length`, `outlets.route`…), заблокированные шаги
ядра (`step:<шаг>`) и недостающие входы. Это не список вопросов Заказчику — PROMPT 10.

## AA. UI

«Расчёты → ВК» (`/projects/{id}/calc/vk`, закрыт флагом): корпус и секция, кнопка «Рассчитать ВК»
(только с правом `calc.edit`), вкладки Обзор, Исходные данные, Расчёт, Структура, Объёмы,
Допущения, Неопределённости; вкладки сверки с ВОР нет. Обзор — статус системы, закрытость
обязательных данных, «Quantor рассчитал», главные проблемы. Позиция объёмов раскрывается:
составляющие («межэтажная часть 70,2 м на стояк», «магистраль — не определено»), база и резерв
отдельно, «почему это количество такое» — дерево до свидетельства. Итога «всего ВК» нет; частичный
итог — «подтверждено …». Адаптивно (моб. тап-цели ≥ 44 px, поля ввода 16 px).

## AD. Real-package trial

Прогон только на чтение на эталонном распознанном пакете АР вне git: блоки засеяны в
изолированную временную базу, как их пишет импорт; после прогона проект удалён, база удалена; в
репозиторий и отчёт не попали ни названия, ни адреса, ни значения объекта. Итог:

- сбор фактов — 180 утверждений за 0,35 с; готовность ВК — 0,36 с;
- назначение систем в АР не названо → все четыре паспорта BLOCKED с вопросом (0,08 с);
- после подтверждения назначения (4 факта) — PARTIAL; этажность в тексте АР не найдена →
  этажная структура «не определено» с точной причиной;
- после ввода этажности (1 факт) — квартирография не покрывает 3 этажа (у них нет экспликаций
  квартир): Quantor называет эти этажи, а не считает их нулём;
- после подтверждения «квартир нет» на трёх этажах — квартирография определена автоматически;
  межэтажный пролёт — «не определено»: отметки есть только у 5 этажей, высот этажей нет (разрезы в
  пакете — изображения, нового OCR нет);
- правил в пространстве нет → все количества «не определено» с названными причинами.

Вывод для гейта: объекту нужны текстовые высоты или отметки этажей (разрез, ведомость, ПЗ) и
легенда систем ВК; иначе инженер вводит 2–5 фактов вручную.

## AI. Limitations

- Калькуляторы не принимают решений инженера по диапазонам (механизм PROMPT 05 есть, в комплект
  ВК не подключён): диапазон остаётся диапазоном до документа или правила.
- Точка отсчёта стояков — уровень 1-го этажа; подземная часть — только правилом концевых
  участков. Подземные квартиры в квартирографию не входят.
- Секции с разной этажностью: этажи без квартир в секции подтверждаются нулём квартир.
- Этажи без квартирографии не считаются нулём — нужен явный ноль.
- Потребители вне квартир (встроенные помещения, ПУИ) только называются: их подключение не
  выбирается.
- Т4 не связан с числом стояков Т3: его стояки — документ или своё правило.
- Контрольного расчёта расходов и грубой трассировки нет — методики не реализованы.
- Переходы — только магистраль—стояк при известных диаметрах; разбивка по диаметрам без
  диаметров документа — UNRESOLVED_BREAKDOWN.
- Файл каталога требований `requirements.py` — данные, он длиннее 500 строк с PROMPT 02.
