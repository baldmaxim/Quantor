# PROMPT 04 — детерминированное расчётное ядро (Calculation Engine)

Дата: 2026-09-28. Пакет — [`_prompts/calc_portal_stage_p/`](../../_prompts/calc_portal_stage_p/Quantor_Opus_5.5_Prompts_Calculation_Portal.md),
задание PROMPT 04 в редакции владельца от 2026-09-28. Решение — [ADR-0030](../adr/0030-raschyotnyj-kontur-stadii-p.md),
раздел «Решения PROMPT 04». Предыдущий шаг — [03-rule-registry.md](03-rule-registry.md).

```text
Facts Registry ──(только чтение)──► Calculation Snapshot (неизменяемый, в запуске)
Rule Registry  ──(только чтение)──► Rule Resolution: ключ → утверждённая версия → id + отпечаток
Calculator Definition (код) ──► Dependency Graph ──► план ──► детерминированное исполнение шагов
──► Calculation Result ──► Explainability Trace
```

Реальных калькуляторов В1, Т3, Т4, К1, ОВ, ЭОМ и пожаротушения нет. Есть ядро и
демонстрационный калькулятор `test.vertical_length@1` на синтетике.

## A. Границы расчётного ядра

Ядро применяет утверждённые версии правил к подготовленному снимку фактов — и только.

| Ядро не делает                                         | Как обеспечено                                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| не читает PDF, не ищет документы, не запускает OCR/LLM | в модулях ядра нет таких зависимостей; вход — только снимок и версии правил           |
| не создаёт и не меняет факты, не решает конфликты      | реестр фактов только читается (`resolve_project`); тест сравнивает таблицы до и после |
| не утверждает и не меняет правила                      | реестр правил только читается; тест сравнивает версии и журнал решений                |
| не выбирает значение ВОР Заказчика                     | утверждения ВОР не допущены к расчёту (ограничение базы) и не проходят в снимок       |
| не придумывает значения, не применяет умолчания        | нет факта, правила, единицы — запуск BLOCKED с причиной                               |

Модули: `app/services/calc/engine/` — чистое ядро (`calculators`, `handlers`, `quantity`,
`numbers`, `policy`, `plan_types`, `planner`, `executor`, `trace`, `demo`, `catalog`, `hashing`) и
слой запусков (`inputs` — чтение реестров, `runs` — запуск, хранение, повтор, `reads` —
представления для API). Чистые модули не
импортируют базу, модели, реестр фактов, реестр правил и карантин — это проверяет тест.

## B. Определение расчёта (Calculation Definition)

`CalculatorDef` — код, версионируемый вместе с приложением: `calculator_id`, `version`, название,
вид (DEMO/ENGINEERING), раздел, системы, стадия, сценарии, обязательные поля области запуска, шаги,
итоговые результаты. Шаг (`StepDef`) — стабильный `step_key`, стабильный ключ правила (версию
выбирает запуск), допустимые типы правил, привязки входов правила к фактам (тип факта и поля
области) и к выходам других шагов, используемые выходы, признак шага допущения. Результат
(`ResultDef`) — ключ, название, шаг и выход, категория, явное округление.

Каталог (`catalog.CALCULATORS`) статический: ошибка в определении — ошибка импорта, а не расчёта.
Отпечаток определения (`calculator_sha256`) — канонический JSON без меток времени; запуск его
запоминает. Схемы расчёта в базе нет.

## C. Реестр обработчиков (Handler Registry)

`implementation_key` → `HandlerSpec` — проверенная функция Python в статическом словаре. `eval`,
`exec`, загрузки модулей по имени и кода из базы нет (проверяется разбором AST всех модулей ядра).

Обработчик:

- получает `HandlerContext` — неизменяемые (`MappingProxyType`) входы и параметры версии правила
  как величины в рабочих единицах; сессии, запроса, реестров он не видит;
- возвращает выходы в объявленных единицах и детерминированное пояснение со своими числами;
- объявляет контракт (имена и единицы входов, параметров, выходов) и контрольные примеры.

Запуск сверяет контракт версии правила с контрактом обработчика (имена и совместимость единиц) и
привязки калькулятора с входами правила. Несовпадение — BLOCKED `RULE_CONTRACT_MISMATCH`.

## D. Снимок расчёта (Calculation Snapshot)

Снимок строится при старте запуска из `resolve_project` реестра фактов и хранится в самом запуске
(`calc_runs.snapshot`, контракт `CalcSnapshot`). В нём только факты, которые запуск использует.
На каждый факт: ключ, тип, место, утверждение-носитель и его версия, каноническое значение и как
значение было заявлено («3300 мм» → 3,3 м), способ получения, уверенность, проверка человеком,
способ выбора значения, источник и его класс, участвовавшие утверждения, ссылки на свидетельства
(ревизия, страница, фрагмент, блок распознанного пакета), `calculation_eligible = true`, отпечаток
записи. Отпечаток снимка — по отпечаткам записей.

Снимок строже «действующего значения» реестра фактов — в расчёт не попадает ничего с открытым
вопросом:

| Состояние ключа                           | В снимке | Причина блокировки    |
| ----------------------------------------- | -------- | --------------------- |
| одно утверждение, согласные, решено       | да       | —                     |
| решение устарело (пришли новые)           | нет      | `FACT_DECISION_STALE` |
| расхождение, значение по политике         | нет      | `FACT_CONFLICT`       |
| расхождение без решения                   | нет      | `FACT_CONFLICT`       |
| только не допущенные (ВОР Заказчика)      | нет      | `FACT_EXCLUDED`       |
| все отклонены проверкой / утверждений нет | нет      | `FACT_MISSING`        |
| диапазон, текст вместо числа              | нет      | `FACT_NOT_EXACT`      |

«Наиболее вероятное» не выбирается: даже значение, которое реестр фактов взял бы по политике
приоритета при открытом конфликте, в расчёт не идёт до решения человека (сценарий B). Утверждение,
не допущенное к расчёту или из ВОР Заказчика, в снимке — нарушение инварианта: сборка падает, а не
пропускает его.

## E. Выбор правил (Rule Resolution)

На старте: стабильный ключ → утверждённая версия, действующая на дату запуска (`effective_on`) →
id версии, номер, отпечаток содержания, `implementation_key`, отпечаток семантики обработчика →
`CalcRuleBinding` в запуске вместе с полным содержанием версии.

- DRAFT, REJECTED, DEPRECATED в новый запуск не выбираются (`RULE_NOT_APPROVED` с перечнем
  статусов версий); правил старого портала в таблицах реестра нет вовсе (`RULE_NOT_FOUND`).
- Вне дат действия — `RULE_NOT_EFFECTIVE`; не та система или стадия — `RULE_NOT_APPLICABLE`.
- Тип версии не из допустимых шагом или сценарием — `RULE_TYPE_NOT_ALLOWED`.
- DEPRECATED используется только при повторе исторического запуска — из его собственной
  привязки, а не из текущего реестра.

После старта смена действующей версии в реестре запуск не меняет: версия и содержание — в запуске.

## F. Жизненный цикл запуска

Запуск синхронный и укладывается в одну транзакцию запроса: снимок, выбор правил, план,
исполнение, запись. Поэтому промежуточных состояний («проверяется», «считается») снаружи не видно,
и записывается только итог:

| Статус      | Когда                                                  | Что записано                                  |
| ----------- | ------------------------------------------------------ | --------------------------------------------- |
| `BLOCKED`   | расчёт нельзя корректно начать — все найденные причины | снимок, привязки, причины                     |
| `SUCCEEDED` | исполнен                                               | снимок, привязки, шаги, результаты, отпечатки |
| `FAILED`    | проверка прошла, но обработчик упал — ошибка программы | снимок, привязки, шаг и текст ошибки          |

Нехватка данных — не HTTP-ошибка: `POST …/runs` отвечает 201 с запуском BLOCKED. Ошибка
обработчика — не 500: 201 с FAILED. Отдельная операция `…/runs/validate` показывает причины без
записи. Запуск фиксирует пространство, проект, калькулятор с версией и отпечатком, сценарий, область,
время, инициатора, снимок, точные версии правил, версии ядра и политик (`versions`), причины,
ошибку, допущения, предупреждения, отпечаток результата, ключ идемпотентности.

## G. Модель шагов

Шаг (`calc_run_steps`) хранит: стабильный `step_key`, позицию в порядке графа, статус
(`EXECUTED`, `REUSED`, `NOT_APPLIED`), правило (ключ, версия, тип, отпечаток, реализация), входы с
источником (факт — ключ и утверждение; шаг — ключ и выход; параметр версии правила), значения в
рабочих единицах, переводы единиц, выходы в единицах правила, округления, пояснение с числами,
отпечаток шага, источник повторного использования, запись о допущении. По шагу видно, откуда
взялось число.

## H. Граф зависимостей (DAG)

До исполнения: уникальность ключей шагов и результатов, ссылки на существующие шаги и выходы,
привязка входов из полей области, которые калькулятор требует, отсутствие циклов, правила для
шагов допущения. Порядок — алгоритм Кана, при равенстве — порядок объявления: порядок
детерминирован. Цикл `A → B → C → A` — ошибка определения: в каталог такой калькулятор не попадёт
(ошибка импорта), а план с ним — BLOCKED `CALCULATOR_INVALID` до любой арифметики.

## I. Единицы

Каталог единиц PROMPT 01–02 (`units.py`) и векторы размерностей PROMPT 03 (`rules/dimensions.py`)
— второго каталога нет. Три уровня защиты:

1. **Правило** при сохранении — размерности выходов (PROMPT 03).
2. **План**: единица факта против входа правила и обработчика, выход шага-источника против входа
   потребителя, контракт версии против обработчика — несовместимо → `UNIT_INCOMPATIBLE` или
   `RULE_CONTRACT_MISMATCH`.
3. **Арифметика**: обработчик считает величинами `Quantity` с вектором размерности —
   произведение складывает векторы, сумма требует одинаковых; выход берётся только при совпадении
   размерности: `3,3 м × 24 эт. = 79,2 м`, а `3,3 м × 24 кПа` длиной не станет.

Обработчики работают в канонических единицах размерности (м, кПа, м³/ч) и счётчиках. Любой
перевод — из единицы факта, параметра или правила в рабочую и из рабочей в единицу выхода правила —
записывается в шаг (`3300 мм = 3,3 м`) и виден в объяснении. Перевод только точный: бесконечная
дробь отклоняется (правило PROMPT 01).

## J. Округление и точность

Всё — `Decimal`. Обработчик исполняется в контексте, где неточная операция — исключение (`Inexact`
перехвачен): деление с бесконечной дробью без явного округления делает запуск FAILED, а не
«примерно так». `79.199999999` взяться неоткуда. Округление — только явное, `CalcRoundingPolicy`
(способ `HALF_UP`/`CEILING`/`FLOOR` и шаг), и каждое записывается с «до» и «после». Числа хранятся
точной десятичной строкой (`ExactText`) без двоичного float.

Промежуточные значения не округляются: `2,95 × 3 = 8,85`, `8,85 × 3 = 26,55`, `26,55 × 1,07 =
28,4085`, округлён только итог — `28,5` (вверх до 0,1). Промежуточное округление, если его требует
инженерное правило, — часть обработчика и видно в шаге. Системные правила округления появятся с
калькуляторами PROMPT 05–06.

## K. Сценарии MINIMUM / EXPECTED / TENDER_SAFE

Политика сценариев (`policy.py`, `calc.scenario_policy.v1`) — жёсткие ограничения, а не
инженерное решение:

| Сценарий      | Допустимые типы правил                                                |
| ------------- | --------------------------------------------------------------------- |
| `MINIMUM`     | PHYSICS, GEOMETRY, NORMATIVE, MANUFACTURER, ENGINEERING               |
| `EXPECTED`    | то же                                                                 |
| `TENDER_SAFE` | то же + TENDER_ASSUMPTION — только в шаге, который его явно допускает |

Сколько трубы относится к какому сценарию, решают калькуляторы PROMPT 05–06 выбором шагов и
правил. Ядро не даёт применить недопустимое: обычный шаг не примет версию типа
TENDER_ASSUMPTION ни в одном сценарии (`RULE_TYPE_NOT_ALLOWED`), а шаг допущения в MINIMUM и
EXPECTED не применяется. Универсального «+10 %» нет.

## L. Допущения

Шаг допущения (`AssumptionSpec`) применяется только в TENDER_SAFE и только с утверждённой,
применимой к системе и стадии версией TENDER_ASSUMPTION (утверждение уже требует решения
ответственного лица, влияния и ограничений — PROMPT 03). Вне TENDER_SAFE или без такой версии шаг
`NOT_APPLIED`: значение входа передаётся без изменения, причина — в шаге, в объяснении и в
предупреждениях запуска. Поэтому без тендерных правил TENDER_SAFE ≡ EXPECTED — видимо, а не молча.

Запись о допущении (`CalcAssumptionRecord`) в запуске и шаге: правило и версия, применено ли и
почему, влияние словами из правила, база, значение, разница, затронутые результаты. Отдельной
таблицы допущений нет — это часть запуска.

## M. Модель результата

`CalcRunResult`: ключ, название, точное значение, единица, категория (`INTERMEDIATE`,
`ENGINEERING`), раздел и система, сценарий, шаг и выход-источник, явное округление. Это
инженерная величина запуска, а не позиция Расчётного паспорта: `ExpectedQuantity` с тремя
сценариями и описателем позиции для сверки с ВОР остаётся черновым контрактом до PROMPT 05–06.

## N. Объяснение (Explainability Trace)

`GET /calc/runs/{id}/results/{key}/trace` — дерево, собранное детерминированно из структуры
запуска, без модели: результат → округление → шаг (пояснение, отпечаток, источник повторного
использования) → версия правила (тип, формула, реализация, источники) → допущение → входы: факт
(значение, как заявлено, способ, уверенность, способ выбора) → свидетельства; выход другого шага →
его шаг и так до фактов; параметры версии правила; переводы единиц. Текст — пояснения шагов по
порядку графа и округление итога. Живой пример:

```text
Длина по всем стоякам (демо) = 169,5 м. Высота этажа 3,3 м × 24 эт. = 79,2 м;
79,2 м × 2 ст. = 158,4 м; Тендерный запас: 158,4 м × 1,07 = 169,488 м;
Округление: 169,488 м → 169,5 м: вверх до 0,1 — округление итогового значения по определению калькулятора
```

## O. Воспроизводимость

Одинаковые снимок, версии правил, калькулятор, сценарий → одинаковые значения и отпечаток
результата (T01; отпечаток запуска через API совпал с отпечатком расчёта без базы).
`POST /calc/runs/{id}/replay` пересчитывает исторический запуск из его снимка и его привязок, не
читая текущие реестры, и сравнивает отпечаток результата. Живой пример: запуск A (этажность 24,
запас v1) → изменили этажность на 25 и утвердили запас v2 → запуск B считает 82,5 м и 181,5 м, а
A по-прежнему 79,2 м и 169,5 м, повтор A даёт тот же отпечаток `273f163e…`.

Если калькулятора или реализации этой версии в коде больше нет или семантика реализации под тем
же ключом изменилась — повтор честно отказывает с причиной, а не считает новым алгоритмом.

## P. Версионирование реализации

Версия реализации — часть ключа: шаблон `implementation_key` PROMPT 03 требует суффикс `.vN`
(`test.vertical_length.v1`). Правило: семантика ключа не меняется никогда; новый алгоритм — новый
ключ, новая версия правила с этим ключом, утверждение.

Техническая защита — отпечаток семантики обработчика (`handler_semantics_sha256`): хеш контракта
и контрольных примеров. Запуск запоминает его в привязке. Контрольные примеры исполняются тестом
на каждом прогоне: изменили алгоритм под старым ключом — падают примеры; изменили и примеры —
меняется отпечаток, и повтор старых запусков отказывает. Хеш текста кода не используется: он
менялся бы от комментариев и форматирования. Версия ядра (`calc.engine.v1`), политики сценариев,
политики приоритета фактов, реестра типов фактов и формата снимка записываются в запуск.

## Q. Отпечатки

| Отпечаток                | Из чего                                                                                                                                      | Где                              |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| определение калькулятора | канонический JSON определения                                                                                                                | `calc_runs.calculator_sha256`    |
| запись снимка            | ключ, утверждение, версия, значение, заявленное, способ, выбор, участники                                                                    | `snapshot.items[].item_sha256`   |
| снимок                   | версия формата и отпечатки записей                                                                                                           | `calc_runs.snapshot_sha256`      |
| привязки правил          | шаг, ключ, версия, отпечаток содержания, реализация, отпечаток семантики                                                                     | `calc_runs.rule_bindings_sha256` |
| шаг                      | калькулятор и его отпечаток, шаг, сценарий, версия правила и отпечаток, реализация и семантика, входы, параметры, отпечатки шагов-источников | `calc_run_steps.fingerprint`     |
| результат                | калькулятор, версия, сценарий, значения результатов                                                                                          | `calc_runs.result_sha256`        |
| запрос                   | калькулятор, версия, сценарий, область — для идемпотентности                                                                                 | `calc_runs.request_sha256`       |

Меток времени, идентификаторов запусков и служебных полей в отпечатках нет.

### Повторное использование шагов и инвалидирование

Реализовано: шаг с тем же отпечатком, что у шага последнего успешного запуска того же калькулятора
в том же проекте, берёт результат оттуда — статус `REUSED` и `reused_from_run_id` (исходный
запуск, даже через цепочку). Надёжность держится на полноте отпечатка: другая версия правила,
реализация, вход или сценарий — другой отпечаток, и шаг считается заново. Только тот же проект, а
значит то же пространство: результаты не переходят между арендаторами. Отпечаток результата от
повторного использования не зависит. Анализ инвалидирования — сравнение запусков (раздел T):
какие шаги получили новый отпечаток и почему.

## R. Хранение

## S. Неизменяемость

Запуск записывается сразу в итоговом состоянии, обновлений в штатной работе нет вовсе. Поэтому все
три таблицы только дописываются: триггер `calc_runs_append_only` запрещает UPDATE и DELETE любым
путём, включая прямой SQL, — и для SUCCEEDED, и для BLOCKED и FAILED (это записи попыток).
Исключение одно — каскад при удалении проекта: триггер вызывается изнутри ссылочного действия
(`pg_trigger_depth() > 1`). Триггер объявлен и в модели, и в миграции; совпадение проверяет
`test_schema_matches_migrations`. Ограничения базы согласуют статус с содержимым: у SUCCEEDED есть
отпечаток результата, у BLOCKED — причины, у FAILED — ошибка, у REUSED — источник. Отсутствие в
JSONB пишется как SQL NULL, а не JSON `null`, иначе эти ограничения нельзя было бы проверить.

Исправление проекта — новый запуск; маршрутов изменения и удаления запуска нет (405).

## Y. Ограничения

- Калькуляторов систем нет — только демонстрационный; реестр правил пуст до подтверждённых
  источников.
- Входы обработчиков — только точные числа (NUMBER, COUNT). Перечисления, логические и текстовые
  входы понадобятся калькуляторам PROMPT 05 — контракт расширяется там.
- Все входы правила обязательны: признак «необязательный вход» правила ядро пока не использует —
  строже, чем объявлено, и без скрытых умолчаний.
- Область запуска — одно место (корпус, этаж, система). Перебор этажей, секций и стояков и сбор по
  ним — задача калькуляторов PROMPT 05.
- Запуск синхронный в запросе; для тяжёлых калькуляторов может понадобиться фоновое задание —
  решается замером в PROMPT 05–06 без новых типов заданий сейчас.
- Одна действующая утверждённая версия на правило (PROMPT 03): выбор по дате ограничен её датами.
- Повторное использование — только из последнего успешного запуска того же калькулятора в проекте.
- Экран запусков — диагностический: запуск и сравнение — через API.

## AA. Готовность к PROMPT 05

Для калькуляторов систем готово: определение калькулятора в коде, граф с проверкой, реестр
обработчиков с контрольными примерами и отпечатком семантики, снимок фактов с происхождением и
строгим допуском, выбор точных версий правил, единицы с размерностями, точная арифметика и явное
округление, политика сценариев и шаги допущений, запуски с неизменяемостью, повтор, сравнение,
объяснение.

Что понадобится PROMPT 05: перебор мест (этажи, секции, стояки) внутри калькулятора, нечисловые
входы обработчиков, первые реальные правила с подтверждёнными источниками (решение владельца),
системные правила округления и `ExpectedQuantity` поверх результатов. MEP semantic для ядра не
нужен.
