Правило принадлежит рабочему пространству: утверждённая версия меняет расчёты всех проектов
пространства, чужое пространство её не видит. Реестр фактов модуль правил не читает и не пишет —
это проверяется тестом по импортам (T15).

## B. Модель данных

Три таблицы. Отдельной таблицы на каждое свойство правила нет: строгую структуру держит контракт
Pydantic, база хранит и защищает.

| Таблица                 | Зачем                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `calc_rule_definitions` | стабильная идентичность правила: пространство, ключ без версии (`vk.riser.vertical_length`), раздел, автор, дата                                                                                                                                                                                                                                      |
| `calc_rule_versions`    | версия: номер, статус, тип, название, описание, формула-текст, `implementation_key`, входы, параметры, выходы, проверки размерности, применимость, источники (JSONB), влияние, даты действия, `content_sha256`, снимок происхождения из карантина, основание изменения, автор и последний редактор, кто и когда утвердил, вывел из действия, отклонил |
| `calc_rule_reviews`     | журнал решений: из какого статуса в какой, кто, когда, комментарий, разбор опасностей старых правил                                                                                                                                                                                                                                                   |

Почему журнал решений — отдельная таблица, а не общий журнал аудита: решение — часть
происхождения правила и читается вместе с версией (будущий запуск покажет, кто утвердил); журнал
аудита открыт правом `audit.read` и хранит события без структуры разбора. Аудит тоже пишется —
шесть действий `calc_rule_*`.

Чего нет: второго каталога единиц (используется каталог PROMPT 01–02), второго хранилища
пользователей (идентификаторы — значения без внешнего ключа, как в реестре фактов), второго
реестра фактов, таблиц для правил старого портала.

## C. Жизненный цикл правила

```text
DRAFT ──approve──► APPROVED ──deprecate──► DEPRECATED
  └────reject───► REJECTED
UNVERIFIED_LEGACY — только у записей карантина; в таблицах реестра этого статуса нет (CHECK)
```

| Статус              | Где живёт      | `calculation_eligible` | Меняется                                 |
| ------------------- | -------------- | ---------------------- | ---------------------------------------- |
| `DRAFT`             | таблица версий | нет                    | содержание — да; в APPROVED или REJECTED |
| `APPROVED`          | таблица версий | да, в пределах дат     | только в DEPRECATED                      |
| `DEPRECATED`        | таблица версий | нет                    | нет; читается по номеру                  |
| `REJECTED`          | таблица версий | нет                    | нет                                      |
| `UNVERIFIED_LEGACY` | карантин       | нет, никогда           | нет, никогда                             |

`calculation_eligible` вычисляется (`validation.calculation_eligible`): только `APPROVED`, и
дата расчёта внутри `valid_from…valid_to`. Пользователь его не задаёт: поле `status` в запросе
отклоняется как лишнее.

Переходы запрещены явно: APPROVED → DRAFT, DEPRECATED → APPROVED, REJECTED → что угодно. Версию
утверждает не её автор и не последний, кто правил черновик (`edited_by`, `CALC_RULE_SELF_APPROVAL`):
инженерная проверка — второй человек. Роль
проверяющего (`calc.verify`) утверждает, роль инженера (`calc.edit`) пишет черновики.

## D. Версия и неизменяемость

Ключ правила стабилен и не содержит версии; версия — номер `1, 2, …` внутри ключа. Ссылка на
правило для запуска — `rule_key@version` плюс `content_sha256` (отпечаток канонического JSON
содержания); контракт `CalcRuleReference` для PROMPT 04 уже есть.

Изменение формулы, параметра, единицы, применимости, источника или реализации — только новая
версия (`POST /rules/{key}/versions`, основание изменения обязательно). На правило открыт один
черновик. Утверждение новой версии выводит прежнюю утверждённую из действия той же транзакцией
(«Заменена утверждённой версией N»): для нового расчёта у правила одна действующая версия, а
старая читается по номеру с тем же содержанием и отпечатком.

### Гарантии неизменяемости

Защита на трёх уровнях, главный — база:

1. **API/сервис.** `PUT` утверждённой версии — 409 `CALC_RULE_NOT_DRAFT`; переходы проверяются под
   транзакционной блокировкой правила.
2. **Схема.** CHECK: статус только из собственных (`own_statuses`); утверждённая и устаревшая
   версии имеют отметку утверждения и реализацию; отметки вывода и отклонения согласованы со
   статусом; частичные уникальные индексы — один черновик и одна утверждённая версия на правило.
3. **Триггер `calc_rule_versions_guard`** (BEFORE UPDATE OR DELETE):
   - версию не в статусе DRAFT удалить нельзя;
   - идентичность версии (ключ правила, номер, автор, время создания) не меняется никогда;
   - у APPROVED меняются только статус (→ DEPRECATED) и поля вывода из действия — сравнение строк
     целиком, поэтому новая колонка защищена автоматически;
   - DEPRECATED и REJECTED не меняются совсем.

   Определение правила (`calc_rule_definitions`) и журнал решений (`calc_rule_reviews`) только
   дописываются — триггер `calc_rules_append_only`.

Почему триггер, а не только события ORM: событие ORM не видит прямой `UPDATE` и массовые
запросы; триггер ловит любой путь записи, включая `psql`. Приём тот же, что у журнала аудита
(ADR-0010): тело триггера объявлено и в модели (`after_create` — тестовая база строится из
метаданных), и в миграции; совпадение проверяет `test_schema_matches_migrations` (добавлена
сверка триггеров и тел функций). `TRUNCATE` строковых триггеров не вызывает — очистка тестовых
таблиц работает, в бою `TRUNCATE` не используется.

Пример отказа (живой прогон):

```text
PUT /calc/rules/test.ov.valve_count/versions/1        → 409 CALC_RULE_NOT_DRAFT
UPDATE calc_rule_versions SET formula_text = … (ORM)  → calc_rule_versions: APPROVED version is immutable, create a new version
DELETE FROM calc_rule_versions WHERE version = 1      → calc_rule_versions: APPROVED version cannot be deleted
```

## E. Контракты входов и выходов

Правило объявляет, что ему нужно и что оно даёт, — без исполнения (формула на этом шаге не
выполняется):

- вход `FACT` — тип факта реестра фактов и единица; вход `QUANTITY` — величина другого шага
  (связывание — PROMPT 04);
- параметр — константа версии (`DecimalText`) с единицей и происхождением словами;
- выход — величина (`pipe.length`) с единицей;
- проверка размерности — члены суммы как произведения входов и параметров в степенях.

По контракту PROMPT 04 проверит: переданы ли входы, совместимы ли единицы, какой результат
ожидается. Реестр при сохранении уже проверяет: тип факта существует; единица входа совместима с
единицей типа факта; у нечислового факта единицы нет; имена не повторяются; выход размерности
объявлен.

## F. Единицы

Каталог единиц PROMPT 01–02 (`app/contracts/calc/units.py`) не дублируется и не расширялся.
Размерность единицы — вектор степеней базовых величин (длина, давление, расход, суточный объём,
температура; площадь — длина², счётчики безразмерны). Это не символьная математика: правило
объявляет члены, реестр сверяет векторы.

- `m × floor + m → m` — проходит;
- `m × kPa` как длина — отклоняется: «длина × давление, а выход — длина»;
- единица вне каталога (`kg`) — отклоняется как неизвестная: масса в контуре пока не нужна, и
  каталог расширяется только при доказанной необходимости.

## G. Происхождение (provenance)

Источники — типизированный список, различаемый по `kind`: нормативный документ, документ
производителя, инженерная методика, решение владельца, решение проверяющего, код старого портала,
другой явно описанный источник. Список источников одной строкой (`source_label`) виден в списке
правил. Для утверждения нужен хотя бы один источник, кроме кода старого портала: старый код —
происхождение, а не основание. Разбор старых правил и итог по каждой опасности хранится в журнале
решений; снимок каталога (версия каталога, класс, действия, опасности, группы) — в версии.

ВОР Заказчика основанием быть не может: упоминание ВОР или «ведомости объёмов» в тексте источника,
в происхождении константы или во влиянии тендерного допущения — ошибка содержания (T16).

## H. Нормативные правила

Источник `NORMATIVE_DOCUMENT`: название, обозначение, редакция или изменение, пункт или раздел,
страница, дата редакции, локальный файл. Обозначение, редакция, пункт и дата обязательны в
контракте — «по СП» без пункта не сохранить. Правило типа `NORMATIVE` без такого источника не
утверждается. Реальных нормативных правил не заведено: подтверждённых документов в репозитории нет,
модель как нормативный источник не используется.

## I. Правила производителей

Источник `MANUFACTURER_DOCUMENT`: производитель, линейка, документ, версия, дата, таблица или
страница, область применения. Утверждение требует, чтобы область применения правила называла
того же производителя и ту же линейку: правило производителя A не применяется к B.

## J. Инженерные правила

`ENGINEERING` утверждается только с источником `ENGINEERING_METHOD` (название, автор,
где опубликована, суть) и названными ограничениями; область применения обязательна в контракте.
Корзиной для неизвестных коэффициентов старого портала он не служит: неизвестное происхождение
остаётся в карантине.

## K. Тендерные допущения

`TENDER_ASSUMPTION` — отдельный тип. Каждый ответ по версии и строка списка несут
`notice`: «Это не норматив и не факт документации. Это тендерное допущение.»; экран показывает это
под названием. Утверждение требует решения ответственного лица (`OWNER_DECISION` или
`REVIEWER_DECISION`: кто, когда, где зафиксировано, основание), описанного влияния на результат и
ограничений. Методика решение не заменяет. Сценарий `TENDER_SAFE` здесь не реализован.

## L. Карантин старых правил

### Почему старые правила не в рабочей базе

- У них нет проверенных контрактов входов и выходов, единиц и источников — в таблицы версий они
  легли бы с пустыми обязательными полями или с выдуманными.
- 365 строк с особым статусом пришлось бы отфильтровывать в каждом запросе реестра; одна
  забытая фильтрация — и старое правило в выдаче рядом с утверждёнными.
- Каталог — данные разбора PROMPT 00, у него своя версия и отпечаток. Он меняется только новой
  сборкой из разбора, а не правкой через API.

Поэтому таблицы реестра принимают только собственные статусы Quantor (CHECK `own_statuses`), а
365 записей лежат в данных пакета и читаются только через API карантина.

### Каталог

`app/services/calc/rules/data/legacy_catalog.json` — канонический машиночитаемый каталог:
`catalog_version` (`calc.legacy_catalog.v1`), `generator_version` (`calc.legacy_build.v1`),
`entry_count` = 365, `source_sha256` (отпечаток входов: пять каталогов разбора и файл находок),
`content_sha256` (отпечаток записей и групп). Каждая запись хранит дословное место в старом коде и
разобранные ссылки (файл, строки, функция), текст правила, класс PROMPT 00 (основной и
дополнительные, дословная запись), допущения и замечания, предлагаемое действие (дословно и
кодами), признаки опасности, группы. Статус у всех `UNVERIFIED_LEGACY`,
`calculation_eligible = false`, пометка «НЕ ПРОВЕРЕНО / НЕ ИСПОЛЬЗУЕТСЯ В РАСЧЁТЕ».

Признаки опасности выделяются по явным словам разбора и дополняются курированными находками
(`data/legacy_findings.json`); член группы с разными константами получает
`CONFLICTING_CONSTANTS`, класс «ошибочное» — `DEFECT`. Пустой список признаков не доказывает, что
правило безопасно.

### Модель продвижения старого правила

```text
запись карантина → человек заводит НОВЫЙ черновик (свой ключ, версия 1)
→ старая запись — происхождение (LEGACY_CODE), опасности переносятся в снимок версии
→ инженер задаёт входы, параметры, реализацию и основание по типу
→ проверяющий записывает итог по каждой опасности → APPROVED получает только новое правило
```

Смены статуса старой записи нет и не будет: у неё нет ни контракта, ни основания, и «утвердить
старое» значило бы утвердить неизвестное. Новый черновик переносит только текст — как исходный
материал: формулу старого правила для человека, замечания разбора в пояснение, место в коде в
происхождение. Тип правила выбирает человек: класс разбора не переносится (эвристика не
становится методикой от переноса). Реализации нет, входы и параметры пусты — такой черновик не
утвердить, пока инженер их не задаст. Записи «вне контура» (цены, НДС, импорт счетов) черновиком
не становятся (`CALC_LEGACY_OUT_OF_SCOPE`).

Разбор опасностей при утверждении — по каждой: `CONFIRMED_SAFE` (проверено, не проявляется),
`FIXED` (была и устранена), `NOT_APPLICABLE` (эта часть старого правила не взята), `REJECTED`
(подтверждена и не устранена — утверждение блокируется). Комментарий обязателен у каждого итога,
одна опасность — один итог. Флажка «проверено» недостаточно.

Пример (живой прогон, `LEG-OV-037` — двойное умножение числа клапанов):

```text
POST /calc/legacy-rules/LEG-OV-037/drafts        → 201 test.ov.valve_count@1 DRAFT,
                                                    legacy_provenance.hazards = [DEFECT, DOUBLE_MULTIPLICATION]
GET  /calc/legacy-rules/LEG-OV-037               → UNVERIFIED_LEGACY, calculation_eligible = false (не изменилась)
POST …/versions/1/approve (итог только по DOUBLE_MULTIPLICATION)
                                                 → 422 CALC_RULE_APPROVAL_BLOCKED
                                                   «LEG-OV-037: нет решения по опасностям: DEFECT»
POST …/versions/1/approve (FIXED + NOT_APPLICABLE, с комментариями)
                                                 → 200 APPROVED; журнал хранит итог по каждой опасности
```

### Упаковка

Каталог — данные Python-пакета: `pyproject.toml`, `[tool.setuptools.package-data]`
`"app.services.calc.rules" = ["data/*.json"]` — по образцу сценариев MEP. Рабочий код читает его
`importlib.resources.files("app.services.calc.rules")`, без путей к репозиторию и к `docs/`. При
загрузке сверяются `entry_count` и `content_sha256` — подменённый или обрезанный каталог не
читается (`LegacyCatalogError`).

Проверено тремя способами: тест загрузчика (T23); тест, который упаковывает пакет в zip по
шаблонам package-data и загружает каталог в отдельном процессе без рабочей копии (T23); ручная
сборка колеса `setuptools.build_meta` — `legacy_catalog.json` внутри колеса, каталог из 365
записей читается и из распакованного колеса, и прямо из zip.

Сборщик зависит от `docs/calc/legacy/*.md` и запускается разработчиком:
`python -m app.services.calc.rules.legacy_build`. Сборка детерминирована: порядок строк —
порядок каталогов и строк разбора, ключи и отступы фиксированы, перевод строк рабочей копии не
меняет отпечаток, путей машины в каталоге нет. Тест собирает каталог дважды и сверяет с пакетом
и смыслово, и побайтно (T24).

## M. Что произошло с 365 правилами старого портала

Все 365 — в карантинном каталоге, ни одно не в таблицах реестра, ни одно не утверждено, ни одно
не допущено к расчёту. Идентификаторы сверены с разбором PROMPT 00 независимым поиском строк
`| LEG-…` (T13).

## N. API

Все пути под `/api/v1/calc/`, флаг `calc.portal`, права `calc.*`; удаления нет ни у одной версии.

| Операция                                                                                               | Право         |
| ------------------------------------------------------------------------------------------------------ | ------------- |
| `GET /calc/rules` — список, фильтры `discipline`, `system`, `rule_type`, `status`                      | `calc.read`   |
| `POST /calc/rules` — новое правило, версия 1 DRAFT                                                     | `calc.edit`   |
| `GET /calc/rules/{rule_key}` — правило и все версии с решениями                                        | `calc.read`   |
| `GET /calc/rules/{rule_key}/versions/{version}` — любая версия, и устаревшая                           | `calc.read`   |
| `PUT /calc/rules/{rule_key}/versions/{version}` — правка только черновика                              | `calc.edit`   |
| `POST /calc/rules/{rule_key}/versions` — новая версия с основанием                                     | `calc.edit`   |
| `POST …/versions/{version}/approve` — утверждение с разбором опасностей                                | `calc.verify` |
| `POST …/versions/{version}/reject` — отклонение с причиной                                             | `calc.verify` |
| `POST …/versions/{version}/deprecate` — вывод из действия с причиной                                   | `calc.verify` |
| `GET /calc/legacy-rules` — карантин, фильтры `catalog`, `legacy_class`, `hazard`, `action`, `group_id` | `calc.read`   |

Изменить, удалить, утвердить или вывести из действия запись карантина нельзя — таких маршрутов
нет (405/404, проверено тестом). Удаление черновика не нужно: ненужный черновик отклоняется с
причиной и остаётся в истории. Источник правила виден в версии целиком и строкой в списке —
отдельной операции «просмотр источника» не понадобилось. Коды отказов: `CALC_RULE_KEY_TAKEN`,
`CALC_RULE_CONTENT_INVALID`, `CALC_RULE_NOT_DRAFT`, `CALC_RULE_DRAFT_EXISTS`,
`CALC_RULE_TRANSITION_INVALID`, `CALC_RULE_APPROVAL_BLOCKED` (текст — что именно не так),
`CALC_RULE_SELF_APPROVAL`, `CALC_LEGACY_OUT_OF_SCOPE`.

Совместимость OpenAPI: добавлено 10 путей (12 операций) и 40 схем `Calc*`; ни одна прежняя
схема и ни один прежний путь не изменились, схемы MEP не переименованы. Клиент `@quantor/api-client`
сгенерирован заново.

## O. Экран

«Расчёты → Правила» (`/projects/{id}/calc/rules`, кнопка «Правила» на экране расчётов), за флагом,
только чтение. Два раздела:

- **Правила Quantor**: правило (название, ключ, пометка тендерного допущения) | версия
  (`v2 · утв. v1`) | система | тип | статус | источник | в расчёте;
- **Старый портал — карантин**: Legacy ID | система | правило | класс | опасности | предлагаемое
  действие | статус «НЕ ПРОВЕРЕНО» и «В РАСЧЁТЕ НЕ ИСПОЛЬЗУЕТСЯ»; фильтр по системе.

Редактора правил нет — черновики и решения идут через API. На телефоне строка таблицы
разворачивается в карточку, как на экране исходных данных.

## S. Известные ограничения

- Реальных правил нет: ни одного нормативного, производительского или инженерного документа в
  репозитории не подтверждено, поэтому реестр пуст до решения владельца по источникам.
- Реализаций по `implementation_key` нет — исполнитель правил появится в PROMPT 04; до него
  ключ проверяется только по форме.
- Выбор версии по дате: у правила одна утверждённая версия; даты действия ограничивают её, но
  «норма 2020 до 2025, норма 2025 после» одновременно не хранится — прежняя выводится из действия.
  Воспроизведение старого расчёта от этого не зависит: запуск ссылается на номер и отпечаток.
- Проверка ВОР в тексте основания — по словам; скрытую ссылку на ВОР другими словами ловит только
  проверяющий.
- Проверка размерностей — по объявленным членам: неверно объявленные члены проверка не заметит,
  это остаётся за проверяющим и за golden-векторами PROMPT 04.
- Черновик по старому правилу переносит только текст: входы, параметры и реализацию инженер задаёт
  сам.
- Экран — только чтение; решения по правилам — через API.
- Сборщик карантина требует `docs/calc/legacy/*.md` и запускается из рабочей копии; установленное
  приложение читает только готовый JSON.

- Поиск и заведение нормативов, документов производителей и методик.
- Редактор правил в интерфейсе и админке.
- Удаление версий через API.
- Импорт старых правил в таблицы реестра и автоматический перенос их констант.

## U. Готовность к PROMPT 04

Готово для ядра:

- ссылка на версию правила `CalcRuleReference` (ключ, номер, `content_sha256`, тип, статус) и
  неизменяемость того, на что она ссылается;
- типизированные входы (тип факта или величина шага) с единицами, параметры `DecimalText`, выходы
  с единицами, проверка размерностей;
- `calculation_eligible` и даты действия — ядро выбирает только утверждённые действующие версии;
- `implementation_key` — место для детерминированной реализации без кода в базе;
- тендерные допущения отделены типом и пометкой для будущего `TENDER_SAFE`;
- карантин доступен ядру только как справка и никогда как правило.

Чего ядру не хватает и что решает PROMPT 04: реестр реализаций по `implementation_key`,
golden-векторы на версию реализации, снимок фактов и связывание входов `QUANTITY` между шагами,
выбор версии на дату запуска. Для реального пилота нужны подтверждённые источники правил ВК —
решение владельца.
