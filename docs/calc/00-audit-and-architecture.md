# Расчётный контур стадии П — аудит и архитектура

PROMPT 00 пакета [`_prompts/calc_portal_stage_p/`](../../_prompts/calc_portal_stage_p/Quantor_Opus_5.5_Prompts_Calculation_Portal.md),
2026-09-26. Статус — **принято 2026-09-28** с корректировками владельца: [ADR-0030](../adr/0030-raschyotnyj-kontur-stadii-p.md),
раздел «Уточнения владельца при принятии». Где этот отчёт расходится с ADR, действует ADR. Production-код, миграции, флаги
и `CLAUDE.md` в этом промте не менялись.

Разбор старого портала — в [00-legacy-portal-analysis.md](00-legacy-portal-analysis.md) и каталогах
[legacy/](legacy/vk.md).

## 0. Итог

- Расчётный контур — **отдельный детерминированный контур `calc`** внутри существующих `apps/api` и
  `apps/web`: реестр фактов → требования к входам → расчётное ядро с реестром правил (синтез
  системы — шаги ядра) → Расчётный паспорт системы → сверка с ВОР Заказчика → вопросы.
- Контур ничего не пишет в обмер, MEP и распознавание: он читает их через адаптеры источников.
  Ядро видит только факты и не знает, откуда они пришли.
- Флаг `calc.portal` объявляется выключенным и **не включается из админки** до гейта на реальном
  объекте после PROMPT 06: по ADR-0023 пилотный флаг означает «сделано и проверено».
- Числа — Decimal с именованными шагами округления; единицы с размерностями и типизированными
  счётчиками. Сценарии MINIMUM / EXPECTED / TENDER_SAFE считаются в одном запуске и проверяются
  инвариантами. «Не определено» никогда не показывается как 0.
- LLM в MVP нет. Выход модели позже — только кандидат, не факт. ВОР Заказчика — объект сверки, а
  не эталон: его данные в расчёт не попадают, качественные факты из ВОР исключены из снимка ядра
  (`calculation_eligible = false`).
- MEP semantic сейчас не нужен; позже он подключается как поставщик фактов без правки ядра.
- Старый портал даёт идеи и контрольные случаи, но не правила: из 365 правил нормативных ноль.
- Нужны решения владельца до PROMPT 01 — раздел 10.

## 2. Старый портал: что следует для архитектуры

Подробно — [00-legacy-portal-analysis.md](00-legacy-portal-analysis.md). Для архитектуры важно:

- 365 правил, из них нормативных 0, потенциально ошибочных 52, неизвестного происхождения 54,
  тендерных коэффициентов 26 → реестр правил обязан хранить статус проверки и не принимать
  «неизвестное» за норматив.
- Дубли правил с разными константами → одно правило — одна запись с версией; калькулятор ссылается
  на правило, а не копирует число.
- Двойное умножение и смешение единиц → единицы с размерностями и типизированные счётчики.
- Молчаливые умолчания → требования к входам с явной политикой допущений.
- Скрытые тендерные коэффициенты → только зарегистрированные `TENDER_ASSUMPTION`, выбранные в
  проекте, с отдельным компонентом резерва.
- Сохранённые проекты — не эталон → инженерный эталон появляется только на гейте после PROMPT 06.

## 3. Предлагаемая архитектура (B)

### 3.1. Цепочка

```text
АР, квартирография, таблицы Region (TEXT), обмеры, ручной ввод
  │ Source Adapters — единый протокол поставщика фактов
  ▼
Facts Registry — утверждения, источники, свидетельства, конфликты, решения
  │ снимок для ядра — только утверждения с calculation_eligible = true
  │ Input Requirements — REQUIRED / DESIRABLE / OPTIONAL / DERIVABLE, политика допущений
  ▼
Calculation Engine — DAG шагов, правила из Rule Registry, три сценария
  │   └ синтез системы — шаги ядра: граф системы с происхождением и диапазонами (артефакт запуска)
  ▼
CalculationResult (расходы, зоны, DN, стояки) + ExpectedQuantity → Расчётный паспорт системы
  ▼
VOR Reconciliation — ExpectedQuantity ↔ CustomerVorItem (ВОР Заказчика приходит только сюда);
  сравнение количеств кодом, допуски по классам позиций
  ▼
Questions & Uncertainty — вопросы по чувствительности, конфликтам, расхождениям (в количествах)
```

### 3.4. Факты

- **Утверждение** (`ProjectFact`) — неизменяемая запись «источник S утверждает, что факт K имеет
  значение V»: метод получения, надёжность, свидетельства, статус проверки, порядковый номер версии
  внутри ключа.
- **Ключ факта** = тип + субъект + квалификаторы.
  - Тип — из реестра типов в коде: вид значения, размерность и каноническая единица, допуск
    сравнения, допустимые квалификаторы, наследование вниз по иерархии, агрегатные связи, русское
    название, признак `quantity_like`.
  - Субъект — место (корпус → секция → этаж или группа этажей → квартира → помещение; паркинг,
    стилобат) или элемент системы (например, стояк К1-3 системы В1). Переименование меняет только
    подпись, слияние — версионированный псевдоним.
  - Квалификаторы — закрытый набор на тип (система, тип квартиры, типоразмер), каноническая
    сортировка.
- **Виды значений**: число с единицей, типизированный счётчик, перечисление, логическое, текст,
  **диапазон** («17–25 этажей», «до 25»), **ссылка на артефакт** по sha256 (топология, граф).
- **Источник** (`FactSource`): класс (АР, квартирография, ВК П, ТУ, ВОР Заказчика, ручной ввод,
  обмер, позже MEP), **заявленная стадия** документа (П, РД, неизвестно), раздел, серия для
  замещения новой версией, ссылка на ревизию или файл. Задаётся при импорте, аудитируется и не
  пишется в ревизию (ADR-0003).
- **Свидетельство** (`FactEvidence`): ячейка таблицы Region (id, sha256 текста, таблица, строка,
  колонка, сырой текст ячейки); ячейка файла; обмер с версией, калибровкой, правилом, отпечатком
  входа и значением; ручной ввод (автор, время, основание); допущение (правило, основание,
  альтернативы — для анализа чувствительности).
- **Методы**: `DOCUMENT_EXPLICIT`, `TABLE_EXPLICIT`, `GEOMETRY_MEASURED`, `CALCULATED`, `INFERRED`
  (только по зарегистрированному детерминированному правилу), `NORMATIVE`, `MANUFACTURER_RULE`,
  `ASSUMPTION`, `MANUAL`.
- **Идемпотентность и замещение**: повторный импорт того же файла ничего не меняет; новый член
  серии замещает утверждения старого, а исчезнувшие ключи попадают в явный отчёт; изменение
  обмера помечает утверждение устаревшим; утверждения отзываются, а не удаляются.
- **Конфликт** — расхождение значений одного ключа вне допуска после явного перевода единиц
  (неверная размерность — ошибка данных при приёме). Допуск задаётся типом:
  \|a − b\| ≤ max(abs, rel·max(\|a\|, \|b\|)). Внутри допуска — подтверждение. Есть и агрегатные
  конфликты: сумма квартир по секциям ≠ итогу по корпусу, строки таблицы ≠ «Итого».
- **Эффективное значение** — детерминированно и никогда молча:
  1. берутся активные утверждения; свидетельства из одного и того же PDF (загруженного сырым и в
     пакете) сворачиваются — это не два независимых подтверждения;
  2. есть решение человека (`ManualOverride`) и набор утверждений не изменился (`claim_set_hash`) —
     значение решения; набор изменился — решение действует, конфликт `REOPENED`, предупреждение.
     Решение отвечает на расхождение: если расхождения больше нет (проигравшее утверждение
     отклонено или отозвано), решать нечего — конфликт `OBSOLETE`, значение по согласию;
  3. все согласны — значение со статусом `CORROBORATED`;
  4. расходятся — политика (тип факта, класс источника, стадия)@версия: `auto_prefer` только при
     единственном лидере (`AUTO_PREFERRED`, конфликт остаётся открытым и виден в запуске), иначе
     `UNRESOLVED` — как отсутствие значения.

  По умолчанию политика — `manual_required`; `auto_prefer` разрешается перечнем типов. Глобальной
  истины вроде «спецификация всегда главнее плана» нет.

- **Надёжность** — категория, вычисляемая версионированной функцией от метода, проверки,
  конфликта и признаков свидетельства, а не произвольное число.
- **Требования к входам**: калькулятор объявляет требование = тип факта + шаблон субъекта +
  уровень (REQUIRED, DESIRABLE, OPTIONAL, DERIVABLE) + правила вывода + политика допущения (нельзя /
  по зарегистрированному правилу / только ручной ввод) + на что влияет. Отчёт полноты отвечает «для
  В1 нужно N параметров, найдено 12, отсутствует 4» и называет причину каждого пропуска. REQUIRED
  без разрешённого допущения даёт результат «не определено», а не 0.
- **Кандидаты** (`CalcFactCandidate`) — отдельный тип и отдельное хранение: выход модели, описания
  IMAGE-блоков. В сценарии не входят. Принятие доверенным сервисом создаёт обычное утверждение с
  происхождением `model_assisted` и хешами модели, запроса, входа и выхода (образец ADR-0022).

### 3.5. Правила

- Типы: `PHYSICS`, `GEOMETRY`, `NORMATIVE`, `MANUFACTURER`, `ENGINEERING`, `TENDER_ASSUMPTION`.
  Поля — по PROMPT 03, плюс русский шаблон отображения формулы (PROMPT 11: без JSON и ID).
- Жизненный цикл: `DRAFT` (изменяем; запуски на нём помечены «черновик, не воспроизводим») →
  `RELEASED` (неизменяем, хеш содержимого в `rules.lock.json`, тест).
- Статус проверки хранится отдельно от содержимого и в хеш не входит: `DRAFT`, `UNVERIFIED_LEGACY`,
  `SOURCED`, `VERIFIED` (с именем проверяющего и датой), `REJECTED`, `REJECTED_LEGACY`, `DEPRECATED`.
  Снимок статуса — в каждом запуске.
- `NORMATIVE` — только с документом, пунктом и редакцией; тест не пропускает нормативное правило без
  них.
- Алгоритмы только добавляются: `vk.riser_length.v1` не правится, исправление — `v2`, как `count.v1`
  и `area_with_holes.v1` в обмере. На каждую версию алгоритма — golden-векторы с точным равенством;
  калькуляторы тоже версионируются (`vk.passport.v1`) и закреплены golden-зданиями.
- Хранение: содержимое — JSON или TOML в git (YAML добавил бы зависимость); в БД — снимки по хешу,
  на которые ссылаются запуски (с PROMPT 04).
- `TENDER_ASSUMPTION` выбирается в проекте явно; выбор фиксируется в запуске.
- Старый портал: кандидаты — `UNVERIFIED_LEGACY`; класс «ошиб» — `REJECTED_LEGACY` (для
  классификации различий `LEGACY_BUG`); расходящиеся константы — отдельные записи с указанием места.
  Fallback допустим только там, где калькулятор объявил его для конкретного шага, никогда в
  MINIMUM, с предупреждением `LEGACY_FALLBACK` в паспорте и понижением надёжности.

### 3.6. Расчётное ядро

- Чистое ядро без БД: вход — снимок эффективных значений и снимок правил, выход — шаги и
  результаты. Источник факта ядру неизвестен — только метод, надёжность и статус, нужные сценариям.
- Шаг хранит: стабильный ключ (например, `vk.v1/K1/sec:2/zone:1/riser:3/length`), сценарий, входы
  (ссылки, значения, единицы), правило с версией или формулу, промежуточный результат с единицей,
  источники входов, использованные допущения, статус.
- **Числа**: Decimal в фиксированном контексте (34 знака, `ROUND_HALF_EVEN`, ловушки ошибок); корни и
  логарифмы — методами Decimal; float — только на границе с измерительным ядром через
  `Decimal(repr(x))`. Округления, ceil и ряды типоразмеров — отдельные шаги-правила. ADR-0017
  (хранение Decimal, расчёт float64) остаётся для геометрии обмера: там float64 нужен для совпадения
  с TypeScript, а в расчётном контуре дискретные операции на float дают ошибки вида
  ceil(0,1·3 / 0,3) = 2.
- **Единицы**: каталог с размерностями и масштабами (м, мм, м², м³, л/с, м³/ч, кВт, кг, «100 м»,
  «компл»); переводы — явные шаги. Типизированные счётчики («кв./этаж × этаж = кв.») проверяются при
  построении DAG и ловят двойное умножение старого портала.
- **Сценарии** — один запуск, один снимок, три прохода:

  |                  | MINIMUM                                                                                                                                                    | EXPECTED                                                | TENDER_SAFE                                                  |
  | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------ |
  | Входы            | явные из документов и таблиц; обмеры с проверенной калибровкой или подтверждённые; ручной ввод; подтверждённые; без открытых конфликтов и `AUTO_PREFERRED` | все неотклонённые, включая допущения и `AUTO_PREFERRED` | как EXPECTED                                                 |
  | Правила          | `PHYSICS`, `GEOMETRY`, `NORMATIVE` и `MANUFACTURER` со статусом не ниже `SOURCED`                                                                          | плюс `ENGINEERING` и объявленные fallback               | плюс выбранные в проекте `TENDER_ASSUMPTION`                 |
  | Диапазон синтеза | нижняя граница, если её основание допустимо, иначе «не определено»                                                                                         | ожидаемое значение, объявленное правилом                | ожидаемое, если тендерное правило не требует верхней границы |

  Инварианты на golden-зданиях: **I1** MIN ≤ EXP ≤ TS для определённых результатов (иначе
  предупреждение); **I2** TS − EXP = сумме компонентов резерва; **I3** без выбранных тендерных правил
  TS ≡ EXP; **I4** в MINIMUM нет шагов на допущениях и недопустимых правилах; **I5** отсутствие
  REQUIRED без разрешённого допущения → «не определено», никогда 0.

- Статусы результата: `DETERMINED`, `NOT_DETERMINED`, `NOT_IMPLEMENTED`, `NOT_APPLICABLE`,
  `BLOCKED_BY_CONFLICT`.
- **Пересчёт** — новый неизменяемый запуск и diff с родительским по стабильным ключам. Свойство
  «пересчитались только зависимые» (изменённые шаги ⊆ потомки изменённых входов ∪ структурные
  добавления и удаления) проверяется тестом: «этажность 24 → 25» меняет только зависимые шаги и
  добавляет шаги нового этажа. Повторное использование шагов родителя — оптимизация, не источник
  истины.
- **Хранение**: результаты — строки со стабильным ключом и описателем позиции (система, группа A–L
  PROMPT 06, функциональный тип, материал, типоразмер, область здания, единица) и статусом по
  сценариям; шаги — строки (запуск, ключ, сценарий) с JSONB входов; граф системы — артефакт JSONB с
  sha256. Типовые этажи агрегируются шагами кратности («3,3 м × 23 этажа»), число шагов
  ограничено.
- **Выполнение**: POST создаёт ресурс запуска со статусом; пока расчёт синхронный — в отдельном
  потоке с ограничением времени, чтобы не блокировать event loop (лимит команды БД — 15 с); шаги
  вставляются пакетом. Новый тип задания — отдельное решение (типы закреплены тестом).

### 3.7. Синтез системы

- Синтез — шаги ядра, а не отдельный этап после него: у каждого синтезированного элемента есть шаг
  происхождения и семантика сценариев.
- Элементы: для ВК — корпус, зона давления, стояки, этажные ответвления, квартирные подключения,
  магистрали, ввод; для ОВ — помещения, расходы, группы, системы, установки, магистрали,
  ответвления.
- Происхождение элемента — `OBSERVED`, `CALCULATED`, `SYNTHESIZED`, `ASSUMED`; диапазон
  (минимум / ожидаемое / максимум) с основанием каждой границы: «ожидается 4–5 стояков К1».
- «Наблюдено или синтезировано»: каждое синтезируемое значение объявляет тип факта, который его
  заменяет, и `OBSERVED` побеждает `SYNTHESIZED`. Поэтому сценарий PROMPT 13 (синтезировано 1260 м →
  измерено 1187 м) проверяется уже в PROMPT 06 ручным измеренным утверждением.
- Фитинги и узлы — из топологии по правилам: узел степени ≥ 3 — тройник, смена DN — переход,
  поворот трассы — отвод, узлы стояка — арматура. Коэффициент на метр — только объявленный fallback
  с предупреждением.
- Граф — артефакт запуска, а не общий граф проекта. Трасса без основания не рисуется: синтезируются
  структура и длины с диапазоном, а не геометрия линий.

### 3.8. Расчётный паспорт системы

- `CalculationResult` — инженерные величины: расходы, зоны, DN, число стояков. Не позиции.
- `ExpectedQuantity` — позиции паспорта: описатель, значения трёх сценариев, ссылки на шаги, доля
  значения на допущениях, надёжность, предупреждения.
- Паспорт = позиции + ключевые инженерные величины + перечень допущений, fallback и открытых
  вопросов. Это не ВОР и не смета; название в интерфейсе — «Расчётный паспорт (оценка стадии П)».
- Выгрузка — CSV в формате выгрузки обмера, с защитой от формул в ячейках.

### 3.9. Сверка с ВОР Заказчика

- ВОР Заказчика — объект независимой сверки, а не инженерная истина. Количества, диаметры,
  типоразмеры и другие решения ВОР на расчёт не влияют. Качественные факты из ВОР (система
  присутствует, материал, тип оборудования), если сохраняются в реестре, получают
  `calculation_eligible = false` и технически исключены из снимка для ядра; типы фактов с признаком
  `quantity_like` из ВОР не принимаются. Цены не импортируются. Порядок: расчёт → ExpectedQuantity →
  CustomerVorItem → сверка.
- Позиции ВОР нормализуются: система, функциональный тип, материал, типоразмер, единица, область
  здания.
- Сопоставление — детерминированные правила и подтверждение человеком; позже LLM предлагает
  кандидатов. Количества сравнивает только код.
- Статусы — `MATCHED`, `PARTIAL_MATCH`, `CALC_HIGHER`, `CALC_LOWER`, `NOT_IN_CALC`,
  `MISSING_IN_CUSTOMER_VOR`, `REQUIRES_REVIEW`; системы вне охвата калькулятора — `REQUIRES_REVIEW`
  с причиной «система вне охвата», а не `NOT_IN_CALC`.
- Допуски — по классам позиций (данные с версией), не один глобальный порог. Отклонение
  показывается вместе с надёжностью, чтобы «расчёт больше» не читалось как ошибка Заказчика.

### 3.10. Вопросы и неопределённость

Вопрос создаётся не на каждый пропуск, а при существенном влиянии: перебор альтернатив допущения
меняет количества выше порога, документы противоречат, решения технически различны, ВОР расходится
с расчётом, оборудование не определено. Влияние выражается в количествах — стоимость запрещена.
Вопрос связан с запуском и конкретными позициями.

### 3.11. Интерфейс

- Маршрут `/projects/[projectId]/calc` с разделами: обзор (пять вопросов PROMPT 11), исходные
  данные, системы (ВК, ОВ, ЭОМ), ВОР Заказчика, сверка, допущения, вопросы, история расчётов.
- Любая итоговая цифра раскрывается по шагам до фактов и свидетельств — без JSON и технических
  идентификаторов, с русскими шаблонами формул.
- Серверное состояние — TanStack Query, числа считает только сервер; токены и слои CSS (ADR-0029);
  адаптивность под целевые устройства.

### 3.12. API, права, флаг

- Флаг `calc.portal`: объявлен в реестре, выключен, из админки не включается, своя метка этапа (не
  «Этап 2»). Разработка и тесты — через `FEATURE_FLAGS` и системное переопределение. После PASS
  гейта и решения владельца — пилотный флаг (ADR-0023). Имя не содержит стадию: РД позже
  подключается без нового флага.
- Маршруты `/api/v1/calc/…`: `projects/{id}/facts`, `conflicts`, `sources`, `files`, `requirements`,
  `runs`, `vor`, `questions`; `conflicts/{id}/decision`; `runs/{id}`, `runs/{id}/results`,
  `runs/{id}/steps/{key}`, `runs/{id}/diff`; `rules`. Без маркеров `takeoff-items`, `measurements`,
  `quantities`, `scale-calibrations` (иначе `test_pilot_flag.py` потребует `takeoff.manual`) и без
  `/mep/` (иначе ломается `test_mep_experiment_api.py`).
- Права: `calc.read` — читатель и выше; `calc.verify` — проверяющий и выше (подтверждение
  утверждений, решения конфликтов, принятие допущений, выбор тендерных правил); `calc.edit` —
  инженер и выше (ручные факты, импорт, запуски). Роль SERVICE не меняется. Действия — в аудит.
- OpenAPI: все модели и перечисления — с префиксом `Calc`, потому что у MEP ~73 неквалифицированных
  имени схем (`Parameter`, `RuleRef`, `SourceRef`, `ReviewStatus`…) и одноимённая модель
  переименовала бы типы MEP во фронтенде. Раздельные модели Create и Read; уникальные имена
  обработчиков (они становятся operationId).
- Новый guard-тест маршрутов calc: все за флагом и правом; без маркеров обмера и `/mep/`; адаптер
  обмеров дополнительно за `takeoff.manual`; схемы calc начинаются с `Calc`; существующие имена
  схем не меняются; 404 для чужого пространства.

### 3.13. Файлы xlsx и csv

- Свой вход контура — `POST /api/v1/calc/projects/{id}/files`: неизменяемые файлы, sha256 уникален
  в проекте, хранение через существующий `ObjectStorage.put_stream`. Общий приём и его тесты не
  меняются.
- Зависимость — решение PROMPT 02. Кандидат: openpyxl + defusedxml (и типы для mypy), проверка по
  `FORBIDDEN_PACKAGES` и лицензиям; `.xls` — только если действительно нужен.
- Защита: xlsx — это zip, а проверка `legacy/archive.py` разрешает только pdf/json/md/html/txt, поэтому
  нужна своя проверка OOXML: лимиты размера, числа частей, распакованного объёма и коэффициента
  сжатия; белый список частей; отказ от макросов; формула без сохранённого значения — «нет
  значения», а не 0; разбор в потоке с ограничением времени. CSV — определение кодировки и
  разделителя. Выгрузки — защита от формул в ячейках (`=`, `+`, `-`, `@`).

## 4. MEP semantic и граница LLM

**Нужен ли полноценный MEP semantic сейчас?** Нет. На стадии П по ВК обычно есть только схемы
(Р-MEP-18), а расчёт стадии П опирается на архитектуру, квартирографию, таблицы и ручные факты. MEP
semantic не реализован: ноль размеченных элементов, генератора П→РД нет, реальные данные ждут
передачи. Сделать его обязательным входом — заблокировать портал на неопределённый срок.

**Какие функции MEP можно использовать опционально?**

- контракты v0.3 — только чтение, для будущего отображения в факты;
- дисциплина происхождения — `Derivation`, observed ≠ inferred, `review_required` при любом выводе;
- `canonical_sha256`, `CalibrationSnapshot` с отпечатком, закрепление профиля по sha — как образец
  воспроизводимости;
- топологические факты — повороты трассы, узлы степени ≥ 3, смена типоразмера — как входы правил
  фитингов calc;
- находки каталога документов D0 (стадия, раздел, системы, вид листа, этаж, корпус) — как будущий
  поставщик метаданных источников;
- UX трассировки строки к основанию.

Quantity Engine 0.3.1 и его правила напрямую не используются: он считает ВОР сети РД, а правил
фитингов у него нет.

**Как подключить MEP semantic позже без изменения ядра.** Через тот же протокол поставщика фактов,
что у остальных адаптеров (объявляется в PROMPT 02, реализуется в PROMPT 13):

| Выход MEP                                                  | В реестре calc                                      |
| ---------------------------------------------------------- | --------------------------------------------------- |
| `MepEvidenceGraph` с `HUMAN_GT` или `HYBRID_REVIEWED`      | утверждения со свидетельствами                      |
| `MepEvidenceGraph` с `MODEL_EXTRACTED`                     | кандидаты                                           |
| строки длины `MepBoq` из подтверждённой калиброванной сети | `GEOMETRY_MEASURED` для типов фактов уровня системы |
| элементы с `rd_prior_inferred` или `retrieved_pattern`     | никогда не «измерено»; только `INFERRED`-кандидат   |
| топология сети                                             | утверждение со ссылкой на артефакт                  |
| блокеры                                                    | пробелы в отчёте полноты                            |

Приоритет «РД измерено» над «П синтезировано» задаёт политика по типу факта и стадии; синтез
уступает наблюдению по правилу раздела 3.7. Ядро читает только факты — пересчёт 1260 → 1187 м и
объяснение разницы получаются diff запусков.

**Где граница между LLM и детерминированными расчётами.**

| LLM может (через шлюз моделей, после открытия `models.gateway`)                                                                                          | Только код                                                                                                              |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| классифицировать документы и таблицы; извлекать значения-кандидаты со ссылкой на ячейку; предлагать сопоставления позиций ВОР; подсказывать противоречия | любая арифметика, перевод единиц, агрегация, допуски, сценарии, округления, выбор эффективного значения, статусы сверки |

Граница проверяема тестами: ядро принимает только утверждения (по сигнатуре), модули ядра, систем,
синтеза и правил не импортируют кандидатов и шлюз моделей, а golden-запуск не меняет хеш от
добавления кандидатов. Клиентские данные — только локальным или одобренным провайдерам
(`DataPolicy`). В MVP LLM нет.

Протокол гейта (объявляется до PROMPT 06, принцип ADR-0021 «гейт не подгоняется»):

- объект — реальный комплект стадии П; РД считается недоступной и не требуется; данные вне git;
- проверка — независимая инженерная: документы П, архитектура, квартирография, доступные таблицы,
  ручной независимый расчёт или экспертиза инженера; ВОР Заказчика эталоном не служит;
- появившаяся позже РД — отдельная ретроспективная проверка, не условие гейта;
- метрики заранее: зоны и число стояков — точно или в объявленном диапазоне; длины труб по системам
  в сценарии EXPECTED — в пределах объявленного порога; число единиц оборудования — точно; все
  fallback и допущения перечислены; объяснимость подтверждена инженером;
- итог — PASS / FAIL / BLOCKED; флаг становится пилотным только при PASS и решении владельца.
