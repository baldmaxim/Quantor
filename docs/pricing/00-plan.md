Статус: **проект плана**, 2026-10-26. Код не начат. Первый шаг (P00) — ADR и решение
владельца о границах: сейчас `CLAUDE.md` запрещает в Quantor стоимость, расценки и ставки.

> **Решение владельца 2026-10-26:** фаза 1 — в TenderConnector

## 0. Где делать — рекомендация

Риск проекта в данных и метриках (справочник, рецепты, гейт), а не в оболочке. Поэтому
работа идёт в две фазы:

1. **Доказательство — в TenderConnector.** Там уже есть зеркало архива TenderHUB, слоты,
   проверки, цепочка приёмки, импорт ФСНБ, реестр цен и 1095 тестов (Python, как и
   `apps/api`). Делаются этапы P02, P03, P05, P06, P07 и гейт P10; экономия — около 2 недель.
   Ограничение: TenderConnector — локальное приложение одного пользователя, параллельная
   проверка справочника несколькими сметчиками в нём неудобна.
2. **Продукт — в Quantor** после PASS гейта: контур `pricing` по ADR-0035, перенос
   доказанного движка, многопользовательская страница P08, P09, P12.

Если справочник и рецепты должны проверять сразу несколько сметчиков, P02–P03 лучше
сразу делать в Quantor. Тогда план ниже выполняется целиком в Quantor.

## 1. Задача и постановка

По позиции ВОР Заказчика предложить **состав**: работы и материалы из справочника компании,
коэффициенты перевода и расхода, а затем **цены** из каталога компании. Сметчик подтверждает
или правит. Результат — расценённая ВОР в формате компании.

Принципы (из разбора 2026-10-26):

1. **Справочник, а не свободный текст.** Строка состава — это ID канонической работы или
   материала, а не произвольное наименование. Без этого качество не измерить.
2. **Рецепт, а не генерация.** Состав собирается детерминированно из утверждённого рецепта
   (шаблона состава вида работ) и параметров позиции.
3. **Поиск аналогов — основной источник кандидатов.** Похожие позиции архива показывают,
   какой рецепт применялся и с какими коэффициентами.
4. **Модель выполняет узкие задачи.** Выбрать рецепт из 3–5 кандидатов и извлечь параметры,
   когда правила не справились. Модель не выдаёт числа и не придумывает наименования.
5. **Человек подтверждает, система учится на подтверждениях.** Принятые составы пополняют
   архив и статистику коэффициентов.
6. **ГЭСН — независимая проверка**, не источник цен: нормы расхода и полнота состава.

## 3. Контур в Quantor

Отдельный изолированный контур `pricing` по образцу `calc`: свои таблицы, сервисы, API и
страница. С обмером, MEP и calc не смешивается.

```text
архив расценённых смет (TenderHUB API только чтение | XLSX компании)
  → Справочник номенклатуры (канонические ID, алиасы, подтверждение человеком)
  → Реестр рецептов (вид работы → состав, параметры, коэффициенты; версии, утверждение)
ВОР Заказчика (XLSX)
  → разбор позиций → параметры (правила; модель — резерв)
  → кандидаты: аналоги архива + рецепты → выбор рецепта
  → сборка состава по рецепту → проверки (единицы, p5–p95 коэффициентов, ГЭСН)
  → уверенность high / medium / low / отказ
  → сметчик: принять / править / отклонить
  → цены из каталога компании (дата, источник, n) → выгрузка XLSX
  → подтверждения возвращаются в архив и статистику
```

- Флаг `pricing.autofill`: объявлен выключенным, из админки не включается до PASS гейта
  (раздел 6).
- Страница `/pricing` в `(portal)`, проверка флага в интерфейсе и на сервере (ADR-0023).
- Тяжёлые шаги (поиск по архиву, массовая сборка) выполняются в исполнителе заданий
  (`apps/api/app/worker`), а не в запросе API.
- Модель — только через шлюз моделей, на сервере ML (локальный Qwen), без внешних API для
  данных компании. До открытия шлюза контур работает без модели.

## 4. Этапы

Работа идёт по пакету промтов `_prompts/pricing_autofill_v1/`: по одному промту, STOP после
каждого. Сроки указаны в рабочих днях разработки, время людей — отдельно.

### P00. Границы и ADR — 1 день

- ADR-0035 «Контур авторасценки»: что разрешено внутри контура (цены компании с датой,
  валютой и источником; справочник; рецепты), что запрещено (число от модели, внешние API
  для данных компании, запись в TenderHUB).
- Правка раздела «Границы этапа» в `CLAUDE.md`: исключение для контура `pricing`.
- Объявление флага `pricing.autofill`, пустая страница-заглушка `/pricing`.
- Инвентаризация данных: проекты и форматы архива TenderHUB и корпуса «Pricer».
  Пересечение объектов, выбор отложенных проектов (holdout).

**Гейт:** ADR утверждён владельцем.

### P01. Архив расценённых смет — 3 дня

- Таблицы `pricing_archive_project / _position / _row` с происхождением: источник, файл,
  хеш, дата расчёта.
- Адаптеры: TenderHUB API `archive:read` (только чтение, ключ в `.env` добавляет владелец) и
  XLSX компании.
- Разбиение по проектам целиком: train и holdout фиксируются в P00 и не меняются по
  результатам.

**Гейт:** архив загружен, суммы строк сходятся с источником, повторов нет.

### P02. Справочник номенклатуры — 4 дня + 2–3 дня сметчика

- Канонические работы и материалы (`pricing_catalog_item`): тип, единица, атрибуты (класс
  бетона, толщина, марка, бренд), алиасы исходных наименований.
- Кластеризация исторических наименований (~1300 работ, ~2900 материалов) без модели:
  нормализованный ключ, триграммы, совпадение атрибутов. Атрибуты не сливаются: B25 ≠ B30,
  100 мм ≠ 150 мм.
- Экран проверки кластеров: сметчик подтверждает, разделяет или объединяет.
- Повторный разбор архива по алиасам.

**Гейт:** ≥ 95 % стоимости строк архива привязано к каноническим ID. Согласованность
«одинаковый текст → одинаковый состав» пересчитана на ID (было 14 % по наименованиям).

### P03. Реестр рецептов — 4 дня + ~1 неделя инженера-сметчика

- Рецепт: вид работы, статья затрат, строки (ID каталога, роль осн/всп, привязка
  материала к работе), слоты параметров, коэффициенты (медиана, p5–p95, n).
- Черновики рецептов строятся из архива: группировка позиций по канонической работе и
  статье затрат, частые наборы строк.
- Версии и утверждение по образцу Rule Registry calc: черновик → утверждён; утверждённая
  версия неизменна, изменение — новая версия.

**Гейт:** утверждённые рецепты объясняют ≥ 80 % позиций архива шести разделов (монолит,
кладка, фасад, отделка, гидро, кровля) с отклонением не более одной строки.

### P04. Разбор ВОР и параметры — 3 дня

- Импорт ВОР Заказчика (XLSX): позиция, единица, объём, раздел, соседние позиции.
- Извлечение параметров правилами: класс и марки бетона (B, W, F), толщины, марки кладки,
  Ду, класс арматуры, бренды. Перенос слотов recipe-v2.
- Требования «не ниже В10» хранятся как ограничения, а не как точное значение.

**Гейт:** на размеченной выборке ≥ 95 % явно заданных параметров извлечены верно, ложных — 0.

### P05. Подбор рецепта без модели — 4 дня

- Поиск аналогов в архиве: `pg_trgm` и TF-IDF по тексту, единице, разделу и соседям; top-k
  с составом и коэффициентами.
- Ранжирование рецептов: голосование аналогов и совместимость слотов.
- Сборка состава по рецепту с параметрами; количества считает код:
  объём × перевод × расход.
- Отказ, когда кандидаты близки или слоты конфликтуют.

**Гейт (на holdout):** рецепт верен в top-1 ≥ 75 %, в top-3 ≥ 90 %.

### P06. Проверки и уверенность — 3 дня

- Единицы, коэффициенты вне p5–p95 рецепта, обязательные слоты, дубликаты, материал без
  работы, конфликт параметров с позицией. Перенос `validate_*` и `compute_confidence`.
- `high` — только при полностью согласованном составе и всех проверках PASS.

**Гейт:** точность `high` ≥ 95 % на holdout, доля `high` ≥ 50 %.

### P07. ФСНБ как независимая проверка — 4 дня + ~3 дня инженера

- Импорт ГЭСН и ФСБЦ (парсеры MaterialBase/TenderConnector) в схему `pricing_fsnb`, версия
  по приказу (91пр от 17.02.2026).
- Ручная привязка рецепта к норме ГЭСН с переводом единиц (один раз на рецепт).
- Отчёт сверки:
  - расход основного материала против нормы (пример: бетон 1,02 м³ ↔ ГЭСН 06-01-001-01, 102 м³
    на 100 м³);
  - материалы нормы, которых нет в рецепте (полнота);
  - трудозатраты по ГЭСН.
- Цены ФСБЦ (уровень 01.01.2022, без индексов) — только справочная колонка, в расчёт не идут.

**Гейт:** у рецептов, привязанных к ГЭСН, отклонения расхода сверх 10 % разобраны инженером.

### P08. Страница «Авторасценка» — 5 дней

- Загрузка ВОР, таблица позиций со статусом уверенности, фильтры по разделу и статусу.
- Карточка позиции: предложенный состав, рецепт, аналоги из архива, параметры, проверки,
  сверка с ГЭСН.
- Действия: принять, править (выбор из справочника), отклонить. Массово — только `high`.
- Адаптив по правилам каталога: телефон, планшет, десктоп; обе темы.

**Гейт:** сметчик проходит ВОР одного объекта от загрузки до принятия без обходных путей.

### P09. Цены и выгрузка — 3 дня

- Каталог цен компании по каноническому ID: последняя и медианная цена, дата, источник
  (архив, Larix, КП), n. Модель в ценах не участвует.
- Применение к принятому составу, выбросы по P25–P75 / Tukey — предупреждения.
- Выгрузка XLSX в формате компании: позиция → работы → материалы → цены.

**Гейт:** итог выгрузки по эталонному объекту сходится с расчётом вручную по тем же ценам.

### P10. Бенчмарк и инженерный гейт — 3 дня + время сметчиков

- Holdout: проекты, не входившие ни в архив, ни в рецепты, в том числе 4 контрольных
  проекта «Pricer» и объект 314 TenderConnector.
- Метрики по шести разделам:
  - рецепт top-1 / top-3;
  - параметры;
  - коэффициенты в пределах ±10 %;
  - полнота состава в деньгах;
  - точность и доля `high`;
  - доля позиций, принятых сметчиком без правок.
- Сравнение с «Pricer» 27B на тех же позициях (по сохранённым ответам) и с recipe-v2 9B.

**Гейт PASS → пилот:**

- ≥ 70 % позиций типовых разделов принято без правок;
- полнота состава в деньгах ≥ 90 %;
- точность `high` ≥ 95 %;
- ноль наименований вне справочника.

После PASS и решения владельца флаг открывается на пилотное пространство.

### P11. Модель как помощник — после P10, по решению владельца

- Только для `medium` / `low`: модель ранжирует 3–5 кандидатов-рецептов и извлекает
  параметры, которых не нашли правила. Ответ — ID из списка или отказ.
- Локальная модель на сервере ML через шлюз моделей. Начать с готовой Qwen с примерами из
  архива в запросе; дообучение — только если замер покажет разрыв.
- Внедряется, только если на holdout поднимает долю принятых без правок не менее чем на
  10 п.п. и не снижает точность `high`.

### P12. Обучение на подтверждениях — 2 дня

- Принятые и исправленные составы пополняют архив, статистику коэффициентов и алиасы.
- Новые рецепты появляются только черновиками для утверждения.
- Ежемесячный пересчёт метрик на свежих объектах.

## 6. Решения владельца до старта

1. Исключение из запрета цен и расценок в Quantor для контура `pricing` (ADR-0035).
2. Источник архива: TenderHUB API только на чтение (рекомендуется), XLSX или оба.
3. Кто утверждает справочник и рецепты (сметчик / инженер), сколько часов в неделю.
4. Объекты holdout и пилотные сметчики.
5. Судьба «Pricer» 27B: заморозить. Новые RL-запуски не делать, корпус и аудит использовать в
   P01 и P10.
6. Использование сервера ML для P11: GPU общий, запуск — по согласованию.

## 7. Риски

| Риск | Мера |
|---|---|
| Справочник не нормализуется за разумное время | начать с монолита, кладки и кровли, где проще; остальное — по мере готовности |
| Рецептов слишком много или они слишком дробные | слоты параметров вместо отдельных рецептов на каждую марку |
| Архив мал (31–60 объектов) | пополнение из P12; holdout фиксирован, обучение на нём запрещено |
| Нетиповые позиции (мебель, декор, бренды) | отказ и ручной путь; в метрику «типовых разделов» не входят |
| Цены устаревают | дата и источник у каждой цены, предупреждение о давности |
| Данные компании в git | только синтетические fixtures; архив — в базе и хранилище сервера |
