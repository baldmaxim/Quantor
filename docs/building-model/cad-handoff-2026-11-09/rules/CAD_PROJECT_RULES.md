# Правила проекта «Чертеж_CAD»

Цель: в рабочей папке остаются актуальный результат, его необходимые данные,
исходники и поддерживаемый код. Пробы, распаковки, дубли и промежуточные
результаты не должны накапливаться после завершения задачи.

## Расположение файлов

- Исходные документы сохранять без изменения. Основной PDF находится в
  `АР_Обработка/00_Исходники`; локальные исходные CAD для сверки пока находятся
  в `_work/network_cad_audit/local_input` и `local_archives`.
- Поддерживаемый движок, его тесты и шаблоны находятся в
  `АР_Обработка/90_Пайплайн`. Не переносить код движка в skill.
- Текущий результат определять по
  `АР_Обработка/16_Все_планы/Последний_прогон.json`, а не по дате папки.
  Точка входа пользователя — `ОТКРЫТЬ_РЕЗУЛЬТАТ.html` в корне.
- Для новых проб, снимков экрана QA, журналов, распаковок и конвертаций
  использовать отдельную папку задачи в системном TEMP; по завершении удалять
  только собственную временную папку. Не создавать в корне файлы `probe*`,
  `test*`, `debug*`, `v2`, `final_final` или новые номерные папки экспериментов.
- `_work/.deps` — действующие зависимости движка, а не мусор. Существующие
  входные JSON повторных прогонов и необходимые QA-сценарии в `_work` сохранять.
  Новые временные файлы в `_work` допустимы только для совместимости с текущим
  кодом; удалить их после проверки, не затрагивая существующие данные.
- Не устанавливать библиотеки заново в папку каждого прогона. Использовать
  существующие зависимости либо отдельное окружение.

## Обязательное завершение каждого прогона

1. Проверить статус, требуемые CAD-файлы, геометрию и локальные ссылки отчёта.
   Состояние `completed_requires_review` сохранять как требующее проверки;
   не объявлять его инженерной приёмкой.
2. Убедиться, что финальный результат содержит все необходимые ресурсы.
   Перед удалением старых папок проследить ссылки HTML/JS/JSON, исходную
   геометрию повторно использованных видов и сертификаты масштаба. Сначала
   собрать самостоятельный результат или оставить необходимые зависимости.
3. После проверки обновить указатель последнего прогона и точку входа
   пользователя. Не оставлять несколько конкурирующих «финальных» версий.
4. Сохранить проверенные повторяемые приёмы в skills по правилам ниже.
5. Удалить собственные временные файлы и `__pycache__`, созданные этой задачей.
   Не удалять файлы только по расширению, возрасту или имени `_work`.
6. Устаревшие результаты, если у них нет действующих зависимостей, упаковать
   в `Архивы_движка/История_проекта_ДАТА.zip` с исходными относительными путями
   и SHA256-манифестом. Проверить содержимое архива до удаления распакованных
   копий. Оставлять один актуальный распакованный результат; предыдущий
   проверенный результат допустим в архиве для отката.
7. После очистки повторить проверку ссылок и необходимые тесты. В ответе
   указать финальный файл, итог очистки и существенные оставшиеся зависимости.

При ошибке или прерывании не заменять последний проверенный результат.
Диагностику незавершённой попытки сохранить компактно в архиве, исходники и
пользовательские замечания не удалять. Файлы `.dwl`/`.dwl2` не удалять, пока
не установлено, что соответствующий CAD-документ закрыт.

- Не считать навык сохранённым, пока реальный `SKILL.md` не записан и не
  проверен. Если запись вне проекта недоступна, сообщить об этом явно.

## Текущие ограничения проекта

По указанию пользователя от 2026-11-07 останавливать проектную работу при
остатке применимой квоты Codex ниже 40%. Ровно 40% допускает работу.
Проверять остаток перед запуском модели, установкой и прогоном. Проверка
должна быть не старше пяти минут. Отсутствующее окно не считать нулём.
Если применимый остаток неизвестен, отложить ресурсоёмкие операции.

Сохранить принятый пилот и контрольную версию архитектуры. PDF-распознавание
не должно читать готовый CAD или заимствовать геометрию пилота. Отделка движка
и выпуск его ведомостей выключены; отделку по зонам считает Quantor (ADR-0042).
Не менять код и конфигурацию во время активного прогона с фиксацией SHA256.
Очистка не разрешает запускать новый инженерный расчёт или изменять приёмку.
При параллельной работе не удалять временные файлы другой текущей задачи.
Если во время очистки изменился движок или указатель результата, проверить
новые зависимости и сохранить параллельные правки без перезаписи.

## План разработки и обязательная отчётность

- Единый реестр задач — `АР_Обработка/План_развития.json`, отображаемый на
  `АР_Обработка/Пайплайн_проекта.html`. Специализированные планы и handoff —
  источники и ссылки, а не конкурирующие реестры статусов.
- Новое поручение до исполнения зарегистрировать в плане: стабильный ID,
  формулировка, источник запроса, исполнитель, дата и критерий завершения.
  Дедлайн указывать только если он известен. Для параллельной регистрации и
  отчётов использовать inbox/updater из
  `АР_Обработка/Рабочий_контекст/Контроль_плана_Astra.json`; канонический файл
  не перезаписывать из устаревшей копии.
- После публикации события выполнить единый `control.py` из этого контракта
  и проверить запись в плане до начала новой работы. Тот же обработчик
  применяет отзывы с блокировкой и проверкой SHA; живую чужую блокировку
  не удалять. Обычная запись отчёта не требует отдельного вызова модели.
- Исполнитель обязан оставить в плане датированный отзыв по ID задачи:
  сделано, не сделано, частично либо заблокировано; указать фактический
  результат, причину незавершения и ссылки на доказательства. Неизвестную
  историческую дату завершения не выдумывать: отличать её от даты отчёта.
- После передачи артефакта с SHA в QA его байты неизменны. Дополнительные
  результаты и уточнения писать отдельным протоколом с новым именем и SHA,
  сохраняя прежний. Служебный рабочий файл не выдавать за неизменяемый снимок.
  Сообщать о готовом файле только после успешной записи, проверки exit code
  и чтения записанного файла. При смене протокола повторно сверить реальные
  HTML/ресурсы и явно связать старую и новую версии, не переписывая прошлый FAIL.
- Готовый прототип, успешные unit-тесты, внедрение, проверка фактического
  выхода и инженерная приёмка — разные стадии. Завершение одной стадии не
  закрывает родительскую задачу. Решения пользователя по замечаниям сохранять.
- Оркестратор в основном чате отвечает за фактическое выполнение каждой
  стадии: проверяет артефакты и критерий, организует независимый QA,
  возвращает недоработки исполнителю и назначает следующий необходимый этап.
  Он доводит работу от диагностики через исправление и внедрение до проверки
  конкретного фактического выхода. Отчёт исполнителя «сделано» сам по себе
  не подтверждает результат всей задачи; итог технической проверки фиксирует
  оркестратор со ссылкой на доказательства. Инженерную приёмку этим не заменять.
- Контролёр Astra ведёт учёт исполнения по выходным отчётам: сверяет наличие
  задач, дат, исходов и ссылок; напоминает о явных просрочках, отсутствующем
  отзыве и формально неподтверждённом завершении. Техническую правильность
  результата и полноту этапов контролирует оркестратор. Astra не анализирует
  движок/чертежи и не запускает распознавание, пилоты или повторные тяжёлые
  проверки. Задачи на паузе по решению пользователя и неизменные сигналы
  повторно не тормошить.
