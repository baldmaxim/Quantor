# Модель здания: привязка к тендеру и версии, plangeom, автоматическая модель Revit

Дата: 2026-11-02. Статус: **предложение**, ждёт решений владельца (раздел 11). Код не менялся.

## 1. Вывод

Строить можно, но `plangeom` нельзя подключать к Revit напрямую. Нужны три новых звена:

1. **Версия тендера** — замороженный комплект ревизий документов. Сейчас такой сущности нет, а привязка
   проекта к тендеру версию фактически теряет (раздел 3). Эта часть полезна сама по себе и не зависит от
   `plangeom`, поэтому её можно начинать первой.
2. **Нормализатор** — из фрагментов `plangeom` собирает здание: стены с хозяевами проёмов, уровни, высоты,
   типы. Это главный объём работы и главный неизвестный риск.
3. **Проверка человеком** — на реальном комплекте ни один лист не получил `accepted`, поэтому утверждение
   обязательно, а не желательно.

Три вещи, которые могут остановить работу:

- **Лицензии у `plangeom` нет.** В метаданных: «No license has been granted yet: all rights reserved».
  Пакет выложен на PyPI 2026-11-02, автор не указан. До письменного разрешения — только офлайн-оценка,
  в боевой контур нельзя.
- **Формата JSON для Revit у меня нет.** На этой машине не нашлось ни образца, ни плагина (раздел 7).
  Без него адаптер не написать.
- **План противоречит действующим запретам `CLAUDE.md`**: автоматический масштаб, генерация Revit и
  другие (раздел 9). Нужно отдельное решение владельца и ADR-0035.

Рекомендация по порядку: сначала один этаж офлайн от PDF до открытой модели Revit, и только после этого
экраны и таблицы портала. Так самый дорогой риск проверяется до самых дорогих работ.

## 2. Что проверено

`plangeom 0.1.0a2` поставлен в отдельное временное окружение, вне `apps/api`. Прогон — локальный, наружу
данные не уходили.

### Как работает библиотека

| Шаг | Что делает |
|---|---|
| Масштаб | По осям и подписанным размерам, затем по размерным линиям, надписи `1:N`, модулю и дверям. Скан не читает |
| Стены | Заливки и штриховки → толщина между кромками → осевые линии |
| Двери, окна | Дуга + полотно; окно — разрыв стены у края плиты с линиями остекления |
| Помещения | Замкнутые грани, водораздел от марок, сверка с экспликацией |
| Комплект | Штамп даёт этаж и отметку; листы с одними именами осей — одно здание; стояки и шахты сквозь этажи |
| Учёт | Каждый штрих имеет владельца, ничейное идёт в `queue`, сомнения — в `summary.doubts` |

Вызов: `parse_page` для листа, `parse_document` для комплекта. Каждый лист читается в своём процессе с
таймаутом 300 с. Единицы — мм в системе листа, ось Y вниз. Сетевых импортов в коде нет (проверено поиском
по исходникам); `subprocess` запускает только собственный обработчик листа.

### Измерения: пример и реальный комплект

Пример — один лист из `plangeom_example_full.json`. Реальный комплект — АР стадии ПД из архива тендеров,
77 страниц, 2 процесса на 8 ядрах при занятой машине.

| Показатель | Пример (1 лист) | Реальный комплект |
|---|---|---|
| Прочитано | 1 | 74 из 77, сбоев 0, планов 50 |
| `accepted` | да | **0 из 74**, все `needs_review` |
| Время | — | 1181 с; на лист: медиана 28 с, максимум 188 с |
| Память и объём | 396 КБ | пик 2,5 ГБ на лист; JSON 33 МБ |
| Фрагменты стен на этаж | 259 | обычно 800–3300 |
| Площадь стен, восстановленная осевыми | 99,8 % | 71 % на 14-м этаже, 47 % на 2-м этаже |
| Помещения со сверкой по экспликации | 44 из 109 | на большинстве этажей 4–6 примерно из 100 и более |

**Пример — это лучший случай, а не типичный.** Ориентироваться на него при оценке нельзя.

Сильные стороны на реальном комплекте:

- Этажи складываются по осям: на проверенных парах совпадение колонн 100 %, несущих стен 99–100 %.
- Комплект разобран на 3 группы листов по сетке осей; отметки этажей читаются из штампа; шаг этажа 3,36 м.
- Результат воспроизводим: два прогона одного листа дали одинаковый хеш (без поля времени). Проверен один лист.

Слабые стороны, важные для модели:

- **Окна нестабильны.** На похожих типовых этажах подряд: 73, 73, 23, 77, 75, 35, 74. Вероятно, это ошибка
  чтения, но по чертежам я это не сверял.
- **Лишние «стены».** На 2-м этаже площадь стен 1240 м² при плите 2043 м², баланс площадей −625 м². На 14-м
  этаже почти половина осевых тоньше 100 мм: похоже на слои фасада и штриховки, но это предположение.
- **Раздел комплекта не определён.** Поле `section` пусто у 70 из 74 листов, хотя от него зависит сверка АР с КР.
  Портал раздел знает сам и должен передавать его из состава версии.
- **Верность масштаба не проверена.** На 48 планах получено 1:100, на 2 — 1:200, но с чертежами я это не сверял.

Склейка стен, грубая проба на примере: из 425 осевых при допуске 30 мм и разрыве до 50 мм получается 289.
Склейка «вслепую» через разрывы до 2 м даёт 240, но завышает длину на 13 %. Склеивать надо с учётом проёмов.
Из 850 концов осевых 144 висят свободно, дальше 50 мм от соседней стены с учётом толщин.

## 3. Тендер и версия: что есть и чего не хватает

**Есть в Quantor:**

- `Project.source / external_id / external_ref`, уникальность `(workspace_id, source, external_id)`, отдельная
  операция перепривязки ([tenderhub_binding.py](../../apps/api/app/services/tenderhub_binding.py)).
- `DocumentRevision` неизменяема, у неё есть `source_sha256` (ADR-0003).
- `calc_runs` хранит снимок и хеш, но прямой ссылки на ревизии нет.

**Есть в HUBTender:** таблица `tenders` с `UNIQUE (tender_number, version)`; новую версию создаёт
`clone_tender_as_new_version` — это новая строка с новым UUID.

**Разрыв 1 — версия тендера теряется.** В `external_id` лежит UUID строки, то есть одной версии, а поле
`version` из `TenderBrief` в проекте не сохраняется. Когда в HUBTender появляется версия 2, остаётся два плохих
пути: завести второй проект и разделить документы или перепривязать и потерять связь с версией 1.

**Разрыв 2 — нет состава версии.** Ревизии лежат внутри документов, но нигде не записано, какие именно ревизии
составляли комплект на момент расчёта. Если заказчик заменил один том, ответить на вопрос «по каким чертежам
построена эта модель» нечем.

**Решение:**

```text
Project (тендер по номеру)
  └─ TenderVersion (замороженный комплект)  ──0..1──> строка tenders в HUBTender (uuid, version)
       └─ состав: DocumentRevision + раздел + роль
            └─ PlanParseRun → BuildingModelVersion → RevitPackage
```

- Один номер тендера — один проект. В списке тендеров другая версия того же номера предлагается как
  «добавить версию в проект», а не как новый проект. ADR-0011 уточняется, а не отменяется.
- Запись в HUBTender по-прежнему запрещена: Quantor только читает, версии создаются там людьми.
- Заморозка вычисляет `manifest_sha256` и запрещает изменения триггером базы — как у утверждённых версий
  правил calc. Удаление ревизии из замороженной версии блокируется внешним ключом.
- Для проектов без HUBTender всё работает так же, только внешняя ссылка пуста.

## 4. Целевая схема

```text
PDF → DocumentRevision → TenderVersion (заморозка, manifest_sha256)
                               │
             задание PLAN_PARSE, отдельный образ с plangeom
                               │
              сырой JSON листов + здания (объектное хранилище, неизменяем)
                               │
             задание MODEL_BUILD, чистая функция без тяжёлых зависимостей
             нормализатор(сырой JSON, параметры, правки человека)
                               │
              кандидат модели → проверка человеком → утверждённая версия
                               │
              адаптер Revit → пакет (JSON, манифест, отчёт)
                               │
              сборка в Revit (вне портала) → квитанция → покрытие
```

Главное свойство: **модель пересобирается детерминированно**. Правки человека хранятся отдельно и привязаны к
устойчивому ключу элемента, поэтому они переживают обновление библиотеки и повторный разбор.

## 5. Разрыв между plangeom и Revit

| Нужно Revit | Что даёт plangeom | Что делает Quantor |
|---|---|---|
| Единая стена с осью и типом | Фрагменты; проём разрывает стену | Граф стен: стыковка, склейка через проёмы, фильтр слоёв и тонких фрагментов |
| Хозяин двери | `host_wall` — фрагмент у петли | Переназначить на собранную стену |
| Хозяин окна | **Нет поля**, только две точки | Найти по геометрии |
| Сторона открывания | Не указана | Вывести из петли и концов дуги |
| Ширина проёма | Полотно и разрыв могут расходиться: 1350 и 1800 мм | Правило выбора + вопрос человеку |
| Высота стены, плита | Только отметки этажей | Параметр на этаж со статусом `assumed` или данные человека |
| Подоконник, верх окна, высота двери | **Нет**, разрезы и фасады не читаются | Таблица параметров по типам |
| Тип Revit | Толщина, роль, безымянный кластер материала | Таблица сопоставления с каталогом шаблона |
| Система координат проекта | Лист, Y вниз | Начало в пересечении осей, Y вверх |
| Повторение этажей | `title.floors` | Экземпляры этажа, а не копии геометрии |
| Перекрытие и отверстия | `slab_outlines_mm`, шахты, `slab_opening_mm` | Плита с отверстиями; толщина — параметр |
| Устойчивый идентификатор | `W0`, `D0` зависят от порядка | Свой ключ: хеш типа, этажа и геометрии относительно осей |
| Колонны, лестницы, лифты | Контуры без типов | Этап 1: контур и отверстие. Семейства позже |

Правила нормализатора, взятые из спецификации SU10 (FloorGraph 0.2, § 12): не соединять стены без явного
разрешения; подбирать тип по каталогу целевого шаблона, а не по названию с чертежа; стабильные идентификаторы
операций; квитанция с покрытием всех элементов.

`plangeom.mep.plan_services` в план не входит: сам автор называет это умолчаниями для планирования, а не проектом.

## 6. Реализация в Quantor

### Данные

Все таблицы — внутри рабочего пространства, за флагом. Номер миграции — следующий свободный на момент работы:
параллельные сессии тоже добавляют миграции.

| Таблица | Назначение и ключевые поля |
|---|---|
| `tender_versions` | `project_id`, `number`, `label`, `external_tender_id?`, `external_version?`, `status` (`draft`/`frozen`), `manifest_sha256`, `frozen_at`, `frozen_by` |
| `tender_version_documents` | `tender_version_id`, `document_revision_id` (RESTRICT), `section` (АР, КР…), `use_in_model` |
| `plan_parse_runs` | `tender_version_id`, `reader_version`, `options`, `input_sha256`, `status`, `job_id` |
| `plan_parse_sheets` | `run_id`, `document_revision_id`, `page_index`, `verdict`, этаж, отметка, масштаб и его основание, `checks`, `doubts`, `artifact_key`, `artifact_sha256` |
| `building_models` | `tender_version_id`, ключ здания (группа по сетке осей) |
| `building_model_versions` | `model_id`, `number`, `status` (`candidate`/`approved`), `parse_run_id`, `normalizer_version`, `params`, `artifact_key`, `artifact_sha256`, `stats`, кто и когда утвердил; после утверждения неизменна |
| `model_overrides` | `model_id`, `element_key`, `action`, `payload`, `reason`, автор, время |
| `model_review_items` | `version_id`, `element_key`, `severity` (`blocker`/`warning`), код, `status` |
| `revit_packages` | `version_id`, `adapter_version`, `artifact_key`, `artifact_sha256`, `receipt_key`, `coverage` |

Геометрия и JSON лежат только в объектном хранилище (ADR-0002): на реальном комплекте это 33 МБ. В базе —
ключи, хеши и счётчики. Ключ лист-артефакта `(source_sha256, page_index, reader_version)`: новая версия тендера
читает заново только изменившиеся тома.

`BuildingElement` — новая самостоятельная сущность, не `Measurement`, не `Region`, не `ExpectedQuantity`. В итоги
обмера и в факты calc модель не пишет. Модель здания — не ProjectGraph.

### Исполнение

- **Новый образ `quantor-plan-worker`:** образ API плюс закреплённая по хешу версия `plangeom` и её зависимости.
  Запуск `python -m app.plan_worker`, исполняет только `PLAN_PARSE`. В основном образе `plangeom` нет,
  а основной воркер этот тип не берёт ([registry.py:45](../../apps/api/app/worker/registry.py#L45)).
- Импорт `plangeom` разрешён только в `app/plan_worker/`, это проверяет тест.
- Ограничения: одно задание за раз, 2 процесса на лист, предел памяти контейнера порядка 6 ГБ — уточнить по
  серверу. PDF недоверенные, поэтому у контейнера минимум секретов.
- `MODEL_BUILD` выполняется в обычном воркере: это чистый Python над JSON, зависимости `plangeom` ему не нужны.
- Вход нормализатора — строгая модель Pydantic под конкретную версию `plangeom`. Незнакомая версия — отказ, а не
  молчаливый разбор: библиотека в альфе, её формат будет меняться.

### Масштаб

Масштаб `plangeom` — **кандидат с основанием**. Человек подтверждает его на группу листов. Таблицы калибровки и
`Measurement` не меняются. Если у листа уже есть калибровка измерительного ядра и расхождение больше 0,5 %,
экран показывает предупреждение, а утверждение модели блокируется.

### Канонический формат модели

Это формат Quantor, он не зависит ни от `plangeom`, ни от целевого JSON Revit. Если сменится библиотека или
формат, меняется один адаптер.

```json
{
  "schema": "quantor.building_model.v1",
  "tender": { "number": "NNN", "version": 2, "manifest_sha256": "…" },
  "reader": { "name": "plangeom", "version": "0.1.0a2", "normalizer": "1.0.0" },
  "units": "mm",
  "origin": { "axes": ["1", "А"], "y": "up" },
  "levels": [
    { "key": "L14", "elevation_mm": 48010, "height_mm": 3360,
      "status": { "elevation_mm": "observed", "height_mm": "derived" } }
  ],
  "walls": [
    { "key": "w_8f3a", "level": "L14", "a": [0, 0], "b": [6200, 0], "thickness_mm": 200,
      "role": "partition", "type_ref": "WT-200", "status": "observed",
      "source": [{ "sheet": "…", "plangeom_ids": ["W12", "W13"] }] }
  ],
  "openings": [
    { "key": "o_21bc", "kind": "door", "host": "w_8f3a", "offset_mm": 1400, "width_mm": 900,
      "height_mm": 2100, "swing": "left-in",
      "status": { "width_mm": "observed", "height_mm": "assumed" } }
  ],
  "slabs": [], "rooms": [], "stacks": [], "review": { "blockers": 0, "warnings": 12 }
}
```

Статусы: `observed` — прочитано с чертежа, `derived` — выведено из подтверждённого, `assumed` — параметр,
`human` — решение человека. Предположение нельзя выдавать за наблюдение; в Revit статус уходит параметром элемента.

### Интерфейс

Новые экраны за флагом `model.auto`, по общим правилам адаптивности, темы и PWA. Панель проверки — Canvas2D поверх
существующего просмотрщика (ADR-0015); WebGL и 3D не нужны.

| Маршрут | Что делает |
|---|---|
| `projects/[id]/versions` | Список версий, сбор состава по разделам, связь с версией HUBTender, заморозка |
| `projects/[id]/model` | Этапы разбора, листы со статусом, подтверждение масштаба, таблица этажей и высот |
| `projects/[id]/model/review` | Наложение на PDF, очередь сомнений, правки стен и проёмов; на телефоне — очередь и утверждение, правка геометрии на планшете и десктопе |
| `projects/[id]/model/export` | Сопоставление типов, список блокеров, выгрузка пакета, загрузка квитанции |

## 7. Revit: что известно о текущем контуре

Владелец сообщает, что Revit-модели уже строятся через JSON. На этой машине я этого не нашёл:

- Нет файлов `.addin`, `.rfa`, `.dyn`, расширений pyRevit и C#-кода с `Autodesk.Revit` в каталогах Odintsov.
  Поиск `.rfa` и `.addin` по всему `/home/usrr` был неполным.
- `revit_export_v1.py` в навыке пожаротушения работает в обратную сторону: Revit → JSON.
- SU10 (`/home/usrr/Quantor-archive/`) описывает `FloorGraph → KIR → C#`, но бэкенд лежит вне архива.
  В итоговом запуске стоит `revit_modified: False`.

Поэтому адаптер — отдельный заменяемый модуль. Пакет выгрузки содержит целевой JSON, манифест (тендер, версия, хеши
ревизий, версии инструментов) и отчёт с допущениями. Квитанция из Revit (элемент → `ElementId`, отказы) загружается
обратно и даёт покрытие. Без неё статус пакета — «выгружен», а не «построен».

## 8. Этапы

Пакет промтов — `_prompts/building_model/`, по одному промту, STOP после каждого. Размер: S — до 3 дней, M — до
недели, L — 2–3 недели. Это грубая оценка до M1, не замер.

| Этап | Содержание | Результат | Размер |
|---|---|---|---|
| **M0** | Решения раздела 11, лицензия, образец JSON, ADR-0035, правка запретов в `CLAUDE.md` | Разрешение начинать | Владелец |
| **M1** | Офлайн в `tools/`: PDF → `plangeom` → прототип нормализатора → JSON Revit на **одном типовом этаже**; проверка поворота страницы и привязки к PDF | Модель открыта в Revit, таблица отклонений | L |
| **Гейт G1** | Сравнение с эталоном (ниже), 3 объекта | Идём, сужаем или останавливаемся | — |
| **M2** | `TenderVersion`, состав, заморозка, связь с HUBTender, экран версий. **От G1 не зависит** | Ответ «по каким чертежам» | M |
| **M3** | Образ `quantor-plan-worker`, `PLAN_PARSE`, артефакты, кэш листов, флаг, деплой | Разбор версии из портала | M |
| **M4** | Нормализатор в продукте: `quantor.building_model.v1`, граф стен, хозяева, этажи, ключи, правки | Кандидат модели | L |

### Гейт G1

Эталон — PlanSwift GT и модели Revit, если они есть. Пороги предлагаемые, их утверждает владелец **до** прогона.

| Показатель | Предлагаемый порог |
|---|---|
| Масштаб планов до подтверждения | 100 % верно или явно помечен сомнением |

числа. Если не проходят только окна, пилот можно сузить до стен, дверей и плит.

## 9. Конфликты с действующими правилами

Каждая строка требует решения владельца. Предлагается снимать запреты **только внутри контура модели** и за
флагом `model.auto`, как это сделано для calc в ADR-0030.

| Запрет сейчас | Почему конфликт | Предложение для ADR-0035 |
|---|---|---|
| Генерация Revit/IFC (`CLAUDE.md`, ADR-0027) | Прямая цель работы | Разрешить выгрузку JSON из утверждённой модели; запись в Revit остаётся вне портала |
| Автоматический масштаб, чтение `М 1:100` | `plangeom` делает это сам | Только кандидат с обязательным подтверждением; измерительное ядро не меняется |
| Распознавание размерных линий | Часть определения масштаба | То же, только как свидетельство масштаба |
| OpenCV, Shapely, pypdfium2 в `apps/api` (ADR-0034) | Зависимости `plangeom` | Запрет сохраняется: отдельный образ и тест на импорт |
| Длины только через каноническую геометрию и калибровку | У `plangeom` своя геометрия | Модель не пишет в обмер и не выдаёт измерений; сверка при наличии калибровки |
| Семантические правила в ядре | Роли стен и типы помещений | В ядро не попадают, живут в контуре модели |
| Сравнение ревизий чертежа (`drawing.compare`) | Этап M8 | Сравнивать только версии модели; решение отдельно, перед M8 |
| ProjectGraph | Модель внешне похожа | Прямо записать: не ProjectGraph, агентов и графа знаний нет |

Остаётся в силе: клиентские данные вне git и внешних API; `.env` не менять; запрет стоимости; `takeoff.ai` не
включается; `plangeom` не выдаёт данные в расчёт calc.

**Связь с другими треками.** Stage 2B: `plangeom` — детерминированный конкурент обучаемым моделям, поэтому в
бенчмарк Prompt 18 его стоит добавить как ещё одну строку. SU10: перед M1 нужно выяснить, не от того же ли автора
эта библиотека: она близка к их работе, но это моё предположение. Пожаротушение (ADR-0034): его геометрия АР может
позже питаться этим же разбором, но только отдельным решением.

## 10. Риски

| Риск | Что с ним делаем |
|---|---|
| Нет лицензии, альфа, неизвестный автор | Решение M0; закреплённая версия, копия пакета в своём реестре; запись в матрицу лицензий |
| Проверка стоит дороже ручной модели | Измеряем время в G1 до разработки экранов |
| Смена формата `plangeom` | Строгий адаптер под версию, повторный прогон при обновлении, правки на устойчивых ключах |
| Кодировка и штампы других проектировщиков | G1 на 3 разных объектах; состав и раздел задаёт человек |
| Сканы | Сразу отказ со статусом; остаётся ручной путь |
| Нехватка памяти на сервере | Отдельный контейнер с пределом, один разбор за раз; проверить размер сервера перед M3 |
| Непубличный API | `on_sheet` доступен только в `plangeom.document`, а `assemble` не документирован; просить автора открыть |
| Данные заказчика в git | `plangeom_example_*.json` и `plangeom_fields.txt` сейчас **не игнорируются**; в тесты — только синтетика |

**Просьбы к автору `plangeom`:** лицензия; публичные `on_sheet` и `assemble`; приём раздела извне; `host_wall` у окон;
устойчивые идентификаторы; версия схемы вывода.

## 11. Решения владельца

1. **Формат Revit.** Прислать образец JSON и сказать, кто и чем его собирает, какой шаблон Revit используется. Без
   этого M1 не завершить.
2. **`plangeom`.** Кто автор и на каких условиях можно использовать в боевом контуре? Без этого возможны M1 и M2,
   но не M3.
3. **Что такое «версия».** Рекомендую: версия Quantor — замороженный комплект, ссылается на строку HUBTender, и
   несколько комплектов могут ссылаться на одну строку, если документы менялись без клонирования тендера.
4. **Запреты.** Утвердить раздел 9 и ADR-0035.
5. **Охват первой модели.** Рекомендую АР: стены, двери, окна, плиты с отверстиями, помещения. КР, лестницы и
   лифты как семейства — после G2.
6. **Объекты для G1.** Три объекта, по возможности с готовой моделью Revit и хотя бы один не от того проектировщика.
7. **Допуски G1.** Подтвердить или изменить пороги раздела 8.
