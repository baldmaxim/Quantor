| ----------------- | ------------------------------ | --------------------------------------------------------------------------- |
| страница pdf.js   | лист × масштаб × DPR           | `apps/web/src/lib/viewer/pdfjs-backend.ts:83-89`                            |
| области           | тот же, от отрисованного листа | `DrawingViewport.tsx:194-199`, `apps/web/src/lib/viewer/overlay.ts:127-141` |
| черновик масштаба | тот же                         | `DrawingViewport.tsx:410-412`                                               |
| измерения         | тот же                         | `DrawingViewport.tsx:439-441`                                               |

Панорама и зум двигают стопку CSS-преобразованием, минуя React (`DrawingViewport.tsx:214-225`).
Страница перерисовывается после паузы жеста и только если сменились масштаб или DPR (:317–335,

### 7.2 Узкие места

1. **Холсты во весь лист.** A1 (2384 × 1684 pt) при 266 % и DPR 1,5 — это 9512 × 6719 ≈ 63,9 Мп
   на холст. Четыре холста — ≈ 256 Мп, около 1 ГБ RGBA. Потолка числа пикселей нет ни у
   pdf.js-бэкенда, ни у слоёв. Браузерные пределы площади холста, особенно в Safari на iOS, при
   такой схеме могут наступить раньше памяти — это стоит проверить замером в Prompt 02.
2. **Каждый слой перерисовывается целиком.** `drawMeasurements` обходит все измерения
   (`measurement-overlay.ts:65-90`), слой областей — все области (`overlay.ts:71`). Отсечения
   по видимой части нет. Кадр слоя с 1000 фигур — ~60 мс на программной растеризации
   (`HANDOFF_TO_STAGE2B.md:125`).
3. **Попадание — линейный перебор.** `hitTestMeasurements` на каждый щелчок переводит в экранные
   координаты все точки всех измерений (`measurement-overlay.ts:197-219`); области — тоже перебор
   (`DrawingViewport.tsx:376-403`). 10 000 фигур — ~4,6 мс (`HANDOFF_TO_STAGE2B.md:126`), в кадр
   уже не укладывается (`16-acceptance.md:158-159`).
4. **Hover областей идёт через React.** При смене области под курсором — `setHoveredId` и полная
   перерисовка слоя областей (`DrawingViewport.tsx:597-602`). Для слоя кандидатов r2 запрещает
   запись состояния React на `pointermove`.
5. **Зум растягивает растр до паузы.** Лист мылится, затем перерисовывается снова целиком
   (`DrawingViewport.tsx:237-253`).
6. **Нет примитива «видимая область».** `RenderRequest` — это `pageIndex`, `scale`, `canvas`,
   `signal` (`apps/web/src/lib/viewer/backend.ts:19-25`): бэкенд умеет рисовать только лист
   целиком. Слоя кандидатов тоже нет.
7. **Память слоя не измерена** — браузер округляет `performance.memory`
   (`HANDOFF_TO_STAGE2B.md:178`).

### 7.3 Истина координаты

`pointFromEvent` (`DrawingViewport.tsx:359-374`) переводит указатель в нормализованную точку через
левый верхний угол стопки, масштаб камеры, размер листа в pt и DPR: `placeRenderedPage`
(`coordinates.ts:222-236`) и `toNormalizedPoint` (`coordinates.ts:113-123`). Размер холста
`canvas.width/height` не читается. **Математическая координата от разрешения растра не
зависит** — инвариант r2 №12 в этом смысле соблюдён, блокера для Prompt 02 нет.

Остаток для Prompt 02:

- **Разные округления.** Размещение квантуется `floor` в физических пикселях
  (`coordinates.ts:232-233`), а CSS-размер холста страницы — `floor` в CSS-пикселях
  (`pdfjs-backend.ts:88-89`). При DPR ≠ 1 край листа расходится со слоями и с моделью указателя
  на долю CSS-пикселя, до одного. Это меньше ошибок живой приёмки, но «пиксель в пиксель», которое
  обещает комментарий `coordinates.ts:218-220`, не выполняется.
- **Прямого теста нет.** Утверждения «координата не зависит от размера растра» тест не держит.
  Ближайшие — `coordinates.test.ts:184` («масштаб 1 даёт размер страницы, а не растра») и
  `DrawingViewport.test.tsx:360` («точки хранятся нормализованными и переживают зум»).

Фраза `16-acceptance.md:370` о том, что «точность клика ограничена пикселем отрисовки», верна для
прицеливания глазом: по грубому растру в линию чертежа не попасть. Для формулы координаты она
неверна. Отсюда вывод прежний, а причина точнее: снижать разрешение нельзя из-за чёткости, и
правильный путь — рисовать только видимую часть (r2 Prompt 03).

## 11. Ловушки, которые сломаются молча позже

- **`apps/api/tests/test_contracts.py:30-64`** — `FORBIDDEN_PACKAGES` читает только
  `apps/api/pyproject.toml`. Инвариант r2 №11 он держит, но `vision/pyproject.toml` не увидит:
  страж Ultralytics из Prompt 09 должен охватить все манифесты. Сообщение теста говорит
  «Stage 1» (:63).
- **`test_contracts.py:66-76` и `:78-88`** — список `JobType` сверяется целиком, и ни одно задание
  не должно совпадать с этапом конвейера, использующим модели. Задание `ai_geometry_predict`
  из Prompt 20 сломает оба — переписывать осознанно, а не подгонять.
- **`test_contracts.py:98-100`** — «у `ModelProvider` нет реализаций». Локальный runtime
  Prompt 20 его нарушит.
- **`apps/api/tests/test_control_plane.py:227-237`** — `admin_editable=False` у `takeoff.manual`;
  изменится в Prompt 01.
- **`apps/web/e2e/smoke.spec.ts:159-169`** — вкладка «Обмеры» всегда включена. Подключение флага к
  вкладке этот тест сломает справедливо.
- **`apps/api/tests/test_meta.py:28`** — `stage == "stage-1.5"`. Тест `:31-35` (флаги Этапа 2
  выключены) при default OFF останется верным.
- **`benchmarks/datasets/measurement_v1.json:336-356`** — «бантик» равен нулю. Prompt 05 меняет
  ожидание, а вместе с ним счёт «16 из 16».
- **Схема против миграций.** `test_schema_matches_migrations.py` без базы пропускается, а
  `alembic check` не видит CHECK, частичные индексы и `server_default`
  (`docs/stage2a/00-preflight-audit.md:189-193`). Миграция отверстий заденет именно CHECK
  `points_match_geometry`.
- **`str_enum` обещает CHECK, которого не создаёт** (`HANDOFF_TO_STAGE2B.md:179-180`). Новые
  перечисления состояний кандидата унаследуют этот дефект.
